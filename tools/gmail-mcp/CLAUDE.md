# gmail-mcp: decisions and traps

Setup and tools are in `README.md`. This file records why it is built this way. It is modelled on `../gchat-mcp/`, whose `CLAUDE.md` holds the reasoning behind the shared mechanisms (permission-prompt lock, per-call timeouts, secret-file denylist, copy-not-import); read it before changing a mechanism here.

| Decision | Why |
|---|---|
| Its own server and token, sharing only the OAuth client with Sheets and Chat (19/11/2026) | A refresh token keeps the scopes it was minted with, so adding Gmail scopes to another tool's token would force that tool to sign in again, and mail is wanted in different projects than Sheets. `auth.ts`, `google.ts`, `zone.ts` and the `secrets.ts` denylist are copies of gchat-mcp's, not imports, so neither tool breaks when the other changes |
| Scopes exactly `gmail.readonly` and `gmail.send`; `auth` stores nothing if Google grants anything else or less (`storeGrant` in `auth.ts`) | The narrowest pair that reads and sends. `gmail.modify`, `gmail.compose` and `mail.google.com` all allow changing or deleting mail, so a misused sign-in can at worst read mail and send a message, never delete or relabel. The check is exact in both directions, as in gchat |
| `gmail.readonly` is a Google restricted scope, so the OAuth client must be Internal (Workspace) | An Internal client needs no verification and keeps the sign-in until revoked. An External client in Testing expires sign-ins after 7 days, and publishing it means Google's restricted-scope security assessment. Written in the README so a colleague outside Workspace knows before they start |
| Sending is two steps, like gchat: `email_send_preview` (read-only), then `email_send` with `_meta["anthropic/requiresUserInteraction"]: true`, no AskUserQuestion step on top | Same reasoning as gchat (the permission prompt is the one lock a model cannot answer, `dontAsk` and `claude -p` deny it so headless runs never send, and gchat's `CLAUDE.md` has the measurements). There is no extra headless code check: the flag is the check, and `tests/send.spec.ts` asserts that only `email_send` carries it, as the JSON boolean `true` |
| The confirmation string is `recipients` ("to: a@x; cc: b@y"), and the digest covers the whole message | gchat shows a space name the user can read; for mail, who gets it is what the user must read in the phone prompt. Matching ignores case and spacing only. The digest is the first 32 hex of sha256 over to, cc, bcc, subject, body, each file's name and content hash, threadId, In-Reply-To and References, so any change after the preview (including a file edited on disk) is refused. From is not in it: it is always the signed-in account |
| Duplicate guard from `sent.log`: a SENT entry with the same digest in the last 10 minutes refuses with ALREADY SENT (logged DUPLICATE) | Gmail has no idempotency key (Chat's `messageId` lets Google refuse a retry; `messages.send` always creates a message), and a retry after a timeout is the likeliest double send. Only SENT arms it: an UNSURE send must stay retriable once the user has looked in Sent, and a deliberate repeat after 10 minutes goes. The guard is process-local to the log file, so two machines or a wiped log are not covered |
| Outcomes: Google 400/401/403/404/413/429 and `gmail:` errors are NOT SENT; a timeout, 5xx or network failure is UNSURE WHETHER SENT with an `emails_search` `in:sent` hint | A post that timed out may have been delivered, and a blind retry mails the recipient twice. Unlike Chat there is no "already posted" answer to lean on, so the user (via Sent) is the check |
| `replyTo` sets `threadId`, `In-Reply-To` and `References` (original's References plus its Message-ID) and defaults the subject to `Re: <original>`, but fills recipients only when `replyMode` is passed (see the next row) | Replying to the wrong people is the costly mistake (reply-all copies a client's boss). Without `replyMode` the preview shows the original's From, To, Cc and Reply-To and the recipients stay the caller's explicit choice, shown in the prompt. A subject that no longer matches the original warns that Gmail may split the thread, since Gmail threads on `threadId` plus a matching subject |
| `replyMode` (`sender` or `all`, only with `replyTo`) resolves the addresses inside `compose`, the same step the preview and `email_send` both run, and the result feeds `recipients` and the digest unchanged (19/11/2026) | The prompt and the mismatch refusal must keep guarding the real list, so the resolved addresses are never a side channel: `email_send` re-reads the original and resolves again, so a changed original (a new Cc) or a different `replyMode` fails the `recipients` check. Explicit `to`/`cc` are merged (union) rather than ignored, because silently dropping an address the user asked for is worse than showing a longer list. The signed-in address is removed from derived lists only (never from an explicit one), and a derived Cc already in To is dropped. Parsing is a small RFC 5322 splitter (`addresses.ts`) because a quoted name can hold commas; a derived address that fails the plain-address check refuses the call instead of being skipped |
| `forwardOf` re-attaches the original's files by fetching them through the API (`gmail.attachment`) inside `compose`, not by a download step (19/11/2026) | The model never has to save and pick a file path, and no path (a possible secret or swapped file) enters the send. The digest covers the fetched bytes' hashes, so the prompt guards what actually goes out. The declared sizes are checked against the 25 MB encoded limit before any download, then again on the real bytes. Recipients are never filled (forwarding to the wrong person leaks a thread), the message is not threaded, and the subject skips a second `Fwd:` or `FW:`. Preview calls the API for the attachments, which is read-only |
| An expired sign-in is named as such: `invalid_grant` from the token endpoint and a 401 that survives the forced token refresh both say "expired or was revoked" with `GMAIL_CONFIG_DIR=<folder> gmail-mcp auth` (19/11/2026); `email_send` prefixes a compose-time failure with `NOT SENT` | With a second account on an External client in Testing the sign-in lapses weekly, and a bare 401 or "invalid_grant" does not tell Claude or the user what to do or which account. The error text keeps the `gmail:` or `Google API 401` prefix, so a send in that state is classified NOT SENT, never UNSURE |
| `bin/enable [name]` registers a second account under its own server name with `--env GMAIL_CONFIG_DIR` (default `~/.config/syafiqkit/google-<name>`), after checking the name (`[a-z0-9-]`, no leading hyphen) is free and that folder is signed in (19/11/2026) | One server serves one mailbox, so a second account is a second registration, and the tool names (`mcp__gmail-personal__*`) tell the model which mailbox it is acting in. The default name `gmail` keeps the old behaviour. A not-signed-in folder prints the exact `auth` command instead of registering a server that would fail on first use |
| Body is plain text, base64 `text/plain; charset=UTF-8`, cap 20,000 characters; no Markdown, no HTML | Chat renders Markdown, so gchat teaches Markdown; Gmail shows what is typed, so `**bold**` would arrive as asterisks. Base64 over quoted-printable because it needs no line-length or `=` edge cases. The cap is far over what a phone prompt shows, so the preview prints only the first 5 lines and Claude must show the full body in its reply. The gchat 1000-character cap does not carry over: emails are longer, and the recipients line (not the body) is what the prompt must make readable |
| Plain `name@domain.tld` addresses only, strict regex, CR/LF refused | A display-name form or a stray newline is a header-injection route (`a@x\r\nBcc: ...`) and makes the recipients string ambiguous. The caller extracts the address from a `From:` line |
| Attachment limit is judged on the encoded size (about 4/3 of the files plus the body) against Gmail's 25 MB, so about 18 MB of files; at most 10 files | The spec's "25 MB total" is Gmail's limit on the whole message, and base64 grows files by a third, so 25 MB of files would pass the check and then fail with a 400 after the user approved it. Refusing at preview costs nothing |
| A message over 4 MB is sent through the upload endpoint (`/upload/gmail/v1/users/me/messages/send?uploadType=multipart`, `message/rfc822`) instead of JSON `raw` | A large base64url string inside a JSON body is fragile; the upload endpoint is Google's route for big messages (its docs list 35 MB). Small messages use the plain `raw` form. The upload path is unit-tested but not yet seen live |
| Search lists ids then fetches each message with `format=full` and a `fields` mask that drops bodies | `format=metadata` has no `parts`, so the attachment count would be unknown; a mask keeps headers, snippet and part names/ids only. 20 messages cost 21 calls (6 at a time) |
| `email_read` takes `message` or `thread`, exactly one | A thread id and its first message's id are the same string, so one `id` parameter could not say whether a whole conversation or one message was wanted |
| Body extraction: first non-attachment `text/plain` part, else the first `text/html` converted to text (`htmlToText` in `mime.ts`); declared charset honoured, UTF-8 fallback | Plain parts are what a human wrote; HTML-only mail (newsletters, many clients' replies) must still be readable. The converter keeps paragraphs and list items and drops script and style; it is not a renderer |
| The tool's own config folder is refused as an attachment even when `GMAIL_CONFIG_DIR` points outside `.config` | The shared denylist covers the default location by folder name; an override elsewhere would leave the refresh token attachable |
| `attachment_download` ids are matched against `[A-Za-z0-9_-]` / `[A-Za-z0-9_.-]` before reaching a URL | Ids come from model arguments; a `../` would walk to another Gmail endpoint (a draft, a delete) under the same sign-in |
