# gchat-mcp: decisions and traps

Setup and tools are in `README.md`. This file records why it is built this way.

| Decision | Why |
|---|---|
| Its own server and token, beside `gsheets-mcp`, sharing only the OAuth client (13/11/2026) | Adding Chat scopes to the Sheets token would force every Sheets project to sign in again, and a refresh token keeps the scopes it was minted with. Chat is wanted in every repo, Sheets in a few, so they register at different scopes (user here, local there). `auth.ts` and `google.ts` are copies, not imports, so neither tool breaks when the other changes |
| `chat.messages`, replacing `chat.messages.readonly` + `chat.messages.create` (Syafiq, 14/11/2026), with an edit tool and no delete tool | A release note posted with italic headings and merged bullets could only be fixed by hand. `spaces.messages.patch` needs `chat.messages` (Google has no edit-only scope), which also allows deleting, so the worst case of a misused sign-in grew from an unwanted post to a changed or deleted message. The edit is locked like sending: `message_edit_preview` (read-only), then `message_edit` with `requiresUserInteraction`, a checked `recipient`, a `version` (the message's last-edit time) refused if it moved since the preview, a checked `was` (the replaced message's first 60 characters, so the phone prompt shows which message changes, since its opaque name says nothing), and a refusal for any message whose sender is not you. `messages_list` now prints every message's name, not only those with files, because a plain text message was otherwise unreachable unless this session had sent it. Widening the scope needed one fresh `auth`, since a refresh token keeps the scopes it was minted with |
| Text is Markdown when sent or edited through the API (measured 14/11/2026) | A send with `*heading*` rendered italic and lines starting with a typed `•` were joined into one paragraph; the same note edited through `message_edit` as `**bold**` and `- ` items rendered bold with a real list (checked in Chat's web app, 14/11/2026). The Chat app's composer reads `*text*` as bold, which is where the old `*bold*` line in `message_send`'s description came from |
| Sending is two steps: `message_send_preview` (read-only: checks the files, returns the recipient line and the newest message's name), then `message_send`, which carries `_meta["anthropic/requiresUserInteraction"]: true` and requires `afterMessage` (13/11/2026, replacing the elicitation dialog) | The elicitation dialog only rendered in the Mac terminal: driven from the phone over Remote Control, the call hung until interrupted. Claude Code's docs (code.claude.com/docs/en/mcp.md, "Require approval for a specific tool") say a tool with that `_meta` gets its full permission prompt on every call, even in `bypassPermissions`, with no "don't ask again" and allow rules ignored; `dontAsk` and `--permission-prompt-tool` deny it, so headless runs still never send. Remote Control shows that prompt on the phone. Syafiq chose a question first (AskUserQuestion, readable on the phone) plus the permission prompt as the lock, because the server cannot see an AskUserQuestion answer, and a gate the model can satisfy itself is no gate (the reason the first build's hashed code was rejected) |
| `message_send` takes a `spaces/…` name plus a `recipient` the server checks against `chat.label` (13/11/2026) | The permission prompt shows the arguments as passed, and a bare space id tells the user nothing; product review found the friendly name lived only in the preview, which nothing forces Claude to show. A checked name is what the user reads, and unlike the rejected hashed code it gates nothing the user doesn't read |
| `afterMessage` is enforced for DMs, group chats and thread replies only, and a send error separates a Google 4xx (NOT SENT) from a timeout or 5xx (UNSURE WHETHER SENT, re-read first) | Live on 13/11/2026 a drafted reply no longer fitted because the chat had moved on. A top-level announcement doesn't depend on the last message, and a busy space made it unsendable across two approvals. A post that timed out may still have landed, and a blind retry would double-post to a team |
| `checkSendFile` resolves `realpath` first and refuses keys and credential files (`SECRET_HOME_PATHS`, `SECRET_NAMES` in `tools.ts`: the `.ssh`/`.aws`/`.gnupg`/`.kube`/`.docker`/`.claude`/`.config` folders, `~/.claude.json`, `.npmrc`, `.netrc`, `.git-credentials`, shell history, Keychains, `.env*`, `auth.json`, `CLAUDE.local.md`, key files), compared case-insensitively | Review found a symlink defeated "the prompt shows the path": an injected `ln -s ~/.ssh/id_rsa /tmp/photo.png` runs unprompted in bypass mode, and the prompt would show only the harmless path. The OAuth tokens sit under `.config`, so one attach would leak the Chat sign-in. A second review found the first list let through `~/.claude.json` (an MCP bearer token) and `CLAUDE.local.md` (plaintext payment and tax credentials), so single files and basenames joined the folders. Bun's `realpathSync` returns on-disk case; Node's does not, hence the lowercase comparison |
| A DM whose members can't be read is labelled "(members unknown)" and not cached | It used to fall through to "DM (yourself)" and stay that way for the session, and that label is the one line the user checks the recipient on |
| Thread replies use `REPLY_MESSAGE_OR_FAIL`, and a thread outside the target space is refused before asking | `REPLY_MESSAGE_FALLBACK_TO_NEW_THREAD` turns a bad thread name into a top-level post to the whole space, which is not what was approved |
| `orderBy` is `createTime ASC/DESC` (uppercase) | The doc spells it that way; lowercase is unverified and the default `messages_list` call depends on it |
| `messages_search` reads and matches locally | The Chat API's `messages.list` filter takes only `createTime` and `thread.name`, and there is no search endpoint for user sign-ins. Space `lastActiveTime` narrows which spaces to read |
| Names: `sender.displayName` first, then the People API directory, then `people.get`, then the raw `users/<id>` | The Chat `User` doc says a Chat `users/{id}` equals the People id, so one `listDirectoryPeople` call names the whole company. All lookups are cached as promises: `messages_list` resolves up to 1000 senders in parallel, and caching the result instead of the promise sent one request per message |
| Own user id = the member common to your two most recent DMs | Measured live 13/11/2026: People `people/me` answers 403 "requires one of the following scopes: [profile]", `members/users/me` 404s and `members/me` 400s. Adding `profile` would force a fresh sign-in for one id, while every DM lists you plus one other person |
| Space list cached for 2 minutes | The server lives as long as the Claude session, and a search filters spaces by `lastActiveTime`, so a list cached for the whole session silently skipped newly active spaces |
| A member with no `displayName` or `email` stays `users/<id>` | Measured live: one DM's other member comes back with neither (a removed or outside account), and People has nothing for it either |
| The Chat app is named `Syafiq` (13/11/2026) | Google shows the Chat app's name as a chip beside the sender on every message created through the API, even with user sign-in, and nothing in the API removes it. Measured live: the first send showed "You · Claude Chat Reader" to the recipient. Syafiq chose renaming the app over draft-and-paste |
| `attachment_download` uses `media.download` (`GET /v1/media/{attachmentDataRef.resourceName}?alt=media`) under the message scope (built on `chat.messages.readonly`; `chat.messages` since 14/11/2026), and writes into a fresh `mkdtemp` folder with sanitised names and mode 0600 (13/11/2026) | Google's media.download page lists `chat.messages.readonly` among its scopes, so no fresh sign-in. A screenshot posted in a thread was unreadable to Claude, and a reply drafted under Syafiq's name asked the sender which page it showed while he could see it. The page also says it "downloads uploaded media, but not Google Drive files", so a Drive-linked attachment returns its link rather than a Drive scope being added. File names come from other people, so they are cut to their last path part before writing, and each download gets its own empty folder, kept apart from any code |
| `message_send` attaches files with `media.upload` (multipart, `POST /upload/v1/{space}/attachments:upload`) under the message scope (built on `chat.messages.create`; `chat.messages` since 14/11/2026), then `messages.create` with each `attachmentDataRef` (13/11/2026) | Google's media.upload page lists `chat.messages.create` among its scopes, so no fresh sign-in. The preview line names each file and its size, because a file is part of what is being approved, and the permission prompt shows the paths. Paths are checked before anything uploads (absolute, a regular file, not empty, at most 50 MB against Google's 200 MB), and uploads run only inside the approved `message_send` call |
| Message text is capped at 1000 characters; longer messages are split by Claude into several sends (Syafiq, 13/11/2026) | The permission prompt shows the raw `text` argument, and on the phone a 4000-character text is unreadable, so approving would become a reflex tap on the one step Claude cannot answer |
| Each send passes a client `messageId` (`client-` + 56 hex of sha256 over space, `afterMessage`, text, thread and file names and sizes), and a 409 "already exists" reads ALREADY POSTED | A timeout or 5xx after Google committed the post is UNSURE, and a model that retries with the same values would double-post. Google's create-message docs require the `client-` prefix, at most 63 lowercase characters, unique per space. Only a retry reusing the same preview values is caught: after a real post the next preview's `afterMessage` changes, so a deliberate repeat still goes. The 409 wording is unconfirmed live |
| Every Google call has a timeout (30 s; 180 s for uploads and downloads) | With none, a stalled POST hung the call until interrupted, which over Remote Control gave no UNSURE text at all while the message might already be up |
| Sending is refused when the chat's label is a placeholder ("members unknown", "couldn't tell which member is you") | Two such chats share the same label, so the recipient check would pass for the wrong space |
| No environment switch gating `message_send` to this registration (Syafiq, 13/11/2026) | Only Claude Code runs the server on this Mac; the limit (another client would send without a prompt) is written in the README instead |
| A DM is found by email with `spaces:findDirectMessage` | Starting a new DM needs `chat.spaces.create`, deliberately not granted |
