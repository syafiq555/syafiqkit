# CLAUDE.md

Guidance for the Claude Code mod in `hooks/src/` (entry `hooks/src/mod.js`). The plugin-wide rules are in the root `CLAUDE.md`. This file is expected to load when a session reads a file under `hooks/` (Claude Code's nested-CLAUDE.md behaviour), but that was not yet seen in a `Loaded hooks/CLAUDE.md` report or `/context` on 2026-10-16; until it is, open it by hand before mod work.

## The Mod {#the-mod}

`hooks/src/mod.js` is a Claude Code mod: `hooks/hooks.json` carries a `modules` entry beside the settings `hooks` that inject the ruleset (the docs allow both in one file). It draws the line above the prompt, the `/sk` menu, the `/task-docs` reader (Typst-rendered in the terminal) and the `/changes` view (stage, unstage, discard, stacked diffs), keeps an image gallery fed by a `show_image` tool the model can call, saves and resumes session handoffs, and adds pictures under Claude's terminal answers for mermaid, `$$` math, local images and video paths. `hooks/register.test.ts` is its test. `claude plugin test .` loads every `*.test.ts` as a mod test, so other suites (the bun suites in `tools/remote-cli`) use `*.spec.ts`, or the mod run fails on their `bun:test` imports (3 failures, 2026-10-15).

### Editing and building {#editing-and-building}

- **Anything that acts for the user is a button, never a timer.** Commit is one press and Hand off a one-line form with an optional message. Done, Ship, Merge, Refresh, Shrink and a Resume that mentions push or ship show the exact message and an effect line first. Stage and unstage in `/changes` run on press (reversible); Discard asks first and is offered only for the working-tree side. A handoff after a wrap-up is saved by `turn.complete`, armed by the next main-loop `turn.start`, so it covers the wrap-up turn and not an unrelated turn that ends first.
- **The host loads `hooks/src/mod.js` and follows its ES `import`s; there is no build step.** One file per concern under `core/`, `docs/`, `git/`, `handoff/`, `prompt/`, `views/`, `answers/`. Until 2026-10-19 the source was concatenated into a `register.js` bundle on the belief that `$` cannot cross files; `cc-intelligent-ui` (about 30 imported modules) showed it can, under one rule the host states when it refuses a load: **past an import, `$` is followed only into a `function name($)` declaration**, never an arrow `const`. So every top-level function is a declaration. Never put `$` in an object, bound, spread or returned; pass it only to a function called by its literal name (not a ternary or a wrapper that picks the callee); give `$.env.get` a literal name.
- **Every `$.noun.method(...)` call goes through one wrapper in `core/api.js` (`hostUiToast($, ...)`).** That keeps `claude plugin validate`'s `calls:` line short enough to list every call; it used to cut off at about 1,000 characters. Wrappers carry the `host` prefix because a local variable named like an imported `$`-taking function fails the load ("a name declared again over this call").
- **Values a drawing reads live in host state atoms (`atom`, `read`, `update` from `'claude-code'`), and a write redraws only the hooks that read it.** That is how the band's Enhance spinner keeps turning beside an open pane (seen live 2026-10-19). Each atom must be declared in `types/index.d.ts` (named by `plugin.json` `"types"`; the file exports nothing) and as a `const` in every file that reads it, or validate fails.
- **A save that fails to load keeps the old version running.** A multi-step edit that leaves a call to a function not yet written fails the reload and the old module stays live. Write the file whole.
- **After any edit run `claude plugin validate .` and `claude plugin test .`.** Validate lists the calls the mod makes; a new `$.process`, `$.fs.write` or `$.prompt.submit` call changes what colleagues are running and belongs in the changelog. With the `core/api.js` wrappers its calls line lists every call (`$.x (via hostX)`), so a new call shows as a new wrapper there. `--strict` fails on three standing warnings (marketplace description, root `CLAUDE.md`, root `CLAUDE.local.md`), so judge by the plain run. 📖 `docs/ARCHITECTURE.md` §8 for the host-API traps found building it.

### Loading a change and testing it {#loading-and-testing}

- **`/reload-plugins` swaps the mod only when it reports "re-read from its folder"; otherwise start a new session.** Before the directory-source install it did not swap a running session's mod, with or without `--force`, at a new install path or at the same one. Measured 2026-10-12: forced reloads at 1.389.0 kept the 1.388.0 doc list; later, with `installed_plugins.json` at 1.396.2, a footer string edited in the cache copy and a rebuilt `register.js` copied in, plain reloads left `/sk` unchanged, while a new Desktop **New** session showed it. A 2026-10-11 plain reload followed by "seems that resolved it" after an in-place edit is unexplained, so don't rely on it. The docs say a reload loads a module afresh and `--plugin-dir` hot-reloads on save (the user declines `--plugin-dir`); nothing documents a mod-only reload. A reload can also leave the session with no band, its presses logged as `ui_press not handled`. Counter-measurement 2026-10-16: with the reload reporting `syafiqkit@syafiqkit re-read from its folder: ~/.claude/plugins/syafiqkit` (the directory-source checkout, not a cache copy), a plain `/reload-plugins` swapped the running mod on each of about ten rebuilds, in iTerm and in a Desktop **New** session (each build's visible change and new `/sk` version showed). The failures above all edited a cache copy, so the source path is the likely difference, unproven. When the reload says "re-read from its folder", reload and check `/sk`'s version; otherwise start a new session and don't run `/reload-plugins` there before testing.
- **Bump the version for every build under live test.** `/sk` shows `mod v<version>`. Across five same-version rebuilds there was no way to tell the old module from the new, and each build then cost a new session, since a reload may not swap it (see the reload bullet).
- **The kit's stubs do not behave like the host.** In the kit, `find` locates a `Button` or `Input` by key but not a `Text` or `Box`: match Texts with `findAll({ type: 'Text', text: /re/ })`. Three more traps (2026-10-16): a `process.spawn` stub is an async generator that yields `{ stream, text }` and must end with `return { value: { code, signal } }`, or the hook is skipped as "returned neither { value } nor { deny }"; the stubbed `clock.every` returns `{}`, not the `{ cancel }` object the host returns, so guard the cancel call with `typeof timer.cancel === 'function'`; and `press` resolves only when the whole handler has, so a state shown mid-run (a spinner, a progress row) cannot be inspected and a test that tries it times out. Four more (2026-10-19): `$.ui.ask` is answered by `on('tool.call', { tool: 'AskUserQuestion' }, ...)` returning `{ result: { questions, answers: { [question]: label } } }` or `{ deny }` for a dismissal (`on('ui.ask')` refuses to load); `$.prompt.compose({...})` needs `model` and `promptModel` or the hook is skipped; an `Image` `{ file }` under `/home/...` is refused as a network path (macOS automounts `/home`), so stub HOME as `/Users/test`; and `$.ui.mount` of a transcript component needs `plugin`.
- **Older clients are unverified.** Mods need Claude Code 2.1.287 or later (Desktop 2.1.286). The docs do not say what an older client does with a `modules` key, so the ruleset hook sharing the file is the thing to check first if a colleague reports the ruleset missing.
- **A Desktop window onto a terminal session is not a Desktop session, and testing there reads as "mods don't work in Desktop".** Measured 2026-10-11: the band, toasts and `/sk` did nothing in a Desktop window whose session ran in iTerm (`~/.claude/sessions/<pid>.json` says `entrypoint: "cli"`, and its `bridgeSessionId` matches the id Desktop shows), while `show_image` still answered, since the tool runs in the terminal process. The docs say a remote view draws a mod only in that terminal. A session started with **New** in Desktop does draw the band (`AbovePrompt` raised with `surface: "desktop"`). Commands (`/sk`) in Desktop are not verified.

### Drawing the pane and band {#drawing}

The kit validates trees and props, never what Desktop or the terminal draws, so check each layout, hover or focus claim in a live session before trusting it.

- **Pictures draw through different elements per surface.** `Image` and `Raster` are terminal-only and `Svg` is Desktop-only (props `source`, `alt`, `width`, `height`; `source` at most 131,072 characters), so in Desktop the gallery draws each PNG as an `<image>` inside an `Svg` (seen 2026-10-11). A PNG too big for that is drawn from a smaller JPEG copy made with macOS `sips`, in a Desktop session only. Where `sips` is missing or the copy is still too big, the picture shows the Open in viewer button.
- **In Desktop the first click after a page change was lost until every page's first button kept `autoFocus`.** The pressed button leaves the tree when the page swaps, so Desktop has nothing focused and the next click only re-focuses it (measured 2026-10-11). Stripping `autoFocus`, hotkeys or boxed-button styling changed nothing, so `autoFocus` is not terminal-only. The same session found, in the user's Desktop only (the kit reproduced none of it): 8 parallel `$.process.run` diff reads never returned, so every git call goes through one serial queue (`gitRun`); and Desktop's diff rows use hex colours (`DESKTOP_DIFF`) because the host's `diffAdded` theme colour was too bright to read.
- **Desktop refuses some drawings without a word: the pane goes blank, or keeps showing the last drawing it accepted.** Refusals measured 2026-10-11: a `hover.scope` over 64 characters (hash long names, `hoverScope`), two siblings with one key, and pages of some 100,000 characters. Size cases were inconsistent (a 108k page drew, a 103k one didn't), and the docs say only that text past 100,000 characters is cut, so treat size as a risk, not a rule. Text inside a Button loses its colour, and a `Text` made of nested `Text` ignores `wrap: 'truncate'`. The kit catches none of this, so `views/pane.js` checks each tree: keys and hover scopes it replaces with a "could not be drawn" page; size it only logs.
- **Desktop draws every `Code` element as its own boxed block with a copy button, so the host's highlighter cannot colour text inside a row.** The box sizes to its text and ignores the row's background, and `format: 'diff'` draws plain red and green text with the raw `@@` line, no keyword colours, no line numbers (measured 2026-10-12, three builds). So `/changes` colours code with its own tokenizer (`git/syntax.js`) as nested `Text`. That roughly triples a page's drawing size, so uncoloured stretches are bare strings. Before building a page on a host element, draw one in a Desktop **New** session: the kit validates the tree, never what Desktop makes of it.
- **Long pages draw only the rows near the scroll position, on both surfaces.** Desktop and the terminal send `ui.scroll` for the Pane (`offset`, `bodyRows`, `contentRows`), and Desktop re-renders on every scroll. `windowedRows` takes the offset from the render's `e.props.scroll` whenever it is present, not from the stored `state.allScroll`: a jump the mod makes with `$.ui.scroll` left the stored offset stale and drew a blank page (↑ Top, measured 2026-10-12). The first render after a page change still draws from the top. It draws about two screens of `{ height, make }` items, with spacer `Box`es for the rest. Heights must be right, or the drawn rows miss the screen: the terminal hard-wraps lines into one-row pieces, so its heights are exact; Desktop wraps naturally and estimates each line's height from its length. Any new long list goes through `windowedRows`, never a cap (a cap hid files behind "N files collapsed"). Anything at the scroll position (the pinned bars, ↑ Top) reads `windowedRows`' clamped offset (`state.windowAt`), never the raw scroll prop, or after a page shrinks it lands below the content. A kit test of a scrolled short page needs a small `bodyRows`, since the clamp otherwise puts the offset back to 0. Spacers draw in blocks of `SPACER_MAX_ROWS` (10,000) because the host refuses any `Box` taller than that and blanks the whole pane (313 dense files hit it; 200 small ones never do), so a size test needs hundreds of files with long diffs, not a short list.
- **The terminal highlights only the first line of a multi-line button, and `inverse` on a multi-line `Text` stops there too.** So a long wrapped item cannot light as one block through focus (measured 2026-10-14, five builds). A hover group works: every row of the item gets `hover: { scope: hoverScope(...), inverse: true }`, and pointing at any row lights them all (seen live in 1.397.1). Each row is a one-line `Button` so a click lands anywhere, making each row its own keyboard stop. The kit drops `hover` from the nodes it returns, so no test can assert it: check it live. A hovered cyan glyph inverts into a solid cyan cell, so keep such a glyph to one character.
- **A row of buttons needs `flexWrap: 'wrap'` or it clips in a narrow pane, with no error.** Measured 2026-10-15: the doc reader's toolbar lost everything after "Hand off" in a ~40-column Desktop pane. Two exceptions. A row inside a `windowedRows` `{ height, make }` item must stay one line, because wrapping breaks its height. A row whose `truncate-end` Texts sit beside its buttons (the band's handoff row) keeps the buttons visible by shrinking the text, which wrapping defeats, since a wrapped row only shrinks an item alone on its line. The kit checks props, not layout, so look at a narrow pane in a **New** session.
- **A `ui.focus` hook wrote nothing in a real terminal while the arrows moved the ring** (1.396.7, 2026-10-14), and the kit raises `$.ui.focus({ requestId, key })` with `key` and no `component`, so the kit cannot stand in for it. Do not build on focus events until a live log line shows one arriving.
- **The band stays drawn beside an open pane, with no hotkeys while the pane is open** (the pane owns `c`, `d`, `g`; 1.405.0), and a dim "keys go to the pane" at the end of the launch row says so. A band press then switches the pane's view in place: `openPane`, `openChanges` and `openImages` take `fromBand`, and with it skip `$.ui.open` when `state.isOpen` and do nothing when that view is already showing (a typed `/task-docs`, `/sk` or `/changes` still opens with `focus: true` and resets, since focus is then in the prompt), because what the host does with a second open of the same id is unmeasured and a re-run would wipe picks, the filter and a typed handoff note. `redrawBandAfterClose` gives the hotkeys back. The Enhance row's spinner reads the `enhanceTick` atom, so it keeps turning beside an open pane (`$.ui.invalidate` could not target the band alone).
- **Rendered pictures go to `Image` as `{ file, format: 'png' }`, never as `{ png }` bytes.** A rendered task doc is several pages of up to 2,400 px; sent as base64 in one tree it was the suspected cause of a blank pane (2026-10-19, not confirmed live), while a file path costs the tree nothing because the terminal reads the file itself. Typst names pages with `{p}`: `{0p}` zero-pads to the page count (`-01.png` from 10 pages), which a reader of `-1.png` misses and the `.ok` marker then caches. Typst runs from the vendored `hooks/render/` template (from `cc-intelligent-ui`, MIT; `NOTICE.md`), so a template change bumps `TYPESET_RENDER_VERSION` to retire cached pages.
- **Answer pictures (`answers/pictures.js`) add to an `AssistantMessage` tree and never replace it.** Claude Code draws an answer's text as one node, so pictures can only come after all of it. The hook returns the host's tree untouched when it already holds an `Image`, which is how it stands aside for `cc-intelligent-ui`; that plugin is all-or-nothing, so with it on (`/iui on`) ours shows nothing. A video or image path counts only with a `/` and a file name before the extension: bare `.mp4` in prose once drew three dead Open buttons.
- **The band must yield while the host holds a survey.** `AbovePrompt` carries `hasSurvey`, true while a notice such as "Heads up ... 1: Learn more 2: Knew this already 0: Dismiss" owns the band; a hook that returns its own tree there covers it, so `bandView` returns `next(e)` first. Seen as a screenshot, 2026-10-14.

### Debugging {#debugging}

- **When a mod seems dead:** `claude plugin test` from a folder with no mod says whether mods can load, `/plugin` shows a `mods active` line, and `claude --debug` logs `hooks module <name> not loaded:` with the reason.
- **When the pane misbehaves, read `~/.claude/doc-pane-cache/mod.log`.** It holds the last 300 notable events: refused or oversized pages, git commands that failed or timed out, pictures that could not be shrunk, and `ui.fault`. Each line carries a per-load tag, so two tags in one run mean two module copies. Close diagnostics: `pane drawn while closed`, `close: <person|plugin> asked to close`, `open <view>: not placed`. A blank expanded Desktop frame after close was still unexplained on 2026-10-12: it stayed blank in a clean restart with one module copy, one `person` close and nothing drawn after, so the post-close redraw is not its cause and it may be Desktop's own. The band does need that redraw (`redrawBandAfterClose`): it stays beside an open pane without hotkeys (the pane owns `c`, `d`, `g`), and the redraw after close gives the hotkeys back. `ui_press not handled` appears in Desktop's `~/Library/Logs/Claude/claude.ai-web.log`, not in `mod.log`. Claude Code's own debug log is written only under `--debug`, which a Desktop session never has.

### What it runs and writes {#what-it-runs}

- **It runs with the user's permissions.** It runs `git` (read-only `status`/`diff`, and `add`, `restore`, `rm --cached`, `clean` only from a button press, with `GIT_LITERAL_PATHSPECS=1` so a file named `[id].tsx` is never read as a glob), `chmod` (best effort), `uname` plus the system viewer (`open`, `xdg-open` or `start`) for the gallery's Open button, `sips` for the Desktop gallery's smaller copies and answer images, `npx @mermaid-js/mermaid-cli@12.0.0` (pinned; bump it deliberately), `typst` (from PATH, `/opt/homebrew/bin` or `/usr/local/bin`) for rendered docs and `$$` math, `ffmpeg` for video first frames, and `perl` once to read the terminal cell size from `/dev/tty`. Each is optional: without it that picture falls back to text.
- **It adds one section to Claude's system prompt** (`prompt.compose`, id `syafiqkit:answer-pictures`) in terminal sessions only, telling Claude its mermaid, `$$` and path output is drawn; `/sk` → Answer pictures turns that and the pictures off, saved in `$.store` key `answerPicturesOff`.
- **The Enhance button** reads and replaces the prompt box (`$.prompt.read`, `$.prompt.fill`) and streams a headless `claude -p --model haiku --permission-mode auto --disallowedTools Edit,Write,NotebookEdit --output-format stream-json --verbose` through `$.process.spawn` (from PATH, else `~/.local/bin/claude`, with `SYAFIQKIT_MOD=0` so the child loads no mod), about US$0.07 a press; when that fails it falls back to two `$.model.complete` haiku calls. `--disallowedTools` holds in the child's sub-agents too ("disabled for this session, in subagents as well as here"), and auto mode works under `-p`.
- **It writes only under `~/.claude/handoffs/` and `~/.claude/doc-pane-cache`** (diagrams, picture copies, `typeset/` doc pages, `answers/` previews, `mod.log`); `npx` also fills its own cache and downloads a browser on the first diagram. `$.tool.register` adds `mcp__syafiqkit__show_image` to every session's tool list.
- **Switches and pictures.** `SYAFIQKIT_MOD=0` turns the mod off without touching the skills. Pictures need `CLAUDE_CODE_FORCE_TERMINAL_IMAGES=1` in terminals Claude Code does not recognise (iTerm2 measured: it answers the graphics query and is still classed as unsupported); the variable went into the `env` block of `~/.claude/settings.json` on 2026-10-10 and pictures drew; whether a plugin reload alone would have been enough was not tested. The gallery draws `Image` from `{ png: base64 }` like the diagrams and holds 12 images at most. A `{ file, format }` source was tried first and showed only the fallback line, but the variable was unset then, so that does not show the source is unsupported.
