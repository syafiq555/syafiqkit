# Git Commit

Create conventional commits from staged changes.

## Workflow

The `gitStatus` context block at conversation start is a snapshot of the invoking directory only, taken at session start — it says nothing about nested repos. Run `git -C <subdir> status -s` for every nested repo before concluding what's in scope.

1. **Find repos to commit** — check working directory for staged changes, then subdirs for nested `.git` repos with staged changes. Skip any repo with nothing staged.

2. **Changelog gate**: if staged changes include user-visible fixes/features/improvements, add an entry to the **workspace-root `CHANGELOG.md`** — the top-level one above all sub-repos — not the sub-repo's own, even when committing inside a nested repo. This applies whenever sibling repos share one root workspace; a standalone single-repo project updates its own `CHANGELOG.md` instead.
   - Read root `CHANGELOG.md`, find/create today's `## [YYYY-MM-DD]` heading, prepend a bullet under the right sub-heading (`### Fixed` / `### Added` / `### Changed`) tagged `- [<repo-name>] <description>`.
   - A staged diff often bundles more than one independent user-visible change (built across separate sessions, committed together). Today's heading already existing doesn't mean the gate is satisfied — check the diff for every distinct user-facing behavior and give each its own bullet.
   - An entry that already exists is a claim to read against the diff, not a gate already passed. Follow-up work on a branch commonly *changes* what an earlier commit's entry described (a unit-per-invoice rule reversed to one invoice per cycle) rather than adding beside it, and the entry's presence is exactly what makes the check feel done. Both commits ship as one unshipped feature, so rewrite the sentence the diff contradicts; a second bullet beside a now-false one leaves the release note stating both.
   - Stage with `git add <path-to-root>/CHANGELOG.md` (relative to sub-repo cwd, e.g. `../CHANGELOG.md`) — it lives outside the sub-repo's `.git`, so commit it as part of the root repo's commit (or a standalone `docs` commit in root).
   - Always a dated heading, never `[Unreleased]`; no per-repo version numbers as headings — version numbers go inline in bullet text.
   - Do this without asking the user first.

3. **For each repo with staged changes**:
   - Read the diff: `git diff --staged --stat` + `git diff --staged`. Ensure staged files belong to this session. On shared checkouts, the index often holds peer work (📖 `../_shared/references/diff-ownership.md`): classify each path by content, not by assumption. If not yours, commit only your paths: `git commit -- <paths>` for whole files. Two cases need a temporary index instead (📖 `../_shared/references/diff-ownership.md#peer-hunk-in-your-file`): a peer's hunk sits inside one of your files, or the repo's pre-commit hook stashes the tree (husky + lint-staged does). A stashing hook also needs `--no-verify`, with its checks run on your paths by hand and said in the body. Afterwards re-sync the shared index for your paths, or a peer's next bare commit reverts them. The same applies when splitting into feature-based commits: each commit needs its own pathspec, never a bare `git commit` taking the whole index. When ownership isn't clear-cut, stop and show the user the foreign list rather than guessing; a process check (`pgrep` for a test runner) is not an ownership check. Measured 2026-10-01: a "commit and pull" took 331 pre-staged files, most belonging to three live sessions, after checking only for running tests. **Tell: you are about to commit more paths than this session edited.**
   - **Read the staged task docs before deciding a subject or whether to commit.** A diff shows what changed, not what the feature is or whether it may be committed. For each staged `tasks/**` doc, read its Quick Start in full and each section a staged hunk sits in; its `Status:` line is a heading that points there, not content to report. A Quick Start commit precondition (e.g. "commit only when the user asks", "commit by pathspec only", "shared with another session: commit only our hunks") gates the commit: check it before the first `git commit`, and when it is unmet, stop and show the user. A staged `decisions/*.md` usually offers the best wording for the body. **Tell: your subject came from a diff hunk, or your doc read was a grep of its Status line.**
   - Decide scope and message. When staged changes span several features, create separate commits — one per feature, not one mega-commit. "All" settles ownership, not history structure; a single commit can't be reviewed or reverted by feature. Write each subject from that group's diff and task doc (not path names — they group files but don't describe what they do). Measured 2026-10-07: titles guessed from `Mail/` and `Onboarding` paths were wrong for two of nine commits, one removed a step rather than "scoping" it, cost a second force-push. Where peers' hunks share the worktree, build commits from a temporary index (`git commit-tree`) so only intended blobs move. When one file's hunks belong to different features and per-hunk staging is impractical, group by file set instead and say in the final message which commits carry a neighbouring feature's hunks. Ask before force-pushing commits already on a remote.
   - Determine type: `feat`, `fix`, `refactor`, `chore`, `docs`, `perf` — highest-impact type wins regardless of file count (a user-visible feature co-landing with a refactor is `feat`). Determine scope from file paths (e.g., `app/Services/Workshop/*` → `workshop`). Commit: `<type>(<scope>): <description>` — lowercase, no period, imperative, max 72 chars. Read `git log --oneline -5` before writing the subject — if a recent commit already names the feature, this subject says what the batch adds on top.
   - Ensure docs reflect committed state. Check `tasks/**/current.md` for docs whose *files* appear in the staged set even if the doc itself isn't staged. A doc's status belongs to its own feature; status read from a neighbouring doc lands in the message wrong. A staged doc from a domain your code didn't touch may record LIVE state (fixtures bought on production, a flag set on one environment) rather than BUILD state; that standing fact survives into whatever ships next, so carry it forward even when the commit is unrelated. Also check for staleness: docs naming uncommitted work, pending changes, or deferred features need `task-summary` to refresh. Use grep `grep -n -i "uncommitted\|not yet pushed\|pending"` — these tokens are true when written but silently stale later. Skip code-shaped tokens (camelCase, kebab, quoted strings like `pending-step chip`) — these are domain terminology; say which hits you skipped and why, since a silent skip looks identical to a doc with no stale markers. If `task-summary` already ran this session, verify the claim is resolved by grepping after the fix; skip re-running if grep returns empty. Also run `grep -rl` across `tasks/**/*.md` for status claims about the features you're committing (e.g. "deferred pending backend work"), and flip stale "deferred"/"scoped"/"not built" language to match what shipped. Run it per repo from that repo's own root, since grep doesn't see across repo boundaries and a two-repo feature often leaves its stalest claim in the other repo's docs. Cross-reference: `/ship` overrides this gate; see `skills/ship/SKILL.md` Step 2. This gate's `task-summary` run satisfies `/done` Step 4 only when a real run happened, not when the hit matched code-shaped tokens — `/done` Step 4 scans independently; see `skills/done/SKILL.md` Step 4.
   - Verify the commit: `git show --name-only --format="" HEAD`, then `git status --short`. Read the file list against what you staged — a pre-commit hook can widen a commit after your last look, so verify against what exists now, not the staged intent. `git log -1 --oneline` can't see this: one subject prints identically whether the commit holds your six files or the whole tree. Also verify peer hunks: a pathspec scopes files, not hunks, so before committing a file another session also touched, read `git diff HEAD -- <path>` hunk by hunk and commit only yours; 📖 `../_shared/references/diff-ownership.md#peer-hunk-in-your-file` for the procedure. If a pre-commit hook reformatted code, its output shows `stash`, `Backing up original state`, or `Applying modifications` — the staged-column reading you took earlier no longer describes what was committed, so re-read the file list. Where the commit came back wider than staged, `git reset --soft HEAD~1 && git reset` restores the pre-commit state, then re-commit with `--no-verify` to bypass the hook. Say so in the commit body — skipping a hook is a decision the next reader should see. For a batch built with `commit-tree`, the moved branch is the proof: `git rev-parse HEAD^{tree}` must equal `git write-tree` (the shared index) once every staged path is committed. Any path committed from a blob the shared index didn't hold shows in `git diff --cached` as a reverse change; re-sync it with `git reset -q -- <path>`, then re-check that `git diff --cached --name-only` is empty.

4. **Validate**: no secrets committed, type matches changes.

5. **Push** (only if the user's invocation includes "push"): per-repo, check `git status -sb` for tracking state. If tracking an upstream, `git push`, unless `git status -sb` shows `[behind N]`: the push would be rejected. Integrate from a throwaway worktree (`git worktree add`), never by pulling or stashing in the shared checkout, since a rebase needs a clean index and a stash takes peers' staged work with it. If no upstream (new local branch), confirm with the user before `git push -u origin <branch>` — creating a new remote branch is visible and hard to reverse.

## Commit Format

```bash
git commit -m "$(cat <<'EOF'
<type>(<scope>): <message>
EOF
)"
```

## Anti-Patterns

| Avoid | Instead |
|-------|---------|
| `fix: fixed stuff` | `fix(auth): resolve token expiry race condition` |
| `update code` | `refactor(orders): extract validation to service` |
| `wip` | `chore: wip - <context>` or don't commit |
| `refactor` when a user-visible feature also landed in the same staged set | `feat` — highest-impact type wins regardless of file count |
