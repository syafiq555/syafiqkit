# Watch Sheets

A shared sheet during a busy week changes in small ways: a client adds a line, a tester flips a status, someone closes a row. Most of it is not the user's turn. The skill is the body of one check, run again on a schedule, and its job is to raise only what needs them. Google's SRE guidance is the bar: "Every page should be actionable", and alerts that come too often get skimmed and then ignored.

## Setup (first check only)

Find each sheet's id and its layout before the first read. Look in the project's own instructions (CLAUDE.md, CLAUDE.local.md, a tracker config JSON) before asking. A project that already runs a tracker usually records the id, the reply column, the status column, which statuses mean "our turn", and the colours and names its side writes with. Write down, for this session:

- **Tracker:** id, reply column (e.g. `Tracker!F2:F200`), status column, ask column, `myNames` (every name your side signs with, teammates included), the colours your side writes in, and which statuses mean our turn. `mine` defaults to black and uncoloured text, so a tracker that colours your side's lines (a `setup-tracker` config's `person_colours`) needs those colours added to `mine`, or every row with a seeded line of yours lists as awaiting a reply. When the status names who acts next, only that status is our turn. A tracker with no status column has no handoff to read, so every client line after ours is our turn.
- **Test workbooks:** id, the summary tab with its counts, the defects tab, and the tester columns on each role tab (tester, date, remarks).

When the user asks for a repeating check and no job exists yet, run the first check in full, then schedule one with `CronCreate`. **The prompt runs step 1 itself and loads this skill only when a sheet moved.** It opens `watch-sheets check:`, names each sheet's id, and says: "`drive_file_get` each. If this conversation holds no earlier `modifiedTime` for a sheet, a read fails, or any `modifiedTime` differs from the one held, invoke the Skill tool with `syafiqkit:watch-sheets` and <the user's wording>. Otherwise reply one quiet line giving each sheet's `modifiedTime`, and stop." Leave the alert route (a chat id, "alerts go to Telegram") out of the prompt, including when it arrives as the user's wording: args that only name a route ("use telegram") become a plain "watch <the sheets>" in the job, or the route rides along in the passed-through words: the skill picks the route when it alerts, from what is connected then, and a baked-in route goes stale when the user moves between a channel and Remote Control, so the job has to be replaced. Missing or failed reads count as changed because "nothing moved" is true by default when there is nothing to compare, and the times in each quiet line keep the baseline visible through a summary. A prompt that invoked the skill on every firing would reload this whole file each time, and that churn drives the compaction which wipes the baseline. Tell the user the job id, that it lasts only as long as this session, and that it expires after 7 days.

**"No job exists" is a `CronList` answer, not a memory of the jobs you made:** a session can hold watch jobs this conversation never created, and each fires its own full check and its own alert. Run `CronList` before creating one and on every later invocation. A job counts as a watch job when its prompt invokes this skill or opens `watch-sheets check:`; one that invokes the skill without that opener is the older full-reload form, so replace it with the lean one and say so. When more than one watch job runs, keep the one whose interval and sheets match the user's latest request and delete the rest, saying which; if none match, delete them all and create one. `CronList` sees only this session, so before the first `CronCreate` also run `ListAgents` and ask each live peer in the same project whether it already watches these sheets: two sessions each watching one tracker both check every edit, and each claims rows the other may answer. If one does, tell the user and let them pick which keeps watching. **Tell: you are about to call `CronCreate`, or say the watch is off, without a `CronList` result this turn.**

## Each check

1. **Did anything change?** `drive_file_get` on each sheet returns `modifiedTime`. If no sheet moved since the last check, report one quiet line giving each sheet's `modifiedTime`, and stop. A cell edit moves it (measured: a row closed between two checks matched the tracker's `modifiedTime`). The gate saves the full read on quiet checks, not correctness, so the first check of a session always does the full read.
2. **Tracker.** `cells_awaiting_reply` with `statusColumn`, `askColumn` and `myNames`. A listed row is a client line after ours, but many of those lines just pass the item to someone on their own side ("pls review", "noted"). Only a row whose status is our turn, or whose last line asks us something, needs the user. Then read the rows whose status is our turn even when nothing new arrived: our own last line may promise something that later work has kept or overtaken. Find them by reading the whole status column once (Closed rows included, which `cells_awaiting_reply` leaves out); step 3 diffs the same read. It comes back unnumbered (an empty row is `[]`, trailing ones are dropped), so name each row by its cell: the range's first row plus the entry's index, never a hand count. Where the tracker numbers its own rows, report both ("No 47, Tracker!F48"), since that number need not match the sheet row. `alsoRead` numbers only the rows the reply check lists, so these rows still need this read. A client who writes on a Closed row ("still not working") without changing its status is invisible to that check, since `statusColumn` drops Closed rows before looking. So run `cells_awaiting_reply` once more with `skipStatuses` set to every open status, which lists only Closed rows with a client line after ours. Most will be sign-offs ("verified", "done reviewed", "closed as duplicate"), so record each one's last line in the baseline, and raise a Closed row only when its line is new since the last check and asks something (measured: 22 Closed rows on one tracker, all sign-offs).
3. **Status-only moves.** Compare each row's status with the last check's, using the status read from step 2: a row that closed or changed hands adds no text, so the reply check never shows it, and a count such as `skippedByStatus` holds steady when one row closes as another reopens. Name each row that moved, with its old and new status.
4. **Test workbooks.** Diff the summary counts against the last check, read the defects tab, and read the tester columns on each role tab. Request only the columns you compare (check ID, status, tester, date, remarks) as separate ranges per tab, never whole rows: the step and expected-result text in between made one batch read of eight role tabs return 145,000 characters, past the tool's output limit. A tester can move a status without writing a name or remark, so the counts are what catch that, and only a per-check status baseline can then name which check moved: the first check records check ID and status on every role tab, not counts alone. A new Fail, a new defect, or a tester line after our last reply needs the user.
5. **Peer sessions.** Run `ListAgents`. A peer counts only when it is live (not offline) and works in the same project. Its name or opening prompt says which project; a session in another repo is not overlap. Only when step 2 or 4 found something for us, and a peer in this project is live, run `read-summary` for that item's domain and message the peer to ask whether it already has the row. Two sessions replying to one client cell is the failure this step prevents. A peer's "yes, I have it" is that session's belief, which a compaction can erase while the row waits: when the row gains a line after the claim, ask again rather than leaving it, and a peer that then denies the row puts it back to the user as our turn. Never ask a peer to do anything this session would not be allowed to do.
6. **Look once more before alerting.** People keep typing while you check, so run step 2 again just before you report anything as our turn.

Keep the baseline (each sheet's `modifiedTime`, each tracker row's status, each Closed row's last client line, the summary counts, the last tester line per check, and each row the user said to leave with its last line at the time) in the conversation, never in a file: these sheets often hold personal data. After compaction, the next check re-reads everything and treats that as its new baseline. A check with no baseline reports nothing as moved: it records the statuses and counts, and raises only what is our turn as it stands.

## Reporting

- **Something is our turn:** raise it with `AskUserQuestion`, so the user sees it even when away from the transcript. Name the row and its ask in plain words, who wrote it, and whether a peer already has it. Offer: draft replies now; leave it, they'll handle it; another session has it. Several items found in one check go into one question, never one each. A row the user said to leave comes back only when its last line or status has changed since: an unrelated edit moves `modifiedTime` and would otherwise raise it on every check.
  - **With a messaging channel** (the session was started with `--channels`, such as the official Telegram or Discord plugin): `AskUserQuestion` reaches a phone only through Remote Control, which needs the phone on the same claude.ai account, and never shows in the chat. It also holds the turn, so a chat reply waits unread until someone answers at the terminal. So send the alert through the channel's `reply` tool instead, as plain text with the options numbered, write the same text in the transcript, and end the turn; the next message from that chat, or from the terminal, is the pick. Send to the chat the user last wrote from; in a session where they have not written yet, use the plugin's allowlist when it holds exactly one person and no group (Telegram's is `allowFrom` in `~/.claude/channels/telegram/access.json`, and a direct chat's id is the user's id), and otherwise say in the transcript that the alert had nowhere to go. The channel can drop mid-watch: Telegram lets one poller hold a bot, and any other session with the plugin enabled takes it over when its plugins load, so the `reply` tool vanishes from this session. When it is gone, alert in the transcript (and by `AskUserQuestion` when Remote Control is on), and say once how to take the bot back (`/mcp reconnect plugin:telegram:telegram`, typed in this session) and how to stop the takeover (enable the plugin only in the `--channels` session). The message leaves for a third party's servers, so it carries the row, who wrote and a short gist, never the cell's text or anyone's personal details. Drafts the user asks for go back to the chat for a yes before anything is written to the sheet, and a stop confirmation goes there too: transcript text never reaches the chat.
- **Nothing is:** a short report with the counts, what moved (e.g. "row 80 closed"), each sheet's `modifiedTime` (the next scheduled check compares against it), and when the next check runs. After several quiet checks in a row, say so in one line and remind them how to stop the job (`CronDelete` with the id). Stopping the watch (`/loop off`, "stop watching") deletes every watch job `CronList` shows (a prompt that invokes this skill or opens `watch-sheets check:`), then lists again and reports it empty: deleting only the id you remember left two duplicate watchers running while the reply said nothing was scheduled. A check prompt queued before the delete can still arrive once; with `CronList` empty it gets one line saying the watch is off, and no check.
- Replying in the sheet is a separate step that follows the project's tracker rules (`cell_append_line` keeps each person's colours, and writes black unless given the writer's own colour). Never write to the sheet because the check found something: the user picks. A pick that already says what to tell them ("just ask them to do it", "tell her it's fixed") is the go-ahead: draft the line in the project's voice, write it, and show what was written in the report, rather than asking a second time whether to post it. Ask again only when the text says something the user did not choose (a fact you had to work out, a new commitment). A row the user asked to have fixed counts as picked for a plain "fixed, live on X" line, which `ship` writes once the deploy is verified; anything more (a partial fix, a new commitment) still asks.
