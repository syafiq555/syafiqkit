# Score loop

One agent builds, a separate agent judges, and the loop repeats until the judge's score reaches what the user asked for. Anthropic calls this the evaluator-optimizer pattern; their harness work found that separating the agent doing the work from the agent judging it is a strong lever, that a standalone judge is easier to make sceptical than a builder is to make self-critical, and that scores rise and then plateau with headroom left. The loop is only as honest as its judge and its rubric, so most of this skill is about keeping both fixed and independent.

## Before round 1: write the rubric and the stop rule

**The rubric is written once, from the brief, and frozen.** Derive the criteria from what the work is for (the client's brief, the task doc's purpose, the spec), not from what the current version happens to do well. A useful default is ten criteria scored 0/1/2, which gives N/20: 2 = fully meets for every audience and context the brief names, 1 = meets with a visible gap, 0 = missing or broken. Small fixed scales with a written meaning for each level are what the evaluation literature converges on; a 1–10 score per criterion invites ties and drift. Give the judge an explicit "cannot assess from here" so it doesn't invent a grade for what it couldn't check.

**Write the scoring conventions next to the rubric, before any score exists.** Name what is not a defect: input the user or client hasn't supplied yet (judge how the work handles its absence instead), decisions the user already made and recorded, and known test artefacts. Without these, round 1 docks points for things no fix can move, and a later round that adds the conventions looks like progress it isn't. Changing the rubric or conventions mid-loop breaks comparability; if it must change, say so beside the score and treat that round as a new baseline.

**Any criterion with a threshold says how it is measured.** "A page more than 25% blank" invites the judge to eyeball it, and an eyeballed figure produces findings no fix can clear. Name the area (between the margins, not the whole sheet), the instrument (measure it, don't estimate) and what counts. Measured on a 40-page manual: a judge eyeballed a page as 45% blank that measured 20% between margins, and pinning the measurement removed the phantom finding.

**The stop rule is the user's.** If they gave one ("stop at 10", "80–90%", which is 16–18/20), use it as given and add nothing; a cap they set ends the loop. If they didn't, ask for it before round 1 with a suggested default, or in a run nobody can answer mid-way (a `/goal` or other unattended loop) state that default and proceed: a target band and a round cap (four rounds; every published loop that lacked a cap grew one). A plateau (a round that gains nothing, or one point, which is within a judge's run-to-run noise) and a default cap you suggested are reported and asked about ("8–9/10 for three rounds: switch judge, extend or stop?"), never imposed (an unattended run stops at its stated cap and reports): the user who wanted 10 extended the cap from 5 to 10 to 15 on that run. The loop stops on its own only when every remaining point needs the user's or a third party's input.

**Save the rubric, conventions and stop rule to the task doc before round 1, and append each round's score.** Record an agreed retained judge too (agent ID, starting round): switching judge kind is a new baseline, like a rubric change. A loop that lives only in the transcript loses its baseline to a compaction or a fresh session, and "was Y" then has nothing to compare against. With no task doc, keep them in one file beside the work and say where.

## Each round

1. **Dispatch a fresh judge.** A new agent each round, report-only, with the same rubric and conventions pasted in full (including how each threshold is measured), using the project's `product-reviewer` when one exists and a general-purpose agent given the brief otherwise (a document or proposal has no codebase for `product-reviewer` to bootstrap from). Tell it to score from evidence it gathers itself (open the code, run the thing, drive the pages, read the document) and never from earlier reports or your summary (a retained judge's own previous list, below, is the one exception), and to give the evidence before each score. A fresh context is what keeps it from inheriting the builder's framing; a judge that saw the previous round's report tends to confirm it.

   **When fresh judges stall inside their own noise, offer a retained judge.** Each fresh judge docks a different handful of points, so near the top the score wobbles ±1 and never settles: on the manual run, rounds 5 to 10 sat at 8–9/10. The alternative is one judge kept across rounds (resume it by agent ID with `SendMessage`, and spawn it without `name:` so its report still comes back), told to re-check its own previous list against freshly gathered evidence and to add only what it newly finds. That run reached 10 in five rounds. If the judge can't be resumed, give a new one its predecessor's last findings list with the same re-check instruction, and still call it retained. The trade-off goes to the user in one line: a retained judge is less independent and can grow lenient toward fixes it asked for, but it converges. Use it only with the user's yes (an unattended run stays with fresh judges), and label every score with the judge kind (step 5, Stopping). The round that switches judge kind is a new baseline: say so beside its score instead of `(was Y)`.
2. **Check the claims that rest on a checkable record before acting on them, the judge's and the builder's alike.** A judge's "X is still broken" is read from whatever it happened to open, and a builder's "done" describes its intent. Where a claim rests on a file, a setting or a rendered state you can check in one call, check it against the source; a gap that was already fixed comes off the list, and you note the miss rather than re-fixing. The manual run caught a wrong UI direction, a capture artefact read as a real error and an unverified autosave claim this way.
3. **Split the gaps.** Plain fixes go to the build. A gap whose fix changes who can do or see something, or what customers or readers are told, is the user's call: ask those through one `AskUserQuestion`, with the rubric's evidence in each option, before the build round starts.
4. **Build the round's fixes in one dispatch** (the project's `task-builder` when it exists, otherwise a general-purpose agent or this session, one at a time if builders share a database), with its own verification: tests, specs, renders at the widths that matter. Keep the same builder across rounds where you can (spawn it without `name:`, resume it with `SendMessage`), since it already holds the files and earlier fixes; check its report against the output before scoring again. Switch to a fresh builder with a short handoff when its context is filling up or its last report failed the check.
5. **Report the round in one line** the user and any `/goal` evaluator can see: `Round N: X/20 (was Y), fresh judge` (or `retained judge`), the criteria that moved, and what is left. A criterion the judge could not assess scores 0 and is named beside the total (`16/20, 1 not assessed`), so the band is never reached on points nobody checked. `/goal`'s evaluator reads only the transcript, so a score that lives only inside an agent's report never ends the loop.

## Stopping

Stop and report when the user's stop rule is met or what's left needs the user; a plateau or your own default cap is reported and asked about, as above. The final report gives the score per round, which kind of judge produced each, the remaining gaps each with its fix and whose call it is, and anything the judge could not assess. Reaching the band is not a reason to hide what's left: list it so the user decides whether one more round is worth it.

📖 `references/worked-example.md`: two runs. A storefront scored 12/20 then 16/20, with the conventions that had to be added after round 1 and the judge claims that turned out stale; and a user manual taken from 4.5 to 10/10, where fresh judges plateaued and a retained judge converged.
