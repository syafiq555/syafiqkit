---
name: score-loop
description: Score a piece of work against a fixed rubric out of N, fix the gaps, re-score with an independent reviewer, and repeat until it meets the user's stop rule or the rest needs the user. Fires on "score it out of 20", "rate it and keep improving", "loop until 80%", "keep going until it's good", "give it a score then fix", "run the product reviewer and score it", "iterate until N/20", or a `/goal` that names a score. Works on any artefact a reviewer can judge from evidence: a UI or storefront, a feature, a document, a proposal. Not for a one-off review with no loop (that is `done`'s reviewers, `uiux`/`impeccable` critique, or a single `product-reviewer` dispatch), and not for planning a list before anything is built (`plan-worklist`).

# Score loop

One agent builds, a separate agent judges, and the loop repeats until the judge's score reaches what the user asked for (Anthropic's evaluator-optimizer pattern). Separating the builder from the judge is a strong lever: a standalone judge is easier to make sceptical than a builder is to make self-critical. Scores rise, then plateau with headroom left. The loop is only as honest as its judge and rubric, so most of this skill keeps both fixed and independent.

## Before round 1: write the rubric and the stop rule

**The rubric is written once, from the brief, and frozen.** Derive the criteria from what the work is for (the client's brief, the task doc's purpose, the spec), not from what the current version happens to do well. Two shapes fit. **For a UI, design or storefront run, split each criterion into two to four yes/no checks and score the count of yeses** (ten criteria give 20 to 40 checks; freeze the count before round 1). Splitting criteria into yes/no questions "improves the average agreement across evaluator models by 0.45" over a 1-to-5 level scale (CheckEval, arxiv.org/abs/2403.18771), and this is the kind of run where fresh judges reversed each other. When the user named a scale ("out of 20"), show the score on it with the raw count beside it (`16/20 (24 of 30 checks)`), so their stop rule reads as they wrote it. **For a document, proposal, feature or anything else, ten criteria scored 0/1/2 (N/20) still serve**: 2 = fully meets for every audience and context the brief names, 1 = meets with a visible gap, 0 = missing or broken. A 1–10 score per criterion invites ties and drift. Under either shape, write a short pass and fail example beside every level or beside none, since an example for one level alone shifts the scores of unrelated work (arxiv.org/html/2506.22316v4). A rubric already frozen in a task doc keeps its shape until that loop ends. Give the judge an explicit "cannot assess from here" so it doesn't invent a grade for what it couldn't check.

**Write the scoring conventions next to the rubric, before any score exists.** Name what is not a defect: input the user or client hasn't supplied yet (judge how the work handles its absence instead), decisions the user already made and recorded, and known test artefacts. Without these, round 1 docks points for things no fix can move, and a later round that adds the conventions looks like progress it isn't. Changing the rubric or conventions mid-loop breaks comparability; if it must change, say so beside the score and treat that round as a new baseline.

**Any criterion with a threshold says how it is measured.** "A page more than 25% blank" invites the judge to eyeball it, and an eyeballed figure produces findings no fix can clear. Name the area (between the margins, not the whole sheet), the instrument (measure it, don't estimate) and what counts. Measured on a 40-page manual: a judge eyeballed a page as 45% blank that measured 20% between margins, and pinning the measurement removed the phantom finding.

**On a redesign, the rubric scores how well a direction is built, never which direction.** The look is the user's pick from rendered screens before round 1 (`uiux` § Scope, dealt by `taste`), and round 1 changes screens the user sees: a round that lays only tokens and atoms shows no difference and reads as no progress, however much it scored. 19/11/2026: three foundation rounds on a rule-picked look, and the user said "not polish".

**The stop rule is the user's.** If they gave one ("stop at 10", "80–90%", which is 16–18/20), use it as given and add nothing; a cap they set ends the loop. With a retained and a fresh judge, the band is met only when both scores reach it in the same round: the retained line alone converges first and is the judge most likely to have grown lenient (Syafiq, 21/11/2026). If they didn't, ask for it before round 1 with a suggested default, or in a run nobody can answer mid-way (a `/goal` or other unattended loop) state that default and proceed: a target band and a round cap (four rounds; every published loop that lacked a cap grew one). A plateau (a round that gains nothing, or one point, which is within a judge's run-to-run noise) and a default cap you suggested are reported and asked about ("8–9/10 for three rounds: switch judge, extend or stop?"; a fourth option is a research pass with the project's design or domain critique run in parallel, which found the next real fixes when fresh judges sat at 14–15/20 for four rounds on 20/11/2026), never imposed (an unattended run stops at its stated cap and reports): the user who wanted 10 extended the cap from 5 to 10 to 15 on that run. The loop stops on its own only when every remaining point needs the user's or a third party's input.

**Save the rubric, conventions and stop rule to the task doc before round 1, and append each round's score.** Keep the settled list there too (below). Record an agreed retained judge too (agent ID, starting round): switching judge kind is a new baseline, like a rubric change. A loop that lives only in the transcript loses its baseline to a compaction or a fresh session, and "was Y" then has nothing to compare against. With no task doc, keep them in one file beside the work and say where.

## Each round

1. **Dispatch a fresh judge.** A new agent each round, report-only, with the same rubric and conventions pasted in full (including how each threshold is measured), using the project's `product-reviewer` when one exists and a general-purpose agent given the brief otherwise (a document or proposal has no codebase for `product-reviewer` to bootstrap from). Tell it to score from evidence it gathers itself (open the code, run the thing, drive the pages, read the document) and never from earlier reports or your summary (a retained judge's own previous list, below, is the one exception), and to give the evidence before each score. A fresh context is what keeps it from inheriting the builder's framing; a judge that saw the previous round's report tends to confirm it.

   **When fresh judges stall inside their own noise, offer a retained judge.** Each fresh judge docks a different handful of points, so near the top the score wobbles ±1 and never settles: on the manual run, rounds 5 to 10 sat at 8–9/10. The alternative is one judge kept across rounds (resume it by agent ID with `SendMessage`, and spawn it without `name:` so its report still comes back), told to re-check its own previous list against freshly gathered evidence and to add only what it newly finds. That run reached 10 in five rounds. If the judge can't be resumed, give a new one its predecessor's last findings list with the same re-check instruction, and still call it retained. The trade-off goes to the user in one line: a retained judge is less independent and can grow lenient toward fixes it asked for, but it converges. Use it only with the user's yes (an unattended run stays with fresh judges), and label every score with the judge kind (step 5, Stopping). The round that switches judge kind is a new baseline: say so beside its score instead of `(was Y)`.

   **The stronger setup runs both each round: the retained judge plus one fresh judge, in parallel.** The retained one measures progress against its own list; the fresh one finds what nobody looked at yet. The pair earns its place through two separate contexts, not two models. The jury result often quoted for judge panels (Verga et al., arxiv.org/abs/2404.18796) drew its judges from "three disparate model families". No source tests a panel of Claude tiers, so extra judges on other tiers should not be expected to add the same gain. On the 12-round design run (21/11/2026, 📖 `references/worked-example.md`), fresh-only judges sat at 29–30/40 for seven rounds; with the pair the retained judge went 31 to 38 while fresh judges stayed near 31.

   - **Report the two scores separately, never their mean.** The retained score is progress and the fresh score is discovery; the mean (about 34.5 on that run) understated both. The round line (step 5) carries both, with the retained judge's closed count and the fresh judge's new count; "new" means on neither the retained list nor an earlier fresh list, and you dedupe. A move of one point is noise, so report it as no change: the same judge run three times gave the same verdict on only 61.3% of cases (arxiv.org/html/2510.27106), and verdicts flip on about 40% of close calls (arxiv.org/abs/2609.33044).
   - **Keep the retained judge blind to the builder's report.** It gets the work and its own previous list, never "fixed X", and never your own step 2 results either. Judges hold a verdict on a neutral re-check but can be argued out of it when challenged ("substantially reversible under targeted post-decision challenge", arxiv.org/abs/2606.05384), and a fix list is that kind of challenge.
   - **Check the retained judge for drift each round, at no extra cost.** Once both reports are in, and before the round line, you (not a judge) read the fresh judge's findings against the items the retained judge closed. A closed item found again is possible drift: check it against the source as in step 2. If it holds, reopen it, count it against the retained score this round, and note it on the round line (`1 closed item found again`). A second confirmed case in one loop goes to the user: replace the retained judge with a new one given its list, or carry on. This check is our own inference, not a published method; the research shows only that a judge's earlier conversation measurably shifts its later verdicts (arxiv.org/abs/2605.22714), which is why it needs a check at all.
   - **Give each fresh brief a settled list**, one line per entry: criterion, decision, why (the goal it serves), date, decided by, and when to revisit it. The fields follow Nygard's short format for recording decisions (cognitect.com/blog/2011/11/15/documenting-architecture-decisions). You keep the list. It holds only the user's decisions: those recorded before round 1, and each step 3 answer, added the round they give it. A fix the retained judge accepted is not an entry, since it stays open to fresh judges and that is how the drift check works (Syafiq, 21/11/2026). Ask judges to name a rubric criterion and its evidence for every ask. An ask naming no criterion is a `Nit`, as in Google's review guide, where the reviewer "accept[s] the preference of the author" between equally valid approaches (google.github.io/eng-practices/review/reviewer/standard.html); an ask that reverses a settled entry is a `reversal`, which the judge tags and you confirm against the list. Neither costs points. A reversal goes to the user as their call, not into the build; in an unattended run it is held unbuilt and listed in the final report.

   **Ask judges to critique as they go, not only to score.** Tell each one to load `SendMessage` through `ToolSearch` and message `main` with each concrete improvement the moment it finds it (screen or section, element, change, why), so building starts while the judge finishes. That needs the judges dispatched with `run_in_background: true`: a foreground judge blocks this session, and its messages only arrive once it returns. Only an agent type that holds `ToolSearch` and `SendMessage` can do this: a project `product-reviewer` generated before 1.464.3 lacks them and reports at the end, so check the agent's tool list first and either re-run `agent-setup` or use a general-purpose judge for mid-run messages.
2. **Check the claims that rest on a checkable record before acting on them, the judge's and the builder's alike.** A judge's "X is still broken" is read from whatever it happened to open, and a builder's "done" describes its intent. Where a claim rests on a file, a setting or a rendered state you can check in one call, check it against the source; a gap that was already fixed comes off the list, and you note the miss rather than re-fixing. The manual run caught a wrong UI direction, a capture artefact read as a real error and an unverified autosave claim this way.
3. **Split the gaps.** Plain fixes go to the build. A gap whose fix changes who can do or see something, or what customers or readers are told, is the user's call: ask those through one `AskUserQuestion`, with the rubric's evidence in each option, before the build round starts. A judge's "user's call" list is a claim too: check each item against the plan the user approved and their recorded decisions first. A feature the plan already names, built behind the same permission, is a plain fix. Asking about it again re-opens a settled decision.
4. **Build the round's fixes** with the project's `task-builder` when it exists, otherwise a general-purpose agent or this session: one builder per surface whose files don't overlap, all at once rather than one after another. Builders that share a database, a build folder or a test server still run in parallel: give each its own test database, keep a second builder to new shared-component files, and let one builder, or you after they report, own the build and the browser run. Queueing builders on a shared resource doubles the round's wall time for a clash the brief can remove (📖 `../haiku/references/writing-the-prompt.md` § A shared resource the agents queue for). Each builder does its own verification: tests, specs, renders at the widths that matter. Keep the same builder across rounds where you can (spawn it without `name:`, resume it with `SendMessage`), since it already holds the files and earlier fixes; check its report against the output before scoring again. Switch to a fresh builder with a short handoff when its context is filling up or its last report failed the check.
5. **Report the round in one line** (plus the `Needs you:` line below when something waits on the user) that the user and any `/goal` evaluator can see: `Round N: X/T (was Y), fresh judge` (or `retained judge`), where T is the rubric's total or the scale the user named; with the pair, `retained 35/40 (was 33, 2 closed) · fresh 31/40 (3 new, 1 nit)`, and a one-point move printed as `(no change)` while the closed count still shows. Then the criteria that moved and what is left. A second confirmed drift case and reversals held for the user go on a second line that starts `Needs you:`. A criterion the judge could not assess scores 0 and is named beside the total (`16/20, 1 not assessed`), so the band is never reached on points nobody checked. `/goal`'s evaluator reads only the transcript, so a score that lives only inside an agent's report never ends the loop.

## Stopping

Stop and report when the user's stop rule is met or what's left needs the user; a plateau or your own default cap is reported and asked about, as above. The final report gives the score per round, which kind of judge produced each, the remaining gaps each with its fix and whose call it is, nits and held reversals, and anything the judge could not assess. Reaching the band is not a reason to hide what's left: list it so the user decides whether one more round is worth it.

📖 `references/worked-example.md`: three runs. A storefront scored 12/20 then 16/20, with the conventions that had to be added after round 1 and the judge claims that turned out stale; a user manual taken from 4.5 to 10/10, where fresh judges plateaued and a retained judge converged; and a 12-round design run where the mean of a retained and a fresh judge understated progress.
