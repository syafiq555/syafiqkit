# Extract a shared package

The failure this skill exists to stop is the one that looks like success: a package that compiles, passes, and can never be installed anywhere but the app it came from, because it reaches into that app's tables, models, auth or UI. The boundary has to exist in the first commit; nothing after that is cheaper.

## 1. Decide the cut before the code

Read the source app's task docs and both consumers' architecture essentials first (`read-summary`). Then measure rather than name: inventory the candidate directory, and for every file list what it imports from outside itself — host models, auth, payment adapters, notifications, UI. The package is the subset both consumers need **identically**; everything with a host-shaped counterpart (identity gates, who may act, money, mail, controllers, side effects) stays in each host and reacts to package events. Size the subset in files and lines before promising anything, because the honest number is usually a third of the directory that carries the feature's name.

Three questions settle most cuts: does the host act **on** the package (calls into it — fine) or does the package act on the host (calls out — forbidden; emit an event instead)? Does a package table point at a host row by foreign key (forbidden — use an opaque id plus a type alias, `subject_type/subject_id` with a morph map the host registers)? Does the package need to *know* something about a host record (rent, parties, dates — ask through a contract the host implements and receive a DTO, never the model)?

## 2. Pick the shape by how many packages are coming

One package per repo is right for one package. The moment "and later invoice automation, and a lot of things" is said, prefer the `laravel/framework` shape: **one repo, one installable package, one namespace and one entry point per capability**, each host registering only what it uses — nothing auto-discovered. Composer `vcs` and npm both consume the repo root directly, one version line covers every capability, one token covers every consumer, and no split workflow exists to fail silently. A per-capability split (`splitsh-lite`) stays available on demand; the trigger is a consumer that wants one capability alone, not tidiness.

## 3. Read how each consumer actually installs at deploy

Before choosing hosting, open every consumer's deploy path — CI workflow, Dockerfile, container entrypoint — and find where `composer install` / `npm ci` really runs. It is often inside the container at start, on the server, not in Actions, and that decides where the credential lives (`auth.json` / `.npmrc` at the app root on the box, gitignored; not an environment variable through a file that keeps its quotes). Also check what the container mounts: a package directory beside the mounted app root is invisible at deploy, which alone rules out "in-repo path repository" for separate-repo consumers. 📖 `references/composer.md`, `references/npm.md` for the concrete shapes.

Pin **exact** versions in every consumer. A caret lets one app drift to a version the other never ran, and the whole point of a shared package is that a change is tested on both sides before it ships.

## 4. Prove it resolves in every consumer's world

Consumers rarely share a framework major. Write the package's constraints as the union (`^10|^11|^12`, peer ranges for npm), then resolve a scratch copy against each consumer's shape and run the package suite there — a matrix in the package's CI (Testbench per Laravel major; Node versions for npm) is the durable form. Expect the resolver itself to surprise you: Composer (2.9 and later) refuses to resolve any release carrying an open security advisory, which reads as a package conflict and is not one. Where two consumers pin different majors of a shared transitive dependency, move the lagging consumer first so the package pins one major.

## 5. Move it as a strangler, source app first

Phase 1 is the app that already has the feature: its actions become thin callers of package services, the schema is adopted in place rather than renamed, and the proof is a byte-identical artifact on a fixture — a document hash, a rendered file, a serialized payload. Write that proof **before** any code moves and commit its recorded value, then assert it unchanged after; the fixture is all literals with the clock pinned. Renderers are not byte-stable by themselves — PDF libraries stamp a creation date, a modification date and a random trailer ID on every run, so normalise exactly those fields before hashing, or two identical renders read as drift and the proof is abandoned as flaky. If a skeleton was scaffolded before the port, expect it to disagree with the real shapes (a placeholder DTO a tenth the size of the real one; a migration already polymorphic where the source table carries a plain foreign key): port the real thing and delete the placeholder rather than growing it, and check the package's fresh-install migrations column-for-column against the source app's whole migration history, because the source app never exercises that branch — only the next consumer does. Two things the port itself does not settle: the consumer's exposure, and the transition columns. Keep the host's own thin actions in front of the package's actions and services so controllers, jobs and listeners never import package behaviour, and write the grep that lists the allowed importers into the task doc — a seam change (an action gaining an argument) then costs one file, and the count is what keeps it that way. And a column the package introduces to replace a host foreign key needs a **writer** for every path that creates the row, not only a backfill for the rows that exist: the backfill answers "what about existing rows" and says nothing about the next one, and the first review after the deploy is where the null shows up. Phase 2 is the second consumer, and it is a **migration**, not an install, whenever that app already has its own version of the feature: its rows map into the package's tables, its media and history stay readable, and its own E2E pair gates the switch. The first tag waits for both consumers to be green against the same package commit (📖 the release notes in `references/composer.md`).

## 6. Write it down where the next session reads it

One task doc in the repo that owns the subject, recording the boundary, the hosting choice and the phases as decisions with their rejected alternatives, and one line in each consumer's CLAUDE.md saying shared capabilities are built once in the package.
