# Run it on haiku

Dispatch the work to `haiku` rather than doing it here. The tier is the point, so the work happens in the agent — resist doing it yourself and using the agent as a second opinion.

`model: "haiku"` only applies to `general-purpose`. Passing it to a registered agent (`code-reviewer`, `Explore`) silently overrides that agent's own frontmatter tier, so dispatch `general-purpose` here.

## What to dispatch

Read the request for three things: whether it names a skill, whether it names a target, and whether it wants more than one agent.

A leading `/skill-name` or a bare skill name means the agent's first action is `Skill(skill: "syafiqkit:<name>")` against the target that follows. Anything else is a free-form task — research, a survey, a bulk read — and goes over as itself.

Fan out when the request asks for it ("3 agents", "split this") or when the work is genuinely disjoint: several independent files, several unrelated questions, a survey across separate areas. Partition so no two agents touch the same file, and give each its own slice rather than the whole list. One coherent task on one file stays a single agent — splitting it produces conflicting rewrites of the same bytes. 📖 `../_shared/references/explore-delegation.md` for batching mechanics and the one-message rule that makes parallel actually parallel.

Partitioning also has a depth axis, and it's the one that decides whether the tier holds up: give each agent a single task — one skill against one target — rather than a chain of them. Two skills in one prompt, or one skill across two files, is where haiku starts reporting work it didn't finish, because a later step in the chain overwrites its own account of an earlier one. Two skills over two files is four calls, not one. That costs nothing extra in total work, and it splits at the seam where each self-report stays checkable against a single before/after pair.

How those calls are then ordered is a judgement about contention, not a default either way: agents whose targets don't overlap can go out together in one message, while anything queueing behind a file another agent is still writing has to wait for it. A user asking for sequential work usually means "don't let these collide," so the same-file legs serialize and the disjoint ones can still run at once — worth saying which you did and why, since a request for one task at a time reads as a request for one agent at a time.

## Writing the prompt

**Keep prompts minimal: skill name (if any), target path, and only facts the agent cannot derive.** Everything else either wastes the judgement you dispatched for or actively breaks it.

Three specific traps:

**Over-specification narrows thinking.** A skill that rewrites code lives in the calling session's judgement about structure — should this merge or split, is this duplication or reuse, does this enum earn a type or stay a string. Each choice the prompt names is a choice the agent doesn't get to make, and restating the skill's own logic, pre-writing conclusions, or listing things that "must survive" replaces reasoning with outline-following. The failure is silent: the agent returns a confident report that describes your outline being executed, which is indistinguishable from the skill doing its own thinking. You discover the problem by comparing the result against what the skill was supposed to do, not by rereading the prompt. 📖 `../_shared/references/explore-delegation.md` for why a judgement-skill gets *less* useful the more you specify.

**One line belongs there that looks like a guardrail and isn't: tell it to do the work itself and not re-dispatch.** `general-purpose` carries the full toolset and will spawn a copy of itself running the same skill against the same target — silently undoing your dispatch while returning a report shaped exactly like success. This is not a conclusion you're pre-writing; it's a fact about the tool grant the agent can't derive. 📖 `../_shared/references/agent-may-not-redelegate.md`

**Constraints that forbid what the skill requires are worse than padding.** Partitioning concurrent agents across files naturally invites a line like *edit only this file, don't write to the others* — appropriate for keeping them off each other's bytes. But a skill like `unhobble-instructions` that splits detail into companions requires writing the destination before cutting from the source. A prompt banning new writes leaves only the cut available, which lands as a leaner file pointing at a companion that doesn't exist. Name the files that are contested rather than prohibiting writes in general — *don't touch these specific paths*, not *create nothing*. **Tell: you are about to blame an agent for a rule your own prompt made impossible to follow.**

**Measure conventions before you mandate them.** A project's style read off two files becomes "this format" in the next sentence; a wrong one hands the agent a mandate to convert already-correct files. The risk inverts here: an over-specified prompt wastes your dispatch, while a *misspecified* one actively directs the agent to break things it would otherwise leave alone. Loop through the actual target set before it goes in a prompt, or where the tree turns out inconsistent, say so and let the skill judge each file. **Tell: you are about to tell an agent what this project's convention is without having counted.**

Against a truly clean tree there are no such facts, and the prompt collapses to skill name and path. That brevity will feel negligent — the instinct to fill the gap is real — but what fills it is rarely a guardrail. It's usually a reporting format, a note on which part of a predecessor's attempt was good, or a list to avoid, and each is a conclusion the agent then works to fill rather than a fact it lacked.

A free-form judgement task with no named skill has no criteria to inherit — "audit what's not needed", "clean this up", "what's missing" all leave the bar unstated. That supplied bar is a real design decision, and a plausible-sounding one can diverge from what you actually meant. Where the request names a recognizable shape a skill owns (overconstraint, staleness, duplication), route there instead — the criteria live in that skill. Where it doesn't, say what bar you're using before dispatch, so a wrong guess costs a sentence not a full cycle.

## Before dispatch, if files will change

For any task that writes files, establish a snapshot baseline before work begins. This is what makes verification possible; without it you're left with the agent's own report.

**First, read the targets' diff.** Uncommitted edits already present — another session's work or your own forgotten edit — will be frozen into your baseline as if they were the committed state, and every downstream check then measures the agent against them rather than against the file the user thinks they have. A snapshot that includes pre-existing work verifies perfectly while answering the wrong question, so a report describing that work as the agent's output clears verification while preserving the mistake. Classify by diff content, not by status plane (`../_shared/references/diff-ownership.md`). Where a target carries work that isn't yours, that's a non-derivable fact belonging in the prompt as a named contested path, or the dispatch waits until the tree settles. **Tell: you are about to snapshot a file you have not diffed.**

**Then snapshot every target the agent may write** (`cp` to the session scratchpad) and record `wc -lc`. A read-only research task needs no snapshot.

## After dispatch

**Wait for the completion notification — don't shadow the agent while running.** Re-reading or re-grepping target files inline pays for the same facts twice and slows down the report that lands later anyway. 📖 `../_shared/references/explore-delegation.md` ("The Waiting Game") for why a read mid-pass is a torn page and how `wc -c`-twice confirms it stopped.

## Verification

The agent's report is a claim about the work, not evidence of it. **The parts that read most decisively are not the parts most likely to be true.** Measured across three actual runs, each returned a confident summary and each had something wrong — including one whose headline claim (a section renamed, a table restructured) had simply not happened. A report volunteering a *preservation* claim ("preserved all references to X", often under its own Verification heading) costs the agent nothing to write whether it's true, and one such claim sat above a diff dropping 9 of 23 pointers.

For a task that wrote files, verification has two phases:

**Phase 1: Did the file change at all?** Run the cheap check: did bytes actually move (📖 `../_shared/references/verifying-a-write-landed.md`). An agent that wrote nothing is the common failure and costs one command to catch. Re-measure the report's own numbers rather than trusting them — they are frequently wrong in ways that flatter the run, and re-counting is the cheapest verification step. A report that contradicts itself (claims lines cut but bytes up, or anchors fixed when new ones were added) has done arithmetic it never took, which tells you nothing about the edit until you measure for yourself.

**Phase 2: Did meaning survive?** Read the file whole, from the top, as its reader meets it — not the diff, not the passages the report names. A report describing a rewrite steers you to exactly the places it feels good about. Counting anything at this stage (surviving identifiers, anchors, rows, bytes) measures shape while the defects that matter live in meaning. This is the only real check; everything below explains why the others fail.

**Shape-measuring instruments fail silently in opposite directions.** A byte-count drop by 7.6KB while the report claims bytes rose is obviously wrong, and that direction prompts you to look. The opposite direction is dangerous because it returns a clean bill: a term-presence sweep (grepping your domain vocabulary and finding every term still there) measures that words survived, never that the sentences around them still say what they said. A rewrite keeping `net`, `gross` and every deduction label while inverting the arithmetic they sit in passes the sweep completely — every term is present, nothing was dropped. But the fact is inverted. A missing-term count at least prompts investigation; an all-present count invites you to stop.

For rules stated in the file (formulas, precedence orders, comparison directions, guards a system depends on), read the specific claim against the original and re-derive it, don't confirm it by the presence of its nouns. 📖 `../_shared/references/two-tier-condense.md` for the value-shaped case where a command or error string must survive verbatim (a genuine lookup), and for the redistribution case where a skill moving detail into its owning sibling file makes a correct pass read as mass deletion — when detail moves, size drops even though nothing was lost.

Read the changed passages against the originals as prose. This is the only check catching the defects that matter: a fact restated into falsehood, an identifier confidently replaced with a plausible wrong one, a claim the source never made. These survive structural checks — the shape is fine, the content is wrong — and they ship broken guidance.

**When the pass claims to have MOVED content, verify the destination exists.** Open the destination file and look for the content there. A relative pointer resolves against the reader's cwd, so checking from repo root while the file sits a level down reports every companion missing and invites you to "fix" paths that were correct. Two failures look identical from the source side: the destination was never written, or it was written where nothing resolves to (a sibling `.claude-companions/` one level up is the common shape). Both leave a file reading as clean extraction with its facts gone.

Once a passage is confirmed genuinely gone (not reworded, not relocated — actually absent), that answers "did this disappear," not "should it have." Don't judge that from whether the passage looks rigid or judgement-shaped — a `**Tell:**` or a mechanical callout can name a checkable, non-derivable fact (an exact command, a specific gotcha) that happens to be dressed as a rule. If the target skill states its own test for what survives (a fact-vs-constraint distinction, an "earn its place" check), apply that test to the dropped passage directly. A live case: a dropped `**Tell:**` initially read as correct trimming, then failed the target skill's own bar and turned out to be a genuine loss.

**A passage surviving unchanged doesn't clear — faithful carry-over answers "did the rewrite distort this," not "was this true beforehand."** A structural skill (like `unhobble-instructions`) preserves stale facts as well as current ones because preservation is what it optimizes for. A gotcha moved verbatim into a companion, stale claim intact, passes every structural check. Where the target is the kind of file whose facts age (branch names, dates, counts, status), do a second independent read: does this claim hold right now, not just does it match before. This is a spot-check on what looks time-sensitive, not full re-verification — most files aren't dated.

For research, the equivalent check is provenance. A finding with no file:line source is the agent reasoning toward an answer. But citations verify FACTS, not MECHANISM — a causal claim can cite real evidence throughout while the wiring between facts is invented. A report citing every fact correctly while inverting the mechanism between them is a failure only independent verification catches. The tell: a report whose every citation resolves and whose conclusion you haven't independently verified.

**Deciding whether to revert or patch.** When the damage is systemic (whole sections gone, a claimed companion never written, numbers contradicting the report's own claims), the run is untrustworthy throughout and reverting before re-dispatch is cheaper than clause-by-clause audit. When the rest of the file checks out and the gap is one contained passage, patch it back in from the snapshot rather than discarding a mostly-good rewrite. Getting this backwards destroys work: an uncommitted rewrite reverted on a byte delta is gone, while the losses it was reverted for are one edit each to patch back. **Tell: you are about to revert on evidence you could have resolved by opening the file.**

**"Systemic" is a verdict you reach after the full read above, never a shortcut past it.** Every symptom qualifying a run as systemically damaged surfaces on its own (a dead pointer, a missing section, a byte count contradiction), so this branch reads as pre-authorised the moment one turns up, and the read starts to feel like a formality. Those symptoms establish that something is wrong, never that the rest is worthless. Only the read separates a good rewrite with one dead pointer from a genuinely untrustworthy pass. Reverting is irreversible, which is exactly why it needs the expensive evidence. **Tell: you can name what the agent deleted but not what it wrote.**

**If the user says they've read the output, verification is done.** Verification exists to tell them whether to trust the result; continuing to audit after they've looked themselves spends their tokens re-answering a question they answered. The failure mode is narrowing an unscoped "it's fine" to whichever file was under discussion and carrying on elsewhere. Where you have a real defect in hand (a dead pointer, a known-wrong fact), state it in one line and leave it with them rather than acting on it. **Tell: you are still verifying after being told the work is good.**

Report what changed and what you verified, and say plainly when a check failed or you skipped one. When the dispatch ran a named skill, say so by name and state that skill's job in one line before reporting its results — "this ran via `unhobble-instructions`, which rewrites a file to convert rigid rules into judgement prose" — rather than presenting the outcome as haiku's own. Two skills are in play (this one dispatches and verifies; the named skill decides what the rewrite should look like), and a verdict about the result belongs to whichever skill's own rules actually govern it — check the target skill's stated criteria before asserting a passage should or shouldn't have survived, not this skill's.
