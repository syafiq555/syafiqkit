# Verification Gotchas

The agent's report is a claim about the work, not evidence of it. These gotchas are where confident claims fall apart — measure every one.

## Shape-measuring instruments fail silently

A byte-count drop contradicts the report's claim of growth — obviously wrong, and you look. The opposite direction is dangerous: a term-survival sweep (grepping for domain vocabulary) measures that words survived, never that their sentences mean the same thing. A rewrite keeping `net`, `gross` and every label while inverting the arithmetic passes completely — every term is present, nothing was dropped, but the fact is inverted. When the dispatch was a rewrite pass specifically (`unhobble-instructions`), `../../unhobble-instructions/references/verifying.md` covers this failure in more depth — delegation risk, rewording-vs-deletion, and the markup damage that survives every content check.

For rules stated in the file (formulas, precedence, comparison directions, guards), re-derive the specific claim against the original. Don't confirm by the presence of its nouns. 📖 `../../_shared/references/two-tier-condense.md` for value-shaped content (commands, error strings) that must survive verbatim, and for the redistribution case where detail moving to an owning sibling makes a correct pass read as mass deletion — size drops even though nothing was lost.

**A zero-hit search is a claim about your pattern before it is a claim about the file**, and it arrives already shaped like a finding — "this fact is gone" is the most alarming thing verification can produce, so it gets reported with the least scrutiny. The pattern is where it usually breaks: an alternation written `\|` under `grep -E` is a literal pipe matching nothing, a `-F` pattern containing regex metacharacters, an unquoted backtick the shell ate before grep saw it, a term the rewrite legitimately reworded. Every one returns clean and looks identical to real deletion. Before reporting anything absent, run the same pattern against the ORIGINAL — a search that can't find the fact where you know it exists is measuring itself, not the rewrite. 📖 `../../_shared/references/explore-delegation.md` → "Verifying Agent Counts" for the control-query form this generalises to. **Tell: you are about to report content missing on the strength of a search returning nothing.**

**A dropped-anchor count from `unhobble-instructions` is the same trap at the structural level, and it's worse because the skill's whole job legitimizes the drop.** That skill folds several named rules into one unnamed paragraph on purpose, so a before/after `{#anchor}` diff on its own output will show dozens gone on a totally clean run — the count alone can't distinguish "merged into surviving prose" from "deleted." Following the count with a keyword grep for the ORIGINAL rule's exact wording compounds the error rather than correcting it: a legitimately reworded sentence returns the same zero-hit a real deletion would, so two instruments that each individually warn about false positives stack into a confident, wrong "this is gone" when read only for their yes/no answer. The only check that actually distinguishes them is reading the current file's relevant section in full, prose and all, and asking whether the specific claim the anchor named is still assertable from it — not whether its old sentence appears verbatim. Do this before proposing any revert; a revert decision made on anchor-count alone is a decision made on the shape-measuring instrument the rest of this file already warns against.

## A pointer existing doesn't prove its destination holds the content

Three ways this fails:

**The destination was never written.** A relative pointer resolves against the reader's cwd, so checking from repo root while the file sits a level down reports every companion missing. Two failure modes look identical: either the destination was never written, or it was written where nothing resolves to (a sibling `.claude-companions/` one level up is common). Both leave the source reading as clean extraction with its facts gone. Open the destination and look for the content there.

**The destination already existed.** The pass deleted a section and cited a destination holding unrelated content, so there is no new file to be missing and every pointer resolves — "every pointer resolves" answers "does the link work," not "does it hold the facts." Grep the deleted passage's identifiers against the destination and expect partial hits from general vocabulary while specific mechanisms are absent. A report claiming content already lived elsewhere is the cheapest claim to make and the one to test first.

**Stale content moved untouched.** A structural skill preserves outdated facts as well as current ones because preservation is what it optimizes for. A gotcha moved verbatim into a companion, stale claim intact, passes every structural check. Spot-check time-sensitive claims (branch names, dates, counts, status) against the live codebase, not against the original file alone. This is not full re-verification — most files aren't dated — but content that ages needs a second independent read.

**When the dispatched skill MOVED content out of a file rather than only rewriting it, read 📖 `../../_shared/references/verifying-a-relocation.md` before reporting the pass clean.** Both phases of the verification above read the rewritten file, and a relocation's defects are outside it — a link whose `../` depth no longer resolves, a documented glob that still matches after it stopped covering, or a destination file nothing in the project cites. Reading the file whole is the strongest check this skill has and it cannot see any of these.

## The agent's own numbers are frequently wrong

A report that contradicts itself (claims lines cut but bytes up, anchors fixed when new ones added) has done arithmetic it never took. Re-measure. A report volunteering a *preservation* claim ("preserved all references to X") costs nothing to write whether true — re-count what actually survived.

A condense report naming **where the deleted bytes went** is the same shape and now the cheapest of them all, since `condense-task-doc` requires the claim before it may report success — so every run produces one, and "the `decisions/*.md` siblings absorbed it" is as easy to write when nothing moved as when it did. Re-run `wc -c` on whichever file the report says grew. A set whose members all shrank had no destination, whatever the report names; that is the shape a consumer caught only by diffing against git after ~40 gotcha rows were already gone.

**Reports also under-claim, and that direction costs more to get wrong.** The framing above is about agents overstating, so a report that omits work reads as honest by comparison — but an agent that silently did *more* than it described is a real failure mode, not a safe one. One run updated three `CLAUDE.md` prose passages and reported only the link rewrites; the near-miss was re-doing work already done, against a file whose state nobody had checked. Verify before *repairing* what a report says is missing, on the same evidence you would demand for what it claims to have done: diff the target against the snapshot baseline. A report's silence about a file is not evidence the file is untouched.

## Deciding whether to revert or patch

When damage is systemic (whole sections gone, a claimed companion never written, numbers contradicting the report), the run is untrustworthy throughout and reverting before re-dispatch is cheaper than clause-by-clause audit. When the rest of the file checks out and the gap is one contained passage, patch it back from the snapshot rather than discarding a mostly-good rewrite.

⚠️ **The count of defects is not what decides this — whether they ENUMERATE is.** A long list of losses reads as systemic because it is long, and that is the wrong axis: a run whose every defect you can name, locate and restore is by definition contained, however many there are, while a run you cannot characterise is systemic at one defect. So ask what would go into the re-dispatch prompt. If the answer is a specific list of facts to preserve, you are holding the patch instructions already, and reverting throws away the good structure to re-earn it from a non-deterministic pass that can fail differently. Weigh what a revert DISCARDS, not only what the run got wrong: a rewrite that fixed the section ordering and halved the byte count has delivered something a patch keeps and a revert spends another dispatch to maybe get back. **Tell: you can list every fact you would name in the re-dispatch prompt — that list is the patch, so patch.**

The pull toward reverting is that it feels like the rigorous choice, since finding real loss and then keeping the file reads as conceding. It isn't: the verification's job is deciding what the artifact needs, not grading the run. Two distinct failures follow from getting this backwards — recommending a revert the evidence doesn't warrant, and the subtler one of framing patch-vs-revert as balanced when the enumeration test already settles it. If the user has to ask why you want to revert, the recommendation was the error, not the explanation.

**Snapshot the agent's OUTPUT before reverting, not just the pre-dispatch baseline.** The pre-dispatch `cp` preserves what the file was; a revert then overwrites what the agent made, and that copy exists nowhere else. The verdict becomes unfalsifiable at the moment it's acted on — asked afterwards to show the loss, you have the original, the report's summary, and nothing to diff. Worse, you can no longer check your own verdict: if the finding rested on a screen rather than a read, the artifact that would expose that is the one the revert destroyed. `cp` the rewritten files to a second scratchpad path first; it costs one command and is the difference between a reviewable call and one the user has to take on trust. **Tell: you are about to overwrite the only copy of the thing your finding is about.**

**A second run of the identical prompt is the cheapest control, and it can exonerate the first.** These passes are non-deterministic, so re-dispatching unchanged produces a different rewrite of the same source — and comparing the two tells you whether a finding is about THIS run or about the metric you screened with. A metric that scores the run you have now read and judged sound WORSE than the run you condemned has just invalidated itself, and with it the verdict it produced. Reach for this when a count is the only thing standing behind a revert: it converts an unfalsifiable claim into a testable one for the price of one dispatch.

**Patching back means restoring the FACT, not the bytes** — and the snapshot holds those bytes in the shape the pass existed to change. Pasting a passage verbatim out of it undoes the dispatch locally while reading as careful repair, because the text is provably the original and provably missing. This bites hardest where the skill was a rewrite pass: a `❌ NEVER / ✅ ALWAYS` table restored intact into a file `unhobble-instructions` just converted to prose puts back the exact shape the run removed, and the restoration is *more* confident than the rewrite because it can cite the source. Separate the two before writing: what does this passage tell a reader that nothing else in the file does, and what form does the rewritten file state things in? Carry the first across in the second. A fact a model cannot derive (a real identifier, an exact error string, a measured number) has to survive somewhere; the enforcement scaffolding it arrived wrapped in usually does not. **Tell: you are pasting from the snapshot into a file whose whole point was to not look like the snapshot.**

⚠️ **A snapshot preserves what the file CLAIMED, never what is true — so a "restored" fact needs checking against the system, not against the baseline.** The whole verification frame points at loss, which makes every absent value read as damage and puts the burden on the rewrite; a value the pass dropped because it had gone stale is indistinguishable from one it dropped carelessly, and confirming it "came back" is a diff against the very artifact whose accuracy was never in question. That reverses the usual direction of doc-vs-reality (📖 `../../read-summary/references/doc-authority.md`): here the pass was the correction and the repair undoes it, which is why it survives a careful patch — the restoration cites a source and reports success. Measured: a rewrite correctly dropped a stale runtime version, the patch put it back from the baseline, and the project's own instructions had recorded the real value weeks earlier. Anything the world can change — a version, a count, a hostname, a live flag, an expiry — gets re-measured at its source before it goes back, and where the measurement is out of reach, say what you restored unverified. **Tell: your evidence that a restored fact is right is that the snapshot says so.**

**"Systemic" is a verdict you reach after the full read, never a shortcut past it.** Every symptom (a dead pointer, missing section, byte contradiction) surfaces on its own, so this branch reads as pre-authorised the moment one turns up. Those symptoms establish that something is wrong, never that the rest is worthless. Only the full read separates a good rewrite with one bad pointer from a genuinely untrustworthy pass. Reverting is irreversible. **Tell: you can name what the agent deleted but not what it wrote.**

**The word "revert" reaching the user is the checkpoint, not the read that preceded it.** A count-based screen (anchor diff, identifier sweep) can feel exhaustive enough to act on, especially stacked with a second screen that agrees — two zero-hits from two different instruments still isn't a read, and "I checked twice" is not the same claim as "I read the current file and the fact doesn't hold." Before saying "revert" — even as a recommendation, even hedged — confirm you can state, for each specific claim you're calling lost, the sentence in the CURRENT file you checked it against and why that sentence doesn't cover it. If the honest answer is "I haven't opened that section of the new file yet," the recommendation isn't ready, no matter how many counts back it. **Tell: you are about to write or say the word "revert" and the last thing you did was run a grep, not a Read.**

## If the user says they've read it, verification is done

Verification exists to tell them whether to trust the result; auditing after they've looked themselves re-answers a question they answered. If you have a real defect in hand (a dead pointer, a known-wrong fact), state it in one line and leave it with them rather than acting on it. **Tell: you are still verifying after being told the work is good.**
