# Apply Design Judgement

Five failures recur: inconsistent UI (surface-by-surface, unaware of what the app already has); generic UI (stock defaults unchecked); shallow UI (happy path only); desktop-first UI (one width designed, not all); crowded UI (every brief item answered instead of the one a reader came for). None shows in a diff.

## Look at the Picture

Images with positional references ("this one", "the second") need the target surface resolved and stated before work starts: the pointer attaches to whatever you worked on last, and a full pass on the wrong screen looks like completed work. 📖 `../design-handoff/references/handoff-incident-patterns.md` for a worked case.

Read a screenshot as a rendered interface *separately* from the question that came with it: even an API or bug question hides overflow, collision, misalignment, truncation or contrast defects. Answer what was asked, then note what else you saw and offer the fix; do not silently fix the layout. That holds for a question about something else (an API, a bug). A complaint about the screen itself ("why is it aligned like this", "looks messy") is a design pass: fix it (next section).

## A design pass ends in a better screen, shown

**Unless the ask is a critique ("what's wrong", "audit", "review it" with no edits), the deliverable is changed screens, not findings.** "Use the design skills", "polish", "improve the UI/UX" or a screenshot with a complaint all mean: find what is wrong, fix it in the same pass, re-measure, and show the result. Only a finding that changes who can do or see something, wording a customer is promised, or a direction the user has not picked goes back as a question (the 15/11/2026 incident: 📖 `references/design-incidents.md`). **Tell: your reply lists findings and the diff has no frontend file.**

**A redesign, a revamp or a "not nice" goes to the deal rule first** (§ Scope and Blast Radius: two or three dealt directions, rendered, each given the `impeccable` critique, then the user picks); steps 3 to 6 then run on the chosen direction, never on today's look. The critique runs as commands on each rendered direction, before any is offered: `../impeccable/scripts/impeccable detect --json <direction URL> --viewport 390x844` (a served URL or `file://` path, since `--viewport` applies only to URL scans) and again at `1280x800`, then `Read` `../impeccable/reference/critique-rubric.md` and score each direction against it; each option carries its score and top finding (📖 `references/direction-approval.md`). **Tell: you are offering directions and no `impeccable detect` ran on them.**

The pass, in order. Paths are relative to this skill's folder (`${CLAUDE_SKILL_DIR}`), and sibling skills sit beside it (`${CLAUDE_SKILL_DIR}/../impeccable`, `${CLAUDE_SKILL_DIR}/../taste`); never resolve them against the project. The scripts need Node 22+ and Chrome, Edge or Playwright's Chromium (`CHROME_PATH` overrides); without them, say so in the reply, read screenshots instead and label the pass unmeasured.
0. **Find the page.** Measuring needs a URL a browser can open: the project's served URL (its `CLAUDE.md`, a `Run locally:` line, `.env` `APP_URL`, a Herd `*.test` host), started if it isn't running. A signed-in screen needs a saved login (`--storage-state`): make one per account with `LOGIN_PASSWORD=… node scripts/save-login.mjs --url <login page> --email <login> --out <file>` right before each batch (or take it from the project's e2e setup); check-render exits 2 on a sign-in page. `impeccable detect` takes no saved login: behind one it reads the page through `--cdp` from a Chromium signed in with that file (steps: `../impeccable/reference/critique.md` § Assessment B, the paragraph ending "close that browser afterwards"), since a source-file scan runs regex rules only. Record `Run locally:` and `Signed-in state:` lines in the frontend `CLAUDE.md`, beside `Token lint:`, so the next session doesn't rediscover them. An email or static page renders from its `.html` file. With no openable page, write "check-render: not run: <reason>", never skip silently.
1. **Probe** an existing app with `scripts/probe-design-system.mjs` (§ When reading an existing app's language), even when you have already read its token file: the probe also reports where raw values crept in and whether a token lint exists. Capture the before state with `scripts/check-render.mjs --out <dir>`.
2. **Find**: your own read plus the other design skills' detectors, run as commands on the before page (`../impeccable/scripts/impeccable detect <page>`, and `taste`'s review path: inside an app that is this skill's own `app-kit/scripts/inspect.mjs --app <page>` and `app-kit/scripts/lint.mjs --app <changed source files or folders>` (they live under `uiux`, not `../taste`; lint reads source, so a URL returns "Not found"), on a public page `../taste/scripts/consistency.mjs <page> --profile <temp dir> --quick` and `../taste/scripts/copy-lint.mjs` on a public page). When the user said "design skills" (or "use all"), also run `impeccable`'s critique in the same pass, as commands like the rest of this step: its `detect` output above plus `Read` `../impeccable/reference/critique-rubric.md`, scored against the before page (§ First decide which job this is). Offering these passes afterwards, when the user already asked for them, is the defect ("say if you want those passes too", headless test, 22/11/2026).
3. **Fix** everything that needs no question, reusing the atoms the probe listed.
4. **Measure** with `node scripts/check-render.mjs <url>` on every changed screen after the last edit (`--storage-state <file>` behind a login; check the final URL is not the login page). Fix every FAIL and WARN or name it as an exemption with its reason: card-in-card, truncated text and uneven cards are WARNs and exactly what the user complains about. **Tell: you are about to call a screen done and check-render has not run since your last edit to it.** What it measures: § Verify by Looking. A change to a shared header or nav also runs `--widths 1024,1366`: a desktop menu runs out of room at laptop widths, which the defaults (320 to 1280) and `taste`'s gate (1440, 390) both skip, and every language's labels get their own run since a longer one collides first (25/11/2026: a shop menu overlapped its header button at 1024 to 1439 px in English while every default check passed). A screen people operate (ticks, steppers, toggles, a drawer, a search box or a dropdown typed into) also gets `node scripts/record-clickthrough.mjs <url> --steps steps.json` at a phone and a desktop width, and you read its frame sheets for a control that greys, a label that flashes or a card that jumps after a click, which no still capture shows (scripts/README.md for the steps format).
5. **Look**: open (`Read`) the after captures yourself at phone and desktop width, plus the `-blur8` capture (the main element and the groups should still separate when blurred, NN/g's squint test); the script cannot judge hierarchy or crowding, and in 39% of measured UI sessions nobody looked at the last edit at all. **Tell: you are about to show captures you have not opened.**
6. **Show** four pictures through the image gallery tool (`show_image` in syafiqkit) where it exists, otherwise as the four file paths in the reply: before and after at 375 and at 1280 (check-render's `w375-…-top` and `w1280-…-top` captures), and say what changed. A desktop-only pair hides the width most users have. **When the user may be following from a phone or another device (Remote Control, the mobile app), send the pictures with `SendUserFile` (`display: render`)**: a path or Markdown image there renders as "Load Image" and asks to open a Mac path as a web link, and the gallery pane is desktop-only (22/11/2026: the user asked twice to see the shots).

## First decide which job this is

**Making a landing page, marketing site or portfolio look better is `taste`'s job whatever the verb (build, redesign, polish, improve, "make it wow"), even when the user named this skill: invoke `taste` rather than designing the page here, and hand over mid-task when a page job turns into a look change.** Stays here: a critique with no edits, research, and a named small fix ("the price is cut off at 375px"). This skill's restraint drifts to the category default on a page; `taste` prevents that with a layout dealt per page kind, licensed stand-in photos and a finish gate in a real browser. A critique of such a page takes 📖 `references/marketing-pages.md`; business tools inherit the app's language. **A shop's own storefront home (a marketplace or grocery home of product rails, deals and grids) is a shop screen, not a marketing page, and stays here**: `taste`'s page rules (one section per screen, the hero alone on the first screen) would strip what makes it a shop. Deal its directions as rendered prototypes from captured live shops, borrowing `taste`'s `photos.mjs` (licensed stand-ins) and `shoot.mjs` (captures).

**A request for every design skill ("use all", "use the design skills", or the user calling a surface's design work "the UI/UX", which means the design skills, not this one alone) runs `uiux`, `impeccable` and `taste` together, whatever the page type**: `taste` then takes its review path, no full run (commands: § A design pass ends in a better screen, step 2), and every finding from it is fixed in the same pass. The routing above names one owner per job, which reads as permission to drop the others (08/11/2026: `taste` was left out of a "use all" pass until the user asked "What about taste skill").

**A go-live check of a website is measured, not designed**: 📖 `references/go-live-check.md` before running any check of a site about to launch or just launched; it holds the checks, the reporting rule and the first one to run.

**Whatever moves or responds to touch belongs to Emil Kowalski's skills, even inside a polish or redesign that never says "animate"**: transitions, press and hover feel, popovers, drawers, toasts, drag and swipe, page-load motion, a mobile web app that feels like a website. Invoke the Emil skill with the motion task as its argument (bare, most of them only greet). 📖 `references/motion-routing.md` for which Emil skill takes which motion task, and the argument to pass it.

Brownfield (an app with a language) and greenfield (nothing to inherit) start from different questions.

**When a design already exists:** A prototype, Figma file, Claude Design project or annotated screenshots means a port: reproduce what is there, and reserve judgement for what the platform forces. Read the design source before asking any layout question. 📖 `references/porting-existing-designs.md` before reading or asking about the design and before briefing any builder: what a port reads first, the screens it never drew, and what the brief carries.

**When reading an existing app's language:** run `node scripts/probe-design-system.mjs <repo root>` first. It lists the token sources, the shared components with how often each is used, the files carrying raw colours, arbitrary values and inline styles, and whether a token lint exists; the brief names the atoms it found that this surface must reuse. Where `tokenLint` is absent, read the frontend `CLAUDE.md` files the probe lists for a `Token lint:` line; with none, show the raw-value counts and ask once, through `AskUserQuestion`, whether to add a build-failing lint rule for raw values (ESLint, stylelint or oxlint, per the stack). Record the answer as `Token lint: added <date>` or `Token lint: declined <date>` so the next session doesn't ask. Then read `frontend/CLAUDE.md` or a similar conventions doc; if none exists, infer the language from sibling pages and shared components. Docs name tokens and rules, but the answer is often a component already built for this job: before writing a treatment, grep for its mechanism (the prop, the component name, the shape). One hit in your own file means you invented a pattern; several elsewhere mean the app already decided. A component reused in a new place brings its old audience: judge reuse by who reads it and what contains it, not by shared fields. Reuse the logic, rebuild the surface when either differs, and say so in the builder's brief (📖 `references/design-incidents.md`, the staff-modal form). A new section must read as its siblings do on that page (same card, label and value pattern), so name the sibling in the brief. Work inside the conventions unless told otherwise; when you break one, say which and why. A brief that pins a direction overrides the app's language. A verdict beyond the visual layer (component library, framework) is a finding with a blast radius, stated before designing and never inside a polish request. 📖 `references/design-language-health.md` for judging each layer.

Design the branch that renders on the active route, not the file that names it: components hold several layouts behind conditionals and flags, so designing from the file redesigns a surface no user sees. 📖 `references/reading-live-branches.md` for how to trace.

**When starting from nothing:** there is no app language to read. Name what you're designing FOR before you design it. 📖 `references/greenfield-minimum-system.md` for the audience, subject and job questions, asked in that order.

Then decide the smallest system that keeps the second screen consistent with the first: one typeface, colour/type/spacing tokens, an 8px base, mobile-first breakpoints, a mature library customised through tokens. 📖 `references/greenfield-minimum-system.md` for where the system is written down and how a screen records a deviation.

**Whichever job it is, write a one-line design read before any code:** audience, subject, job, and how bold or restrained this surface should be. Ask one question only if the read genuinely forks; otherwise state it and proceed within the scope below, never past an approval gate. A critique writes no design read.

## When the user asks for research, or how real products solve it

"Research" in a UI request triggers this section even when the question is about the user's own screen ("research how to make this compact"). Run the dispatch before proposing: measuring the app runs alongside it and never replaces it. A proposal that cites "best practice" and not one URL you opened means the research didn't happen.

**Every research run includes real-world case studies: live products, named, where the same situation occurs, each with a URL you or an agent fetched.** Research about the subject (the client's brand, the user's own app, a competitor's data) is brief input, never the case-study leg, and it feels complete on its own. 📖 `references/design-incidents.md` for the run that stopped there. **Tell: every URL in your research is the subject's own.**

**Every research run also reaches outside the user's own domain, whatever the question (a redesign, a critique, a design-system choice, one control).** Same-domain products show the market's baseline, which the current screen usually already matches; the answer worth having often comes from products renowned for their UX in other domains that face the same page job or decision (Apple, Aesop, Airbnb, Stripe, Linear, Our Place). Keep at least two such products in the list beside the domain's best. Start from `app-kit/library/ux-patterns.json`: renowned-UX pages captured at 390 and 1280 px, each tagged by `mechanisms` (scroll-story, sticky-stage, product-reveal, variant-picker, buy-column, brand-story, founder-note, collection-grid, pricing-compare, feature-tour, onboarding, social-proof) with `steal` moves; filter it by the mechanism your screen needs, then capture fresh, since pages change. Append what a run verifies to it. Measured twice: 22/11/2026 (a grocery redesign) and 25/11/2026 (a shop's page-system decision briefed as "fashion brands" only), both times the user had to ask. **Tell: every product in your brief sells or does what the user's product does.**

Start from the situation and send agents to where it occurs, not to a category of products. Subject research is a third agent, never a substitute. **A report where most cells say "not stated" means the brief aimed at the wrong evidence, not that no precedent exists:** re-brief once at a different source kind before relaying. Open the cited sources yourself before relaying, and report evidence and judgement separately. For a look or layout, capture the live pages yourself (`scripts/capture-references.mjs`): shops and admins built in the browser give a text fetch nothing but a title. 📖 `references/case-study-research.md` for the dispatch (through `syafiqkit:haiku`: live products, libraries, subject research), the cells, and what to check in returns.

**Research is the first half of this skill's job, never all of it.** The build comes many turns later, when the research rules are recalled, not read, and it still needs a design decision and a graded render. **So before briefing UI builders, re-invoke this skill for the build, and again when they return, before calling the screens done.** 📖 `references/design-incidents.md` for the builders that followed a research-only invocation. **Tell: you invoked this skill for research, and your next UI verdict cites no re-invocation.**

A design principle the user supplied (a screenshot, a reel) is a source to read, not research to replace. 📖 `references/case-study-research.md` for how to brief and what comes back.

## When asked to review a screen

"Critique", "audit" or "what's wrong with this" is a judging job, not a fixing job: score it, rank what the reader loses, and hand the findings back before touching anything. 📖 `references/critique-mode.md` for the two isolated reviews and the 0-4 scoring.

## Scope and Blast Radius

Scope by blast radius, not phrasing: "polish this section" touches existing surfaces, while "redesign this page" reworks structure.

Single-element fixes build directly; section polishes (card layout, forms) propose inline and code. A control the app does not have yet (a picker, a suggestion pattern, a new input behaviour) is a question other products have answered: run the research dispatch above before its options reach the user, even unprompted (📖 `references/design-incidents.md`). **Tell: every option you are about to offer cites only the app's own components.** Page redesigns and module-wide passes survey first (language, audience, subject, job), capture the before-state, then propose and wait for approval. **A new look (palette, type, layout language) is dealt by a script, never chosen from memory: `app-kit/scripts/draw.mjs --app` for screens inside an app (how to read its sheet: `app-kit/references/app-screens.md`), `taste`'s own deal for a public page. A deal that returns the style the app already uses is redealt (`draw.mjs` with another `--kind`), since today's look shown as an option offers no change. It is shown as two or three real screens beside today's, for the user to pick or reject; a score, a tiebreak or "closest to current" never picks it.** A user who calls a product "not nice" expects a revamp they can see; a direction chosen by rule lands as the old look tidied (19/11/2026: a tiebreak picked the variant nearest the current look, three rounds of tokens and atoms followed, and the user saw "little visual change": "not polish"). **Tell: your plan names the winning direction before the user has seen any of them rendered.** Before a new flow or page direction goes for approval, run both reviewers and fold their fixes in or put the open findings beside the question (📖 `references/direction-approval.md` for what each reviewer covers, the commands, and how the direction is put to the user).

**Prefer a rendering tool to a text mockup:** Claude Design's tools (`mcp__claude-design__*`), artifacts or a dev-server page show type, weight, spacing and colour; box-drawing shows none of it, and the ASCII fallback happens silently. Use one where stakes are highest (page redesign, new visual direction, brand or palette), usually one `ToolSearch` away. Reserve text mockups for layout order and hierarchy.

## Verify by Looking

**On a redesign, capture the before state**, both states side by side. Single-element fixes need no baseline; section polishes usually do; page redesigns always do.

A UI change is verified by looking, not by the diff: spacing right at one viewport breaks at another, and a three-item card layout wraps differently with twelve. The rendering carries meaning the source never does.

`scripts/check-render.mjs` (the pass, step 4) captures 320, 375, 768 and 1280 px in each colour scheme and measures what a model reading a screenshot keeps missing and the user then finds by eye: text too faint for its real background, clipped or truncated text, overlaps, tap targets under 44px, clickable things without a pointer cursor, cards in one row with uneven heights or edges, card inside card, sideways scroll, em dashes. Captures go to a temp folder unless `--out` names one. It does not judge hierarchy, crowding or whether the screen reads well: that is still your grade, by opening the captures.

Reproduce only what you can fully read. Where the real page won't fit (too many files, an unlocated component, an unresolved branch), the gap fills from the design system as a plausible page that looks faithful and isn't. Writing "likely", "probably" or "presumably" about a layout means you are in that case: name the unreadable part and what it leaves unverified.

Verify the render came from your source. 📖 `references/verification-traps.md` before trusting a capture: a stale bundle, a fixed or sticky element, or a phone bottom bar each looks like a design defect.

**A builder's screenshots are a set to grade, not a sample to spot-check.** Open every one before calling the screens done, and grade them on a fresh invocation of this skill, not the research invocation whose rules are recalled by then. The skipped shots are usually the reused or secondary surfaces, where the defects sit. Add what a static capture misses (📖 `references/verification-checklist.md`), and grade each against its siblings (§ Grading a builder's set there). When the user calls a screen unpolished, check its structure before its copy: a component in the wrong context needs replacing, and string patches waste a round. **Tell: your verdict cites fewer screenshots than the builder produced.** `done` runs this grade as its Design row at wrap-up, alongside `impeccable` `critique`, for any diff that changes something a person sees.

Ask for screenshots after proposals; the first render is a second approval gate. 📖 `references/verification-checklist.md` § Flows and recordings before running a browser flow. A cut-off edge at the viewport is a boundary, not a layout bug.

Verification scales with blast radius: a single-element fix checks the widths where it can break (usually phone and the desktop it sits in); a page redesign checks 375px, 768px, 1280px, plus a short height (375×667, 1366×650) wherever a stage is pinned or sized to the screen, with hover, focus, disabled, loading, contrast, motion and layout-shift. Look in one batched round, confirm fixes in one more, and go further only for a named defect. The before capture and the approval render are not rounds. 📖 `references/verification-checklist.md` § Parallel builders and specs for when builders share a round, and for thresholds.

## The Tension

Matching the app fights being distinctive. Unchecked, "match existing conventions" inherits templated defaults, and "be distinctive" produces a page that matches nothing. **Spend distinctiveness where the surface's actual *job* calls for it; keep everything else consistent.** Core workflow pages can stand out; sidebars, modals and settings inherit. A brief that pins a direction (brand refresh, new component system) makes consistency win.

Without neighbours to anchor against, distinctiveness is a question: was this shaped by its audience, subject and job, or did it default? Choices collapse into stock looks when nothing drives them, and each bundles an unexamined assumption: when you recognize one, ask what your audience, subject and job would choose instead. 📖 `references/ai-look-tells.md` names the six stock looks (`#stock-looks`) and the concrete giveaways (edge-stripe cards, gradient text, a label above every heading), each with the question it should prompt. (Adapted from `frontend-design` skill, Apache-2.0, and `superdesign` skill, MIT.) **A screen called boring, plain, flat, busy or default, or one that "doesn't stand out" or has "no focal point", gets the move for that complaint**: break the layout, exaggerate the scale, add detail from the subject, one odd element, one tap colour, or three planes, each with the screens it would harm. Read 📖 `references/composition-moves.md` before choosing; a vague "meh" is diagnosed from the blur captures first, since each move fixes a different failure.

A one-word theme ("industrial", "brutalist", "retro") names a direction, not a costume to assemble. Spend it on one element, keep everything around it quiet, and cut what exists only because of the theme word. A brief's "no need to follow the existing palette" removes a constraint; it does not make the theme the goal.

Five questions test whether something was shaped or defaulted: **Swap** the typeface or layout with a default one, would anyone notice? **Squint**: does hierarchy survive? **Signature**: point to the element carrying this product's character. **Token**: do the variable names belong to this world or any project? **Exclude**: name an audience this direction would be wrong for; a look that suits everyone was chosen by nobody.

Where a surface has a logo slot and the product has a real logo, the real logo goes there. Where none exists, leave the space empty or set the product name as text, and say the logo is missing: that is a question for whoever owns the brand. Any stand-in mark (initials, an emoji, an icon-set glyph, an invented SVG) reads as a finished decision and ships silently. 📖 `references/design-incidents.md` for the measured cases behind the theme, crowded-page, control-placement and logo rules.

## Mobile-first is the default, not a viewport check

Design at 375px first and let columns arrive with width: that order locks in what a later "check it on mobile" pass cannot undo. A surface that works only with a pointer and a wide screen was not designed for most of its users. 📖 `references/mobile-first.md` for the default checklist (thumb reach, targets, bottom tabs, text size, phone tables) and WCAG target-size floors.

## Design for people who scan

People look for one thing and act. Scan headings, read chunks when earned: chunk under descriptive headings, front-load labels, name button outcomes. One bold action per screen (the first two seconds); rare actions in a menu; defaults instead of questions; errors say what happened, why and what's next; empty states say what would appear and how to create it. Only home, search and print work unlabelled. 📖 `references/designing-for-scanners.md` for patterns and progressive-disclosure traps.

**A gap-list brief produces a crowded page.** "Can't find property, tenant, grouped meaning, ungroup route, relations" reads as items to cover, so each gap gets its own element; each is defensible, and together they bury the one figure the reader came for. Apply hierarchy to the list itself; a reader in a hurry is the audience, not completeness.

**A control belongs in the same container as what it changes.** A row, tab or switch that re-renders a card elsewhere reads as two separate things, and a chevron or chip on that distant control labels the separation without fixing it. Open the detail inside the thing clicked (accordion row, expanding card), or put selector and detail in one card. A fix that adds a label rather than moving the content is the wrong fix. 📖 `references/design-incidents.md`.

## The States Beyond the Happy Path

A populated, working interface is what gets reviewed; shallow UI breaks silently in loading, zero-row, one-row, error, disabled and text-overflow states. Build for those too.

**Loading**: stale content feels broken rather than pending, and users can't tell fetching from a hang. Show a pending state in its place (skeleton, spinner or gray), at the final size (📖 `references/design-incidents.md`, the stale slider).

**Empty states invite action; errors explain and show the path forward.** "No activity yet" names the absence, not what the state means or how to change it.

**Lazy-loading is design, not just performance.** Defer what users hunt for; keep resident what tells them what the screen is and what to do. Deferred content still needs a loading state and a placeholder at its final size. 📖 `references/designing-for-scanners.md`.

**A populated interface needs the same question.** Accurate figures with nowhere to go answer "what is true", never "what do I do". Ask what the reader does next with each figure and give them a way to act. Where there's no honest next step, state the meaning rather than invent a destination: a drill-down built on an API-unsupported filter reads helpful but goes nowhere.
