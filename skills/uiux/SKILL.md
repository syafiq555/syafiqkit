# Apply Design Judgement

Five things go wrong: inconsistent UI (working surface-by-surface without knowing what the app already has); generic UI (stock defaults unchecked); shallow UI (only the happy path); desktop-first UI (designing at one width, not across all of them); crowded UI (answering every item in the brief instead of serving the one readers came for). All are invisible from a diff, which is why UI changes are verified by looking at them.

## First decide which job this is

Brownfield (an app with a language) and greenfield (nothing to inherit) start from different questions, and a skill that asks the brownfield question of a greenfield brief stalls on reading a language that doesn't exist.

**When an existing app provides the language:** infer the app's existing design language: spacing scale, type scale, colour usage, component patterns, border/shadow/radius treatment, interaction conventions. Look for a `frontend/CLAUDE.md` or similar conventions document — if one exists, read it for the app's established rules and component library. If not, infer the language from sibling pages and shared components. The point is not to copy the lowest-common-denominator treatment reflexively; it's to know what you're departing from and whether you're doing it deliberately.

Work inside those conventions unless explicitly asked otherwise. When you propose to break them, say which convention and why the change needs to break it. A brief that pins a direction (brand refresh, new interaction model) overrides the existing app language — that's explicit departure, not inconsistency.

Reading the language also means judging it. An existing language can be healthy, drifting, or dated, and the verdict decides what "match the conventions" is worth: keep it, modernise within it, or propose migrating off it. The verdict may reach past the visual layer to the component library, the framework and the build tooling, but a verdict at that depth is a finding with a blast radius — stated before designing, never executed inside a polish request. 📖 `references/design-language-health.md` for the signals at each layer, how to confirm the stack, the three verdict routes, and where the finding goes.

Reading a conventions doc is not the same as having found the convention, and the difference is invisible until someone points at the result: a doc names tokens and rules, while the answer you need is usually a component that already exists for this exact job. So once you've chosen a treatment, grep the codebase for the mechanism you're about to write — the prop, the component name, the shape — before writing it. A single hit that turns out to be your own file means you just invented a pattern; several hits elsewhere mean the app already decided and you're about to disagree with it by accident. This costs one command and it is the only step that catches the failure while it's still cheap, because everything downstream — the diff, the type checker, the screenshot — shows an invention and a convention as equally working code.

⚠️ **Read the branch that actually renders, not the file that contains it.** A component routinely holds several layouts and picks one at runtime — `if (!isMobile) return …`, a feature flag, a route check — so the page you are redesigning may be the desktop master-detail while the first layout in the file is the mobile grid. An import name, a component name and a file's opening JSX all describe what *exists*, never what *ships on this route*, which is why designing from them produces a careful redesign of a surface no user sees. The same holds one layer up: confirm a framework or library from the entry point that loads it, not from a manifest that declares it. **Tell: you are describing a layout you inferred from a name rather than one you traced to the branch that returns it.** Trace the render path first; where a surface genuinely has two live branches, design both and say so.

**When you're starting from nothing:** there is no app language to read, so the anchor points come from elsewhere. Pin down three things: the audience (who is looking at this, what's their situation), the subject matter (what does the surface represent, what's its domain), and the job (what does a user need to do here, what's the single point of friction you're solving). These three push back against the stock looks named below. A surface designed for an 8-year-old reads different from one for a surgeon; a dashboard for hospital operations differs from a dashboard for a social network; a permission screen has one job, a home page another. Name what you're designing FOR before you design.

Then decide the smallest system that keeps the second screen consistent with the first: one typeface, tokens for colour, type and spacing, an 8px base, mobile-first breakpoints, and a mature library customised through its tokens rather than a component set built from scratch. Write those decisions into the conventions doc the brownfield branch above goes looking for — `frontend/CLAUDE.md` by default, created through `update-claude-docs` when it doesn't exist yet, which on a greenfield brief it won't — so the next session reads them instead of re-deciding; a screen that needs a different value records it there as a named deviation, not a second rule. 📖 `references/greenfield-minimum-system.md` for the decisions in order.

## The Tension

Matching the app fights being distinctive. "Match existing conventions" unchecked inherits the app's own templated defaults — the generic looks that appear regardless of subject matter. "Be distinctive" unchecked produces a page that doesn't match anything. Neither reads as a failure when examined alone; the failure is when both are true at once — a distinctive page beside a conventional one, or a conventional page that *should* stand out.

**When neighbours exist,** the resolution isn't a rule. Spend the distinctiveness where the surface's actual *job* calls for it, and keep everything around it consistent with its neighbours. If the surface is a core workflow page, make it sing. If it's a sidebar, a modal, or a settings section, let it inherit. If the brief pins a direction already — brand refresh, a new component system rolling out across the app — that decision is made and consistency wins.

**When you're starting from nothing,** there are no neighbours to anchor against, so the tension inverts: the only question left is whether the surface was shaped by the audience, subject and job you named earlier, or whether it defaulted. A dashboard built for a surgeon mid-procedure reads nothing like a reading platform for a novelist. Neither is distinctive by accident; both become distinctive by being shaped for their purpose.

Either way, choices collapse into stock looks when nothing drives them: **cream/serif/terracotta** (warm, literary); **near-black + acid accent** (high contrast); **broadsheet hairline** (newspaper, airy); **SaaS card kit** (rounds, one shadow); **template chrome** (tracked labels, monospace); **AI-native gradient** (indigo-to-pink, glowing). Each bundles an unexamined assumption; they show up everywhere because nothing anchors them. Recognising one is the moment to ask what your audience, subject and job would choose instead. ⚠️ **A one-word theme in a brief names a direction to interpret, not a costume to assemble.** "Industrial", "brutalist", "retro" — the failure is reaching for the theme's signifiers and stacking them, and it is invisible to every check above: hazard stripes, a rotated rubber stamp, rivets and a hatch texture are on no stock-looks list, read as nothing templated, and each passes the five questions alone. The section above makes it likelier rather than catching it, since a reader just warned off defaults hears a named theme as permission. Spend a theme the way distinctiveness is spent — on one element, everything around it quiet — and read a brief's "no need to follow the existing palette" as removing a constraint, not as setting the theme as the new goal. **Tell: the page holds several separate things that exist only because of the theme word.** Measured 2026-09-14: four of them (stripes, stamp, rivets, hatch) were rejected outright as "too much industrial", and what was accepted inverted the register — off-white ground, the brand's own two colours as the only accent, one typeface with weight carrying hierarchy, the theme surviving as restraint.

Where a brief names a *look* rather than a problem, the calibration above is worth a second pass: name the one element that will carry the theme, then cut every other thing on the page that exists because of the theme word. `frontend-design@claude-plugins-official` covers the same ground more fully where it happens to be installed, but it ships separately and this skill does not depend on it.

**A defaulted aesthetic is dull; a fabricated identity is wrong.** Where a surface has a logo position and the product has a real logo, the real logo goes there — never initials in a circle, an emoji, a generic mark from an icon set, or an invented SVG that merely looks brand-shaped. The failure is specific to identity because a placeholder mark reads as a finished decision rather than as a gap: nobody reviews it, and it ships. Where no real mark is available, leave the space honestly empty or set the product's name as text, and say that the logo is missing — that is a question for whoever owns the brand, not a hole to fill with something plausible.

Five questions tell you whether the result was shaped or defaulted. **Swap:** replace the typeface or layout with the usual one — would anyone notice? Where it wouldn't matter is where you defaulted. **Squint:** blur the screen — does the hierarchy survive, and does anything jump out harshly? **Signature:** point to the specific component where this product's character lives; "the overall feel" doesn't count. **Token:** read the CSS variable names aloud — do they belong to this product's world or to any project? **Exclude:** name the audience this direction would be wrong for; a look that suits everyone was chosen by nobody.

## Mobile-first is the default, not a viewport check

Design at 375px first and let columns arrive with width. That order locks in things a later "check it on mobile" pass cannot undo: primary action within thumb reach, destructive actions away from it, 44px touch targets with spacing, three to five destinations in a bottom tab bar, every icon carries a label, nothing hidden on hover, 16px body text (no zoom), tables get a phone shape. A surface that only works with a pointer and wide screen was not designed for most of its users. 📖 `references/mobile-first.md` for checks and WCAG target-size floors.

## Design for people who scan

People look for one thing and act. Eye-tracking favours the layer-cake: scan headings, read chunks when earned. Chunk content under descriptive headings, front-load labels, name button outcomes. One bold action per screen (the first two seconds); rare actions in a menu; defaults instead of questions; errors say what happened, why, what's next; empty states say what would appear and how to create it. Only home, search and print work unlabelled. 📖 `references/designing-for-scanners.md` for patterns and progressive-disclosure traps.

**A brief written as a gap-list produces a page that answers every item — and that page is crowded.** "Can't find property, tenant, grouped meaning, ungroup route, relations" reads as items to cover, so each gap gets its own element — link, card, explainer. Each is defensible; together they bury the one figure the reader came for. Measured 2026-09-05: a header linking and explaining everything was rejected as "very crowded, lesser things to focus". The fix was fewer elements — relations folded to a muted line, zero-column hidden. Apply hierarchy to the gap-list itself, not each gap; a reader in a hurry is the audience, not completeness.

## Scope and Blast Radius

A "polish this section" request is smaller than a "redesign this page" request, even if the page is small and the section is large, because polish affects existing surfaces and redesign can rework the whole structure. Scope by blast radius, not phrasing.

Single-element fixes build directly. Section polishes (card layout, forms) propose inline and code. Page redesigns or module-wide passes survey first — existing language or audience/subject/job — capture the current surface before anything replaces it (`## Verify by Looking`), then propose and wait for approval before coding. Use `AskUserQuestion` for genuine branches, inline prose for one direction to confirm. Put the mockup in option `preview`, not in prose ahead — the prompt is what the user sees, and detached proposals misdirect (📖 `brainstorming` Step 4). This prevents rewriting when spacing was wanted, or tweaking when rework was intended.

## The States Beyond the Happy Path

A populated, working interface is what gets reviewed. What it looks like while loading, with zero rows, with one row, on error, when disabled, and when text overflows is the space where shallow UI breaks silently. Build for those too.

**Loading specifically**: stale content feels broken rather than pending — users can't tell fetching from hang. An image slider kept showing the previous photo until the next loaded, reported as a bug. Show nothing (skeleton, spinner, gray) instead.

**Empty states invite action; errors explain and show the path forward.** "No activity yet" names the absence, not what the state means or how to change it.

**Lazy-loading is design, not just performance.** Deferring a component or list buys a faster first paint by hiding discoverability — what you defer decides what users find. Defer what they hunt for (heavy picker, map, page two); keep resident what tells them what the screen is and what to do. The trade lands hardest on phones where deferred is below-fold and slow connections mean "never appears". Use deferral only where weight exists; splitting small content costs a round trip. Deferred content still needs loading states and full-size placeholders so layouts don't shift.

**A populated interface needs the same question.** A surface showing accurate figures but offering nowhere to go answers "what is true", never "what do I do". Ask what the reader does next with each figure and give them a way to act. Where there's no honest next step, state the meaning rather than invent a destination — a drill-down built on an API-unsupported filter reads helpful but goes nowhere.

## Look at the Picture

When a screenshot arrives, read it as a rendered interface *separately* from whatever question came with it. Even when the question is about a bug, an API, or a query — not about UI at all — scan the image for overflow, collision, misalignment, inconsistent spacing, truncation, contrast. This applies even when nobody has called it a UI problem, because visual defects hide themselves inside technical questions.

Answer what was asked first, then note what else you saw and offer to fix it; don't silently widen scope. "Your slider timeout question — here's the fix. I also spotted the image overflowing its container and the title text colliding with it; want me to address those too?" beats silently fixing the layout and reporting it back.

## Verify by Looking

**On a redesign, capture the before.** "Does this look good" is answered by the new screenshot alone; "is this better than what it replaced" is the question a redesign actually asks, and it needs both states side by side. Take the current surface first — a screenshot, or the page as it renders now — and keep it beside the new one, because once the old surface is gone it is gone, and the comparison gets made from memory of a thing nobody looked at carefully. Scope it by blast radius like everything else here: a single-element fix needs no baseline, a section polish usually does, a page redesign always does.

⚠️ **Reproducing a surface from sources you could not fully read produces invention wearing reproduction's clothes.** Where the real page won't fit — too many files, a component you couldn't locate, a branch you couldn't resolve — the gap fills itself from the design system and the result is a plausible, on-brand, entirely fictional page. It looks like a faithful copy, which is exactly why nobody checks it, and every judgement downstream is then made against a surface that does not exist. Stopping is the correct move: say which part you could not read and what that leaves unverified, rather than shipping a reproduction you cannot vouch for. **Tell: you skipped a file for its size, or you are writing "likely", "probably" or "presumably" about a layout, or you are describing a component's contents from its name without having opened it.**

A UI change is verified by looking at it, not by the diff. A screenshot of the changed state suffices; a diff shows what bytes moved, not whether the interface reads right. Spacing that looks correct at one viewport breaks at another; a button that reads as clickable on desktop sits at ambiguous contrast on mobile; a card layout that works with three items wraps differently with twelve. The rendering carries meaning the source never does.

⚠️ **First confirm the render came from YOUR source; a stale bundle is indistinguishable from a design defect and misdirects every explanation.** A dead dev server serves its last built bundle plausibly wrong, so a vanished control reads as a broken conditional, a shifted layout reads as bad spacing, a failed selector reads as a regression. Checking the server *process* fails here — it outlives its source file; instead verify the bundle is present, fetchable, and newer than your edits. Measured 2026-09-10: live processes with the hot-reload gone, a three-week-old bundle served, an hour spent explaining a blank page with its own recent edits. **Tell: you are explaining something you SAW with something you WROTE, and the two are not connected.**

Where a browser-driving agent exists, verify flows with it — test that a click does what's intended. Otherwise, screenshots verify static state: spacing, alignment, readability, contrast, truncation. Ask for screenshots after proposals, especially at scope where surprises are common. ASCII mockups aren't screenshots — box-drawing hides type, padding and weight, so tidy `preview` becomes two stacked grey-text cards. Treat the first render as a second approval gate.

Verification scales with blast radius: single-element fixes at one width plus one other; page redesigns at 375px, 768px, 1280px with interaction states (hover, focus, disabled, loading), contrast, motion, layout-shift. 📖 `references/verification-checklist.md` for thresholds.

E2E recordings walk real flows and surface defects assertions can't — markup rendering as text, copy broken by the product never delivering. Treat a cut-off edge as the viewport boundary, not a layout bug.
