# Target types — what counts as a genuine fact in each

Read when the target isn't an obvious SKILL.md — an agent definition, a CLAUDE.md, a slash command, an on-demand reference table, or something carrying ADR blocks. The fact-vs-constraint test is constant; what it protects differs by class.


The test above is constant; what counts as a "genuine fact" differs by target, and getting this wrong in either direction — treating a real boundary as removable constraint, or treating stale scaffolding as an untouchable fact — is the actual risk of this pass.

**SKILL.md** — a workflow loaded on demand, only when triggered. The clearest case: almost everything in a mature SKILL.md that reads as a rigid step-by-step with trip-wires is fair game, because the whole point of a skill is that a competent agent is already reading it in the moment it's needed and can be trusted to apply judgement to what it just read. Genuine facts here are usually narrow and structural — an exact shell command, a file path, a version-bump protocol, a described consumer-vs-owner split.

**Agent definitions** (`.claude/agents/*.md`) — same body-text judgement as a SKILL.md, but the `tools:` frontmatter is a different animal entirely. A restricted toolset (no `Edit` on a reviewer, no `Bash` on a read-only worker) is the actual mandate boundary, not overconstraint dressed up as one — removing it doesn't free judgement, it changes what the agent *is*. Scrutinize the body prose the way you would a SKILL.md; leave `tools:` and the stated mandate alone unless the session has independent reason to believe the boundary itself is wrong, which is a different, much rarer finding than "this reads as rigid."

**CLAUDE.md / CLAUDE.local.md** — loaded on *every* turn of *every* session, unconditionally, which is the opposite cost profile from a skill. A rule here is paid for whether or not it's ever relevant to the current task, so the bar for keeping something as a standing rule (versus routing it to a companion file read on demand) is if anything stricter here than in a skill, even though the target of this pass — overconstraint — is the same. Don't read "unhobble" as "CLAUDE.md should get shorter across the board"; read it as "a rule that's really a judgement call dressed as a mandate costs the same on every turn, so it's the first thing worth cutting."

**Slash commands** (`commands/*.md`) — usually thin by nature (a short imperative wrapping a tool call or a skill dispatch), so this pass most often finds nothing. Worth checking anyway if one has grown a body of caveats and edge-case handling that reads like a SKILL.md wearing a command's clothing — that's a sign it should probably just delegate to a real skill instead of accumulating its own enforcement layer.

**On-demand reference tables** (companion `.md` files split OUT of a CLAUDE.md into their own file, a task doc's symptom index, anything whose own header says "read this when the symptom matches" rather than "load every turn" or "follow as a workflow") — a fifth cost profile the four categories above don't cover, and the one most likely to get force-fit into "it's basically a CLAUDE.md" or "it's basically a SKILL.md" without noticing neither fits. The read pattern for this class is lookup, not linear consumption or every-turn cost: a reader arrives already holding a specific symptom and needs the one matching row, not the file's overall argument. What the file exists to provide is scan-by-row-boundary — one bounded chunk per gotcha, findable without reading its neighbors — and that property survives a table→prose conversion as long as the row shape stays bounded and self-contained; a header naming a fixed convention (`❌ NEVER | ✅ ALWAYS`, `Symptom | Cause | Fix`) is this codebase's chosen way of making rows bounded, not the only way, so converting one to consequence-stated prose is a legitimate rewrite provided each unit still reads as its own lookup-able chunk. What it is NOT legitimate for is losing content: a merge into a differently-shaped table (or into prose) is exactly the moment a specific method name, error code, or measured figure quietly drops while the row still reads as a faithful paraphrase — verify by diffing every backtick-quoted identifier and number in the original against the rewrite, not by re-reading for a sense of completeness (the same claim step 5 makes about the whole-file pass applies here at row granularity). A third, independent question is whether the row's own decoration — a leading ⚠️, bold on the left-hand cell, a trailing `**Tell:**` sentence — is adding a checkable fact the row's plain text doesn't already carry, or just restating the row's own condition back at the reader; a table of genuinely fact-shaped rows can still read as overconstrained if a chunk of them are wearing emphasis that says nothing new.

⚠️ **This class requires a genuinely separate file — a `## Part N — Reference` SECTION living inside a CLAUDE.md is never class 5, no matter how it's headed, worded, or how many former companion files it says it was merged from.** The class-5 cost profile (lookup, not every-turn) comes from the file being outside what the harness auto-loads — that's a fact about the harness's file-discovery mechanism, not about a section's internal narrative. A CLAUDE.md is the standing exception: the harness loads the *entire physical file* into every session unconditionally, so a section inside it that calls itself "Reference," says content is fetched "one hop further down," or narrates its own history as "former companions… merged into one file" is still paid for on every single turn regardless of what that framing claims. Test it structurally, not rhetorically: if the content is a header inside the CLAUDE.md you're auditing, it's Part 2 of *this* class (CLAUDE.md, loaded every turn) wearing class-5 vocabulary, not an instance of class 5 itself — the size and organization of a merged reference section is real information about *what to prioritize* inside the CLAUDE.md pass, but it does not exempt that section from the every-turn cost bar or hand it lookup-class treatment. The one way a "reference" narrative is accurate is when the content sits in a physically separate file nothing auto-loads, referenced only by a `📖` pointer sentence — check the file boundary (is this a different path on disk?) before believing the label, in either direction. A prior run of this skill misclassified exactly this case: a project CLAUDE.md's own "Part 5 — Reference (former companions)" section, ~63% of the file by size, was read as class 5 on the strength of its self-description and left unexamined for overconstraint — the size argument for *why* a merge happened is not evidence about the *cost* of the merged result once it's back inside the always-loaded file.

When genuinely unsure whether a target is this class or one of the other four, check the file boundary first, then the header — a header saying "not auto-loaded, read explicitly when X" is only trustworthy once you've confirmed the words sit in a file the harness doesn't auto-load in the first place.

⚠️ **The same file-boundary check applies to any "does NOT auto-load" claim, not just the class-5 case above.** A section carrying that exact sentence is still loaded unconditionally if it physically lives inside a file the harness auto-loads at session start. The tell that this has actually gone wrong, not just that the claim is imprecise: the file's own header states a different architecture than the claim does — "merged into one combined file, everything here auto-loads" at the top and "this section does NOT auto-load" three hundred lines later is a direct self-contradiction the "do the copies still agree" check (step 1) is built to catch, and it is worth cross-checking specifically whenever a target carries this phrase about itself. Where the claim is accurate — a genuinely separate file nothing `import`s or auto-reads, referenced only by a pointer sentence elsewhere — cite it as a real instance of the shift; where it's a self-referential claim inside the always-loaded file itself, its accuracy is a fact to check via the file's own header or the harness's real load behavior, not a structural signal to take on the strength of its own wording.

**Not a sixth target type — a MADR/decision log is out of scope entirely, not a stricter case of one of the five above.** The "fact vs. constraint" test doesn't apply to it: a decision log records what was decided and why, it doesn't issue instructions to a reader, so there's nothing in it to unhobble. What puts it out of scope is that job, not its path — and the two come apart routinely, because a `tasks/**/current.md` carries ADR blocks *and* a symptom-indexed gotcha table in the same file. That table does instruct a reader ("you hit X, here's what's going on"), making it the fifth type living inside a file a path-based reading would exclude wholesale. So judge the section you were pointed at rather than the filename: ADR blocks stay untouched, a `| Symptom | Rule |` table beside them is fair game. A request that names only the file, or that arrives as a design question plus the asker's own reasoning, is worth one clarifying question — both about which section, and about whether they want this pass at all rather than help reasoning through the decision itself.
