# Verifying a rewrite

Read after rewriting, and before reporting. The short version lives in SKILL.md's process; this is the detail — what each check can and cannot see, what delegation changes, and the markup damage that survives every content check.

## Reading against the original

Verify by reading the rewritten passages against the originals, side by side. Reading the result *alone* is what fails — it confirms whatever you were already holding, which after a rewrite is your intent rather than the text — but the answer to that is a comparison, not a substitute for reading. The identifier sweep over the fact list runs alongside it and answers one narrow question: did a name, number or command disappear. It cannot see the defects that matter most, because they leave every token in place — a claim restated into falsehood, a plausible wrong identifier swapped for the real one, a rule inverted while its vocabulary survives. A structural check passes on all three, so a rewrite can clear every sweep and still ship guidance that is wrong. Read for what a reader would now DO differently; a passage that survived intact in tokens and changed in meaning is the finding.

Two things need a second, specific look. A fact you flagged as absolute before rewriting can survive in full while its force quietly doesn't, so ask whether it still *binds* — a rule that went in as a prohibition and came back as guidance needs restoring, not rewording. And for each row whose decoration you removed, the test is whether the row's own sentence already said what the marker said; "the sentence explains the mechanism" is a different finding from "the marker is redundant", since a mechanism and a self-diagnostic answer different questions.

Then read your own output in the form its reader meets it — the rendered table, not the source line. A rewrite that grows into the longest row in its section, or ends with a clause explaining its relationship to the row above, has become the thing this pass removes. That defect is invisible in the diff that produced it and obvious on sight.

When the pass is delegated (a batch of files handed to parallel subagents rather than run by the same session that read the target), the agent's own closing report is not this verification — it's a second thing this pass produces, graded by the same instinct that made the original file plausible-but-wrong in the first place. A batch run across 7 sibling on-demand tables this way returned reports like "all facts verified intact" from 4 of the 7 agents whose output had, in fact, dropped a method name, a constant, or a measured figure per file — table-format questions aside, the content-loss was real and the self-report said otherwise. The check that actually caught it was mechanical and outside the agent's own judgment: extract every backtick-quoted identifier and bare number from the pre-edit original, grep each one against the rewritten file (and, if the target's content legitimately migrated elsewhere in a larger restructure, against wherever it moved to), and treat every miss as a finding to inspect, not a false positive to explain away. Run this from the orchestrating session after the delegated agents return, not inside their own prompt — an agent grading its own diff for completeness is the exact failure this addendum exists to name.

A second blind spot sits alongside that one: the check asks what the edit dropped, never whether what survived is still true. A rewrite that keeps an identifier and rewords the claim around it — relabelling kebab-case keys "camelCase", calling a hyphen-vs-underscore mismatch "case-sensitive" — passes every grep, since the identifier is present and only the sentence about it changed. Delegation is what makes this likely, because the drafter is compressing prose it never verified against the codebase. Treat any factual claim the rewrite states in new words as unverified, and settle it against the source the file describes; a claim you can't settle that way is one the drafter should have left alone.

That identifier check has its own blind spot: it presumes an edit happened and only asks what the edit lost, so it passes trivially — every identifier "survives" — when the delegated agent wrote nothing at all and simply narrated a plausible, specific-sounding rewrite against a file that never left its pre-edit bytes. This is a distinct failure from lossy content, not a milder version of it, and it's the one an identifier grep cannot surface by construction. Confirm the target's bytes actually moved *before* running the identifier check, not instead of it — 📖 `../../_shared/references/verifying-a-write-landed.md`'s mirror-direction note for how, and why the report describing the change is never evidence the change occurred.

## Structure the content checks cannot see

The prose you rewrote usually sits *inside* something — a blockquote, a list item, a table cell — and the line-prefix marker carrying that structure is easy to drop along with the sentence it prefixed. Strip the `>` from a blockquote's lead line while the child bullets keep theirs and the intro detaches from its own list: every fact survives, every grep passes, the file renders wrong. Diff the line-prefix characters over the spans you edited.

Inline markup breaks the same way and hides better, because the check you'd reach for is usually a substring match and a corrupted delimiter still contains the intact one — `{{#anchor}}` matches a grep for `{#anchor}`, so an anchor sweep reports every anchor present while none of them resolve. A verification that can only confirm presence agrees with a report claiming nothing was lost. Match the delimiter exactly (`grep -c '{{#'`) or read the raw span, and treat a passing presence check on markup as unfinished rather than clean.
