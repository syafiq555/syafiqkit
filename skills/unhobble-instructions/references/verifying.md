# Verifying a rewrite

Read after rewriting, and before reporting. The short version lives in SKILL.md's process; this is the detail — what each check can and cannot see, what delegation changes, and the markup damage that survives every content check.

## Reading against the original

Verify by reading the rewritten passages against the originals, side by side. Reading the result *alone* is what fails — it confirms whatever you were already holding, which after a rewrite is your intent rather than the text — but the answer to that is a comparison, not a substitute for reading.

Two things need a second, specific look. A fact you flagged as absolute before rewriting can survive in full while its force quietly doesn't, so ask whether it still *binds* — a rule that went in as a prohibition and came back as guidance needs restoring, not rewording. And for each row whose decoration you removed, the test is whether the row's own sentence already said what the marker said; "the sentence explains the mechanism" is a different finding from "the marker is redundant", since a mechanism and a self-diagnostic answer different questions.

Then read your own output in the form its reader meets it — the rendered table, not the source line. A rewrite that grows into the longest row in its section, or ends with a clause explaining its relationship to the row above, has become the thing this pass removes. That defect is invisible in the diff that produced it and obvious on sight.

## Verification is blind to meaning and to facts that migrated

Single verification methods miss different classes of defects. An identifier sweep answers one narrow question — did a name, number or command disappear — but it cannot see the defects that matter most, because they leave every token in place. A claim restated into falsehood, a plausible wrong identifier swapped for the real one, a rule inverted while its vocabulary survives — each passes every token-level check. Read for what a reader would now DO differently; a passage that survived intact in tokens and changed in meaning is the finding.

**Delegated passes are highest-risk** because an agent's closing report is graded by the same instinct that made the original file plausible-but-wrong, leaving it blind to its own omissions. A batch run across 7 on-demand tables this way returned reports like "all facts verified intact" from 4 of the 7 agents whose output had, in fact, dropped a method name, a constant, or a measured figure per file — the content-loss was real and the self-report said otherwise. The check that catches it is mechanical and outside the agent's judgment: extract every backtick-quoted identifier and bare number from the pre-edit original, grep each one against the rewritten file (and, if the target's content legitimately migrated elsewhere, against wherever it moved to), and treat every miss as a finding to inspect, not a false positive. Run this from the orchestrating session after the delegated agents return, not inside their own prompt — an agent grading its own diff for completeness is the exact failure this section exists to prevent.

**Deletion disguised as routing** is the riskiest form. A pass can delete a section and justify it by an *existing* file the source already pointed at, so the pointer resolves, no new file appears, and the report reads as tidying rather than deletion. A companion scoped to the same domain is not evidence it carries the same facts — topic matching is why the deletion looked safe. Grep the deleted passage's own identifiers against that destination before accepting the claim, and expect the result to be partial: a companion can hold a section's general vocabulary while missing the specific mechanism the deleted prose existed to state, which is precisely the half worth keeping. **Tell: a section was dropped in favour of a companion nobody opened.**

**Rewording changes meaning while keeping tokens.** A rewrite that keeps an identifier and rewords the claim around it — relabelling kebab-case keys "camelCase", calling a hyphen-vs-underscore mismatch "case-sensitive" — passes every grep, since the identifier is present and only the sentence about it changed. Delegation makes this likely, because the drafter is compressing prose it never verified against the codebase. Treat any factual claim the rewrite states in new words as unverified, and settle it against the source the file describes; a claim you can't settle that way is one the drafter should have left alone.

**Delegated agent wrote nothing at all.** An identifier check presumes an edit happened and only asks what the edit lost, so it passes trivially — every identifier "survives" — when the agent simply narrated a plausible, specific-sounding rewrite against a file that never left its pre-edit bytes. This is a distinct failure from lossy content, not a milder version. Confirm the target's bytes actually moved *before* running the identifier check, not instead of it — 📖 `../../_shared/references/verifying-a-write-landed.md`'s mirror-direction note for how, and why the report describing the change is never evidence the change occurred.

## Structure and markup damage

**Stripped prefixes break rendering.** The prose you rewrote usually sits *inside* something — a blockquote, a list item, a table cell — and the line-prefix marker carrying that structure is easy to drop along with the sentence it prefixed. Strip the `>` from a blockquote's lead line while the child bullets keep theirs and the intro detaches from its own list: every fact survives, every grep passes, the file renders wrong. Diff the line-prefix characters over the spans you edited.

**Corrupted delimiters hide in substring matches.** Inline markup breaks the same way but hides better, because the check you'd reach for is usually a substring match and a corrupted delimiter still contains the intact one. A doubled-brace anchor like `{{#anchor}}` matches a grep for `{#anchor}`, so an anchor sweep reports every anchor present while none of them actually resolve. Match the delimiter exactly (`grep -c '{{#'` for double-braces, etc.) or read the raw span, and treat a passing presence check on markup as unfinished rather than clean.

**When the pass moved content out to a companion, read 📖 `../../_shared/references/verifying-a-relocation.md` before calling it clean.** Every check on this page reads the file the pass produced, and a relocation puts its defects outside that file: a link whose `../` depth no longer resolves once both halves changed level, and a documented glob that still matches after it stopped covering — the split renamed the files out from under an instruction that is intact and now finds a fraction of them.
