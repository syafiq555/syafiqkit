name: unhobble-instructions
description: >
  Read an instruction-bearing file as a whole and rewrite it into better shape — a SKILL.md, an agent definition, a CLAUDE.md/CLAUDE.local.md, a slash command, or an on-demand reference table. This is a whole-file improver, not a marker checker: it judges what the file makes a reader DO (ordering, where each rule sits relative to the moment it applies, what's stated in three places) and restructures accordingly, then separately folds rigid imperatives, "Tell:"-style trip-wires and mechanical thresholds into judgement prose wherever judgement already covers them — while keeping every fact a model can't derive (harness behavior, a real binary with a real consequence, this repo's layout). Moving, merging and resequencing whole sections is in scope and often the main deliverable. Trigger on "apply unhobbling to X", "unhobble these skills", "rewrite this as judgement prose", "read this file as a whole and improve it", "is this skill overconstrained", "this file has too many rules", "check this agent for rigid instructions", "de-constrain this", or when authoring or reviewing an instruction file that has accumulated more enforcement machinery than the judgement it protects seems to warrant. The lens is judgement-vs-constraint, not length — plain trimming is `condense-claude-md`/`condense-task-doc`. A first-draft file rarely qualifies, since overconstraint is drift rather than a day-one property, and a decision log is out of scope entirely (see "the one test" and the target-type notes below for that boundary, which turns on the section rather than the path).

# Unhobble Instructions

Anthropic's framing (the "Unhobbling Claude" note): internal transcripts showed system prompt, CLAUDE.md, and skills stacking conflicting directives — "leave documentation as appropriate" next to "DO NOT add comments" — because constraints installed once to prevent a worst case never got removed once the model could be trusted to reason about that case from context instead. The fix isn't fewer words; it's fewer *rules standing in for judgement the model already has*.

This skill runs that pass for real, on one target file at a time, across five content classes that need different judgement calls — and it does NOT run at all on a class that only looks similar: a decision log.

**This is a whole-file improver, not a marker audit.** The per-rule test below is the second half of the pass; it only earns its keep once you have read the file as a document and formed a view of what it makes a reader DO. Run the per-rule test first and you get an enumeration — a verdict on each unit, a tally, a handful of callouts softened — while the thing that actually hobbles a reader survives intact, because it lives in the arrangement rather than in any one rule. A file can be composed entirely of genuine facts and still be badly shaped: the same rule stated in three places, a mandate positioned above the branch that doesn't need it, a cold-path detour inlined in the hot path, a step whose completion nothing can check. None of that is visible one row at a time.

So the deliverable is a better file, which routinely means moving, merging, resequencing or rewriting whole sections — not a list of rules graded fact-or-constraint. Grepping for `⚠️`/`MANDATORY`/`**Tell:**` and grading what comes back is the failure mode this paragraph exists to name: it finds overconstraint's vocabulary while its shape goes untouched, and it reports clean.

The same count misleads one step earlier, when several files are candidates and you're choosing which to open. Marker density predicts a file's *subject* — verification files are dense in `**Tell:**` because self-diagnostics are what they're for — not how overconstrained it is, so the densest-looking candidate is often the healthiest and the file with no markers at all can be the badly shaped one. Treat a count as a way to locate candidates and nothing more; the choice comes from reading each one's arrangement. Acting on the count instead is expensive in the one direction that matters: a file's markers can be 97% load-bearing, and a pass that arrives expecting to strip them will.

## Read the file as a document first

Before any rule-by-rule work, read it end to end and answer three questions about the file as a whole. These have nothing to do with which rules are facts:

- **What does this make a reader do, in order?** Trace the actual path — first action, second, third. Where does the physical order of the file disagree with its execution order? A reader who meets a rule 80 lines before the moment it applies has to carry it, and mostly won't.
- **Where is each rule relative to the moment it's needed?** A correct rule in the wrong place fails as reliably as a wrong rule. The commonest shape: a warning stacked at the top, above the branch it governs, where it's read before there is anything to apply it to — or a mandate sitting in a path most invocations don't take.
- **What does the file say more than once, and why did that happen?** A rule in three homes isn't a wording problem; it's the residue of three sessions each patching the same miss without retiring the previous patch. Collapsing those is usually worth more than softening any individual one.

Whatever this read surfaces is the pass's main finding. The per-rule test then runs against what's left.

## The second test: per rule

Once the shape is settled, for each rule, callout, or instruction that remains: **is this a fact the model can't derive on its own, or a behavioral constraint installed to force a process onto something judgement already covers?**

A fact has a real, checkable consequence if missed — a harness quirk (an env var that only expands in one context), a genuine binary with a silent-failure cost (owner vs. consumer checkout), a structural detail about this specific repo (which file is the template, which is the generated copy). No amount of "just reason about it" gets a reader to the right answer, because the answer isn't derivable — it has to be told.

A constraint is a rule that's really re-stating what a competent read would already conclude, made rigid because a past mistake got patched with a new rule instead of trusting the next read to do better. The tells: a "Tell: you did X" trip-wire naming one specific way to have failed; a bolded ALL-CAPS imperative; a numeric threshold standing in for "does this feel right"; two callouts making the same point because the first one apparently didn't stick; a worked incident embedded in the instructions themselves instead of left in git history where it belongs.

A row that already reads as a clear fact can still carry this in its decoration rather than its content — an ⚠️ or a `**Tell:**` sentence bolted onto a row whose own right-hand side already states the reasoning is the same over-emphasis, one layer down, and it's easy to credit the row as "already fine" because its content passes the test while never separately asking what the marker itself is adding. The genuine version names a checkable fact the row's own text doesn't already contain (an exact column name, a specific magnitude, a concrete symptom to look for); the hollow version just restates the row's own left-hand condition back as a "watch for this," which reads as extra diligence but tells the reader nothing new. Check the two separately — a table full of terse, correct rows can still be dense with this if half of them are wearing a warning label that says nothing the row beside it didn't.

Facts stay, stated plainly. Constraints get rewritten as judgement prose — state the reasoning, let the reader apply it, don't pre-empt every way it could go wrong with a named trap for each one. Losing a genuine fact while chasing this is the actual failure mode to watch for, not the deletion count.

## Reading the five target types

The test above is constant; what counts as a "genuine fact" differs by target, and getting this wrong in either direction — treating a real boundary as removable constraint, or treating stale scaffolding as an untouchable fact — is the actual risk of this pass.

**SKILL.md** — a workflow loaded on demand, only when triggered. The clearest case: almost everything in a mature SKILL.md that reads as a rigid step-by-step with trip-wires is fair game, because the whole point of a skill is that a competent agent is already reading it in the moment it's needed and can be trusted to apply judgement to what it just read. Genuine facts here are usually narrow and structural — an exact shell command, a file path, a version-bump protocol, a described consumer-vs-owner split.

**Agent definitions** (`.claude/agents/*.md`) — same body-text judgement as a SKILL.md, but the `tools:` frontmatter is a different animal entirely. A restricted toolset (no `Edit` on a reviewer, no `Bash` on a read-only worker) is the actual mandate boundary, not overconstraint dressed up as one — removing it doesn't free judgement, it changes what the agent *is*. Scrutinize the body prose the way you would a SKILL.md; leave `tools:` and the stated mandate alone unless the session has independent reason to believe the boundary itself is wrong, which is a different, much rarer finding than "this reads as rigid."

**CLAUDE.md / CLAUDE.local.md** — loaded on *every* turn of *every* session, unconditionally, which is the opposite cost profile from a skill. A rule here is paid for whether or not it's ever relevant to the current task, so the bar for keeping something as a standing rule (versus routing it to a companion file read on demand) is if anything stricter here than in a skill, even though the target of this pass — overconstraint — is the same. Don't read "unhobble" as "CLAUDE.md should get shorter across the board"; read it as "a rule that's really a judgement call dressed as a mandate costs the same on every turn, so it's the first thing worth cutting."

**Slash commands** (`commands/*.md`) — usually thin by nature (a short imperative wrapping a tool call or a skill dispatch), so this pass most often finds nothing. Worth checking anyway if one has grown a body of caveats and edge-case handling that reads like a SKILL.md wearing a command's clothing — that's a sign it should probably just delegate to a real skill instead of accumulating its own enforcement layer.

**On-demand reference tables** (companion `.md` files split out of a CLAUDE.md, a task doc's symptom index, anything whose own header says "read this when the symptom matches" rather than "load every turn" or "follow as a workflow") — a fifth cost profile the four categories above don't cover, and the one most likely to get force-fit into "it's basically a CLAUDE.md" or "it's basically a SKILL.md" without noticing neither fits. The read pattern for this class is lookup, not linear consumption or every-turn cost: a reader arrives already holding a specific symptom and needs the one matching row, not the file's overall argument. What the file exists to provide is scan-by-row-boundary — one bounded chunk per gotcha, findable without reading its neighbors — and that property survives a table→prose conversion as long as the row shape stays bounded and self-contained; a header naming a fixed convention (`❌ NEVER | ✅ ALWAYS`, `Symptom | Cause | Fix`) is this codebase's chosen way of making rows bounded, not the only way, so converting one to consequence-stated prose is a legitimate rewrite provided each unit still reads as its own lookup-able chunk. What it is NOT legitimate for is losing content: a merge into a differently-shaped table (or into prose) is exactly the moment a specific method name, error code, or measured figure quietly drops while the row still reads as a faithful paraphrase — verify by diffing every backtick-quoted identifier and number in the original against the rewrite, not by re-reading for a sense of completeness (the same claim step 5 makes about the whole-file pass applies here at row granularity). A third, independent question is whether the row's own decoration — a leading ⚠️, bold on the left-hand cell, a trailing `**Tell:**` sentence — is adding a checkable fact the row's plain text doesn't already carry, or just restating the row's own condition back at the reader; a table of genuinely fact-shaped rows can still read as overconstrained if a chunk of them are wearing emphasis that says nothing new. When genuinely unsure whether a target is this class or one of the other four, its own header usually says so directly ("not auto-loaded, read explicitly when X") — that line is the signal to check before defaulting to the nearest-looking category.

**Not a sixth target type — a MADR/decision log is out of scope entirely, not a stricter case of one of the five above.** The "fact vs. constraint" test doesn't apply to it: a decision log records what was decided and why, it doesn't issue instructions to a reader, so there's nothing in it to unhobble. What puts it out of scope is that job, not its path — and the two come apart routinely, because a `tasks/**/current.md` carries ADR blocks *and* a symptom-indexed gotcha table in the same file. That table does instruct a reader ("you hit X, here's what's going on"), making it the fifth type living inside a file a path-based reading would exclude wholesale. So judge the section you were pointed at rather than the filename: ADR blocks stay untouched, a `| Symptom | Rule |` table beside them is fair game. A request that names only the file, or that arrives as a design question plus the asker's own reasoning, is worth one clarifying question — both about which section, and about whether they want this pass at all rather than help reasoning through the decision itself.

## Process

1. Read the target file whole, cold — as if seeing it for the first time, not defending anything you or anyone else wrote into it — and answer the three document-level questions above in writing before opening a single rule. Written down, because a whole-file read that produces no artifact collapses into a warm-up for the rule-by-rule pass and stops informing it; the ordering, positioning and repetition findings are what step 4 rewrites toward, so they have to exist as text first. If this step produced nothing, the pass has not started yet.
2. Then go through what remains against the per-rule test. For each rule: name whether it's fact or constraint, and for a fact, what the actual consequence of getting it wrong is (not just "this seems important"). Before softening anything that reads as absolutist (a "no exceptions," "no judgment permitted" rule rather than a garden-variety `⚠️ MANDATORY`), grep the project's `decisions/*.md`/task-doc history for the rule's own keywords — some rigid-looking rules are the surviving fix to a documented incident where judgement was tried at that exact spot and failed, and a Rejected-alternatives entry saying so outranks this pass's default lean toward loosening. The absolutism there isn't unexamined scaffolding; removing it reopens the failure it was written to close. Apply the same per-row test to a row's decoration as to its content, separately: a `⚠️` or trailing `**Tell:**` that just restates the row's own left-hand condition is hollow and comes off; one that gives the reader a checkable fact or self-diagnostic question their prose doesn't already state — "did you verify this before or after the last tool call" is a real question, not a rephrasing of "you asserted stale state" — stays. Reading the row's main sentence as sufficient because it explains the mechanism isn't the same test as checking whether the Tell adds something that sentence doesn't.
3. Before rewriting, list the genuine facts explicitly — these are what verification checks against afterward, and skipping this step is how a full-file rewrite quietly drops something real while still reading plausibly. Mark which of them are stated *absolutely* ("never", "no exceptions", "no judgment permitted") as you list them, because those carry a second property the list would otherwise lose: a fact can survive a rewrite in full while its force quietly doesn't, and the softened version reads as a faithful paraphrase. On a row-table target, also list which rows carry a decorative marker worth a second look — this second list is what step 5 checks the decoration pass against, the same way the fact list anchors the content pass; without it, a marker's removal is judged only by whether the row still "reads fine," which is exactly the re-reading step 5 already warns can't be trusted.
4. Rewrite. Facts stay, stated as plainly as the file's existing prose allows. Constraints get folded into flowing judgement prose — state the reasoning once, trust the reader, don't leave a trip-wire behind for every way it could be misapplied. A full `Write` rewrite is usually the right tool once more than a handful of scattered rules are affected; targeted `Edit`s are fine for one or two isolated callouts.
5. Verify against the fact list from step 3 — grep for each one and confirm it survived somewhere in the rewrite, rather than reading back over the result to see whether it "feels complete." Re-reading is what the fact list exists to replace: it reliably confirms whatever you were already holding in mind, which after a rewrite is your intent rather than the text, so "verified by re-reading" is a claim the method can't support and the report reads as sound either way. This is the step most likely to get skipped under time pressure and the one most likely to matter. For the ones flagged absolute, checking survival isn't enough: re-read each and ask whether it still *binds* as hard as it did, since a surviving-but-softened rule passes a presence check and reopens exactly the failure the absolutism was closing. A rule that came back as guidance where it went in as a prohibition needs restoring, not rewording. For each row on step 3's decoration list, re-check the specific test rather than trusting the earlier read: does the row's plain-text sentence already say what the marker says, or does the marker carry a fact/question the sentence doesn't? "The sentence explains the mechanism" is not the same finding as "the marker is redundant" — a mechanism explanation and a self-diagnostic question answer different things, and conflating them is how a genuine Tell gets stripped alongside the hollow ones.

   When the pass is delegated (a batch of files handed to parallel subagents rather than run by the same session that read the target), the agent's own closing report is not this verification — it's a second thing this pass produces, graded by the same instinct that made the original file plausible-but-wrong in the first place. A batch run across 7 sibling on-demand tables this way returned reports like "all facts verified intact" from 4 of the 7 agents whose output had, in fact, dropped a method name, a constant, or a measured figure per file — table-format questions aside, the content-loss was real and the self-report said otherwise. The check that actually caught it was mechanical and outside the agent's own judgment: extract every backtick-quoted identifier and bare number from the pre-edit original, grep each one against the rewritten file (and, if the target's content legitimately migrated elsewhere in a larger restructure, against wherever it moved to), and treat every miss as a finding to inspect, not a false positive to explain away. Run this from the orchestrating session after the delegated agents return, not inside their own prompt — an agent grading its own diff for completeness is the exact failure this addendum exists to name.

   A second blind spot sits alongside that one: the check asks what the edit dropped, never whether what survived is still true. A rewrite that keeps an identifier and rewords the claim around it — relabelling kebab-case keys "camelCase", calling a hyphen-vs-underscore mismatch "case-sensitive" — passes every grep, since the identifier is present and only the sentence about it changed. Delegation is what makes this likely, because the drafter is compressing prose it never verified against the codebase. Treat any factual claim the rewrite states in new words as unverified, and settle it against the source the file describes; a claim you can't settle that way is one the drafter should have left alone.

   That identifier check has its own blind spot: it presumes an edit happened and only asks what the edit lost, so it passes trivially — every identifier "survives" — when the delegated agent wrote nothing at all and simply narrated a plausible, specific-sounding rewrite against a file that never left its pre-edit bytes. This is a distinct failure from lossy content, not a milder version of it, and it's the one an identifier grep cannot surface by construction. Confirm the target's bytes actually moved *before* running the identifier check, not instead of it — 📖 `../_shared/references/verifying-a-write-landed.md`'s mirror-direction note for how, and why the report describing the change is never evidence the change occurred.
6. Reconcile what points AT the file. Restructuring is the operation that invalidates inbound references, and they live outside the file so nothing in the rewrite surfaces them: a new anchor means every pointer still advertises the old shape, a merged or moved section leaves `file.md#anchor` links landing in the right file at a section that no longer exists, and a summary clause listing the target's contents now under-describes it. None of this 404s — the reader arrives somewhere plausible and concludes the fact isn't there. `grep -rn "<basename>" ` across the docs tree that owns the file, check each hit against what the file now says, and fix the ones that drifted. This is the same rule `update-claude-docs`'s `references/pointer-discipline.md` §2 states for editing a companion; it applies with more force here because a whole-file pass changes structure rather than one row.
7. Re-read your own new prose against the same test you just ran on the target. A rewrite that argues against rigid imperatives while itself opening with a bolded ALL-CAPS directive has undercut its own point mid-sentence — this is an easy mistake to make precisely because you're holding the target's flaws in mind and not your own draft's.
8. Report what changed and why, leading with the structural changes — what moved, what merged, what got resequenced, and which of step 1's three questions each answers. A report that opens with a count of softened callouts is describing the smaller half of the pass and reads as complete while the shape findings go unmentioned. Include anything that was a genuine bet rather than a strict improvement — e.g. trading a numeric mechanical check for a judgement call is a real trade-off (the mechanical check would fire reliably regardless of how a given read feels; judgement might not), not something to gloss over as a pure win. A pass that found no structural problem and only softened wording is a legitimate outcome, but say so explicitly, since it's also what a marker hunt produces.

## Owning skill/plugin conventions

When the target is a syafiqkit file specifically, this pass runs alongside — not instead of — the plugin's own authorship conventions: version bump + CHANGELOG entry via `CLAUDE.md`'s Version Bumping convention (unless told to skip), Step 0's ownership check before patching (`update-plugin`'s pattern — never edit a consumer-side install), and a shared-mechanism grep before assuming a fix is single-file (if the same overconstrained pattern shows up in a sibling skill, it's worth flagging even if only one target was asked for). For a third-party or non-syafiqkit file, none of that applies — just the audit-and-rewrite itself.

## What this skill is not

Not a general condensing pass — `condense-claude-md`/`condense-task-doc` own byte/line reduction and structural splits, and this skill can make a file *longer* if a genuinely dense but under-explained rule needs to become judgement prose with real reasoning instead of a terse trap. Not a correctness review — a rule can be perfectly correct and still be the wrong *shape* (a rigid mandate for something judgement handles fine); conversely a piece of prose can read as tasteful and still be quietly wrong, which this pass won't catch, `code-reviewer`/`product-reviewer` will. Not a one-time fix — overconstraint accumulates the same way it did in the file that prompted this skill to exist, one patched worst-case at a time, so a file that's been unhobbled once can still need it again after enough sessions of "and also never do Y."
