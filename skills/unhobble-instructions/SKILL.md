# Unhobble Instructions

Anthropic's framing (the "Unhobbling Claude" note): internal transcripts showed system prompt, CLAUDE.md, and skills stacking conflicting directives — "leave documentation as appropriate" next to "DO NOT add comments" — because constraints installed once to prevent a worst case never got removed once the model could be trusted to reason about that case from context instead. The fix isn't fewer words; it's fewer *rules standing in for judgement the model already has*.

This skill runs that pass for real, on one target file at a time, across five content classes that need different judgement calls.

## The one test that matters

For every rule, callout, or instruction in the target: **is this a fact the model can't derive on its own, or a behavioral constraint installed to force a process onto something judgement already covers?**

A fact has a real, checkable consequence if missed — a harness quirk (an env var that only expands in one context), a genuine binary with a silent-failure cost (owner vs. consumer checkout), a structural detail about this specific repo (which file is the template, which is the generated copy). No amount of "just reason about it" gets a reader to the right answer, because the answer isn't derivable — it has to be told.

A constraint is a rule that's really re-stating what a competent read would already conclude, made rigid because a past mistake got patched with a new rule instead of trusting the next read to do better. The tells: a "Tell: you did X" trip-wire naming one specific way to have failed; a bolded ALL-CAPS imperative; a numeric threshold standing in for "does this feel right"; two callouts making the same point because the first one apparently didn't stick; a worked incident embedded in the instructions themselves instead of left in git history where it belongs.

Facts stay, stated plainly. Constraints get rewritten as judgement prose — state the reasoning, let the reader apply it, don't pre-empt every way it could go wrong with a named trap for each one. Losing a genuine fact while chasing this is the actual failure mode to watch for, not the deletion count.

## Reading the four target types

The test above is constant; what counts as a "genuine fact" differs by target, and getting this wrong in either direction — treating a real boundary as removable constraint, or treating stale scaffolding as an untouchable fact — is the actual risk of this pass.

**SKILL.md** — a workflow loaded on demand, only when triggered. The clearest case: almost everything in a mature SKILL.md that reads as a rigid step-by-step with trip-wires is fair game, because the whole point of a skill is that a competent agent is already reading it in the moment it's needed and can be trusted to apply judgement to what it just read. Genuine facts here are usually narrow and structural — an exact shell command, a file path, a version-bump protocol, a described consumer-vs-owner split.

**Agent definitions** (`.claude/agents/*.md`) — same body-text judgement as a SKILL.md, but the `tools:` frontmatter is a different animal entirely. A restricted toolset (no `Edit` on a reviewer, no `Bash` on a read-only worker) is the actual mandate boundary, not overconstraint dressed up as one — removing it doesn't free judgement, it changes what the agent *is*. Scrutinize the body prose the way you would a SKILL.md; leave `tools:` and the stated mandate alone unless the session has independent reason to believe the boundary itself is wrong, which is a different, much rarer finding than "this reads as rigid."

**CLAUDE.md / CLAUDE.local.md** — loaded on *every* turn of *every* session, unconditionally, which is the opposite cost profile from a skill. A rule here is paid for whether or not it's ever relevant to the current task, so the bar for keeping something as a standing rule (versus routing it to a companion file read on demand) is if anything stricter here than in a skill, even though the target of this pass — overconstraint — is the same. Don't read "unhobble" as "CLAUDE.md should get shorter across the board"; read it as "a rule that's really a judgement call dressed as a mandate costs the same on every turn, so it's the first thing worth cutting."

**Slash commands** (`commands/*.md`) — usually thin by nature (a short imperative wrapping a tool call or a skill dispatch), so this pass most often finds nothing. Worth checking anyway if one has grown a body of caveats and edge-case handling that reads like a SKILL.md wearing a command's clothing — that's a sign it should probably just delegate to a real skill instead of accumulating its own enforcement layer.

**On-demand reference tables** (companion `.md` files split out of a CLAUDE.md, a task doc's symptom index, anything whose own header says "read this when the symptom matches" rather than "load every turn" or "follow as a workflow") — a fifth cost profile the four categories above don't cover, and the one most likely to get force-fit into "it's basically a CLAUDE.md" or "it's basically a SKILL.md" without noticing neither fits. The read pattern for this class is lookup, not linear consumption or every-turn cost: a reader arrives already holding a specific symptom and needs the one matching row, not the file's overall argument. That makes a ❌/✅ table's row-per-unit structure a property worth defending on its own terms, separate from whether any individual row's *content* is fact or constraint — collapsing rows into flowing prose for readability trades away exactly the scan-by-row-boundary property the file exists to provide, even when the prose is objectively better writing. Apply the one test per row as usual, but treat "should this row become prose" as a second, independent question from "is this row's content a fact or a constraint" — a genuine constraint can still belong in table form if the file's whole reason for existing is fast symptom-matching. When genuinely unsure whether a target is this class or one of the other four, its own header usually says so directly ("not auto-loaded, read explicitly when X") — that line is the signal to check before defaulting to the nearest-looking category.

## Process

1. Read the target file whole, cold — as if seeing it for the first time, not defending anything you or anyone else wrote into it.
2. Go through it top to bottom against the one test. For each rule: name whether it's fact or constraint, and for a fact, what the actual consequence of getting it wrong is (not just "this seems important").
3. Before rewriting, list the genuine facts explicitly — these are what verification checks against afterward, and skipping this step is how a full-file rewrite quietly drops something real while still reading plausibly.
4. Rewrite. Facts stay, stated as plainly as the file's existing prose allows. Constraints get folded into flowing judgement prose — state the reasoning once, trust the reader, don't leave a trip-wire behind for every way it could be misapplied. A full `Write` rewrite is usually the right tool once more than a handful of scattered rules are affected; targeted `Edit`s are fine for one or two isolated callouts.
5. Verify against the fact list from step 3 — grep or re-read for each one, confirm it survived somewhere in the rewrite, not just that the file "feels complete." This is the step most likely to get skipped under time pressure and the one most likely to matter.
6. Re-read your own new prose against the same test you just ran on the target. A rewrite that argues against rigid imperatives while itself opening with a bolded ALL-CAPS directive has undercut its own point mid-sentence — this is an easy mistake to make precisely because you're holding the target's flaws in mind and not your own draft's.
7. Report what changed and why, including anything that was a genuine bet rather than a strict improvement — e.g. trading a numeric mechanical check for a judgement call is a real trade-off (the mechanical check would fire reliably regardless of how a given read feels; judgement might not), not something to gloss over as a pure win.

## Owning skill/plugin conventions

When the target is a syafiqkit file specifically, this pass runs alongside — not instead of — the plugin's own authorship conventions: version bump + CHANGELOG entry via `CLAUDE.md`'s Version Bumping convention (unless told to skip), Step 0's ownership check before patching (`update-plugin`'s pattern — never edit a consumer-side install), and a shared-mechanism grep before assuming a fix is single-file (if the same overconstrained pattern shows up in a sibling skill, it's worth flagging even if only one target was asked for). For a third-party or non-syafiqkit file, none of that applies — just the audit-and-rewrite itself.

## What this skill is not

Not a general condensing pass — `condense-claude-md`/`condense-task-doc` own byte/line reduction and structural splits, and this skill can make a file *longer* if a genuinely dense but under-explained rule needs to become judgement prose with real reasoning instead of a terse trap. Not a correctness review — a rule can be perfectly correct and still be the wrong *shape* (a rigid mandate for something judgement handles fine); conversely a piece of prose can read as tasteful and still be quietly wrong, which this pass won't catch, `code-reviewer`/`product-reviewer` will. Not a one-time fix — overconstraint accumulates the same way it did in the file that prompted this skill to exist, one patched worst-case at a time, so a file that's been unhobbled once can still need it again after enough sessions of "and also never do Y."
