description: >
  Read an instruction-bearing file as a whole and rewrite it into better shape — a SKILL.md, an agent definition, a CLAUDE.md/CLAUDE.local.md, a slash command, or an on-demand reference table. This is a whole-file improver, not a marker checker: it judges what the file makes a reader DO (ordering, where each rule sits relative to the moment it applies, what's stated in three places, what the balance of the file trains) and restructures accordingly, then folds rigid imperatives and mechanical thresholds into judgement prose wherever judgement already covers them — while keeping every fact a model can't derive. Moving, merging and resequencing whole sections is in scope and often the main deliverable. Trigger on "apply unhobbling to X", "unhobble these skills", "rewrite this as judgement prose", "read this file as a whole and improve it", "is this skill overconstrained", "this file has too many rules", "check this agent for rigid instructions", "de-constrain this", or when authoring or reviewing an instruction file that has accumulated more enforcement machinery than the judgement it protects seems to warrant. The lens applies equally to live files and those being drafted — the difference is deliverable shape and where verification starts. A file accumulating constraint-drift usually does so long after authoring; invoking this on a half-drafted file to govern its construction before drift sets in is a legitimate use case and often cheaper than fixing later. The lens is judgement-vs-constraint, not length — plain trimming is `condense-claude-md`/`condense-task-doc`. A decision log is out of scope entirely.

# Unhobble Instructions

**Read the target whole, decide what shape it should have, and rewrite it.** The deliverable is the edited file (when rewriting an existing file) or the drafted file (when authoring one informed by this lens). A run that ends in findings, a strategy or an estimated cut has not done the job however good the analysis — two live runs stopped there and left the target byte-identical. If you reach the end holding a plan, execute it.

When authoring a new instruction file under this lens, the structure reads differently than when auditing an existing one: there is no before/after to diff, no drift to measure against a baseline. Apply the six-question read as you draft — what should a reader DO in order, where does each rule sit relative to its moment of need, what facts repeat, what would the balance train — and write toward that shape from the start. The verification step still applies (read it whole when draft is done, ask the same six questions) but it measures against the file itself rather than against an earlier version. A run that ends in an outline or a structure sketch has not delivered, the same as an audit-shaped run that ends in strategy.

Constraints installed to prevent a worst case don't get removed once the model can reason about that case from context, so instruction files accumulate rules standing in for judgement the reader already has. The fix isn't fewer words — a genuinely dense but under-explained rule may need to get *longer* to become reasoning. It's fewer rules doing work judgement would do better.

Anthropic's write-up of this (`claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models`) names six shifts: rules→judgement, examples→interfaces, upfront→progressive disclosure, repetition→one home, CLAUDE.md-memory→auto-memory, simple specs→rich references. Two of them carry most of the work on a real file — rules becoming judgement, and hot-path detail moving behind a pointer — and they are the two a structural pass silently skips, because neither shows up as a section in the wrong place. That applies to this file as much as to any target.

A large cut is a fine outcome and often the right one — what doesn't transfer is treating the percentage as the goal. Anthropic didn't compress their prompt into a terser version of itself; they deleted rules that had stopped being true and rewrote the rest as principle, so `never write multi-line comment blocks` became `match the surrounding code's comment density`. Fewer words, same meaning, now applicable to cases the enumeration got wrong. That's the operation: meaning is what's conserved, form is free. Squeezing prose for bytes is the other thing, and it doesn't hold — two skills hand-condensed that way measured denser than their pre-fix state a fortnight later. And in a file edited ~22 times a week, a cut without a change to what gets admitted just refills, so the durable lever is arrival rate even when the cut itself was right.

One boundary is measured rather than argued: prose-only is right for judgement-shaped content and *wrong* for value-shaped content, where a reader needs a literal answer prose has nowhere to carry. A command, an error string or an id stays a lookup row however much reasoning surrounds it — an A/B test found a reader's confidence drops on a pure-lookup question when prose has dissolved the value it needed.

## Read the file as a document first

Read it end to end before opening a single rule, and form a view on six things. A source the pass leans on gets the same treatment — an article summarised from memory yields a reading that is plausible, specific and wrong in the details that decide the rewrite.

- **What does this make a reader do, in order?** Where the physical order disagrees with the execution order, a reader meets rules before there's anything to apply them to and mostly won't carry them that far.
- **Where does each rule sit relative to the moment it's needed?** A correct rule in the wrong place fails as reliably as a wrong one — commonly a warning stacked above the branch it governs, or a mandate in a path most invocations skip.
- **What does it say more than once, and do the copies still agree?** A rule in three homes is three sessions patching the same miss without retiring the previous patch, and collapsing them beats sharpening any one. Copies drift as well as duplicate: two statements of the same fact hundreds of lines apart can contradict outright — one saying a tool doesn't exist here, the other giving its install path — and whichever a reader hits first is the one they act on. Reconciling that pair is a correctness fix, not a tidying one, so it survives even when you leave the rest of a section alone.
- **What would a reader who absorbed all of it default to?** Not what any row says — what the balance trains. Twenty mechanical rows beside one judgement sentence produce a reader who reaches for the instrument every time, because the instrumental options carry concrete shape and the judgement is a line they scroll past. This is the only question that fails on a file where every individual row is true, and the answer can be that a section of correct rows should collapse into the reasoning it encodes.
- **Which enumerations are standing in for one principle?** An enumeration is the raw material this pass converts. Twenty rows each naming a way to have erred usually encode two or three mechanisms a reader could apply to cases the list never anticipated — `never write multi-line comment blocks` becoming `match the surrounding code's comment density` is the whole operation in one line. Name the mechanism each cluster encodes; that name is the replacement.
- **What here does a reader need on every invocation, and what do they need twice a year?** The rare half belongs behind a pointer in `references/`, and the file auto-loading on every turn is where this pays. Read frequency answers this for a lookup — an error string, a command, an id — because the reader arrives already holding the failure that sends them looking. It answers it wrongly for a rule governing a routine choice (which tool to reach for, what to check before a common action): that rule is read seldom precisely because it's meant to be absorbed, and there's no symptom to search under until someone has already violated it, so deferring it behind a pointer means it never arrives again. Ask what the reader is doing when they need it — holding a failure, or about to act — and keep the second kind on the every-turn path however rarely it's consulted. A hundred-row lookup table nobody reads until something breaks is the standing candidate. A target's own claim to already defer content ("does NOT auto-load") is not evidence to take at its word here — verify against how the harness actually loads that file; 📖 `references/target-types.md`'s on-demand-reference-tables entry for the check. This question is not answered by confirming the content is factually genuine — that's the constraint-vs-fact test further down, and it answers a different question. A thousand true, incident-backed facts can still be the wrong thing to load on every turn; "every row here is earned" and "this should all auto-load unconditionally" are separate claims, and settling the first is not settling the second. Where the target already documents having been assembled FROM separate on-demand files (a "merged from N companions" note, a changelog of a prior split), that's a standing signal the reverse move — splitting back into files the harness doesn't auto-load, reached by the pointers already in the text — needs to be genuinely evaluated as the primary candidate, not dismissed in a paragraph because the merged content reads as accurate and dense. Evaluating it means sizing what a split would actually remove from every-turn cost and naming why it's rejected, not asserting the current framing is honest and treating that as the whole answer.

The first four questions are about shape and the last two about content, and that split is why a pass can go wrong while looking thorough: reordering sections, merging duplicate homes and regrouping a table all answer the shape questions completely, and a file can come out of that better organised with every rule it started with. Reorganisation is not this pass. If nothing became a principle and nothing left the hot path, the two content questions went unanswered whatever the structural work looked like.

A target large enough that the six-question read feels like the whole job is exactly where this pass most often substitutes a different one: a file that announces its own recent merge or restructure reads as evidence the shape work is already done, and the reasoning quietly drifts to whether the file is big (`condense-claude-md`'s question) instead of whether its rules are judgement dressed as mandate (this pass's question). Answering "is this bloated" is not answering "is this overconstrained," and a verdict built on the first while believing it settled the second is the failure this paragraph exists to name. Read `references/target-types.md` before concluding a large or already-restructured target needs no edit — not after, and not only when its class is ambiguous — because the file exists specifically to correct the size-driven misreadings this pass is prone to (a `📖` pointer inside an always-loaded CLAUDE.md is not progressive disclosure; the harness loads the whole file regardless of what any paragraph inside it claims about deferring).

Reading is what does this. A marker count locates candidates and nothing more — density predicts a file's subject, not its health, so the densest file is often the healthiest and the one with no markers can be the badly shaped one.

## Then, per rule

Take the cluster verdicts first, because this step will otherwise quietly overturn them. Every row in a thirty-row table passes the per-row test on its own — each was earned by a real incident and each names something true — so a pass that drops straight to row-by-row judgement keeps the table intact and reports the enumeration as irreducible. It isn't; the question was never whether a row is true but whether thirty of them are the right form for what two or three sentences of mechanism would cover. Convert the cluster, then run the test below on what's left.

Converting a large cluster is a rewrite, not a deletion, and that distinction is what makes it safe to attempt. The mechanism sentences replace the rows, the value-shaped specifics inside them survive as a shorter table or a companion, and a reader ends up able to handle cases the enumeration never listed. Where a cluster genuinely resists — the rows share no mechanism, each is a separate arbitrary fact about a different tool — that is a real finding worth stating, and the honest form of it names what you tried to abstract and why it didn't hold. On a file with many tables, that verdict is earned per table, not per table-genre: skimming three tables, calling their shape "heterogeneous facts," and extending that label to every table sharing their format is the row-by-row shortcut one level worse — it never opens the un-sampled tables at all. A genre-level "no clusters here" claim needs at least one attempted, failed conversion per distinct table to back it, named in the report; a claim resting on a sample is a claim about the sample. This generalizes past cluster-convertibility: a whole-file verdict ("well-shaped", "no edit needed") built the same way — a handful of tables sampled, found sound, and the finding silently extended to every table the pass never opened — is the identical shortcut wearing the file-level report instead of the table-level one. The sample size the verdict needs scales with what it's a verdict about; five tables checked out of forty is a claim about five tables, not about the file.

The conversion runs one direction only: enumerations become principles, never the reverse. A section already written as reasoning is the finished product of this operation, not raw material for it, and it will look like a target because it is long, unstructured and free of the concrete rows that read as substance. Compressing it into a numbered checklist reads as tidying and is the operation running backwards — the general statement is what let a reader handle the case nobody enumerated, and a list of five named failure modes silently narrows the file to those five. Prose that states a mechanism is the most expensive thing in the file to regenerate and the easiest to mistake for padding, so leave it whole unless it repeats a sibling.

For what remains: **is this a fact the model can't derive, or a constraint forcing process onto something judgement covers?**

A fact has a checkable consequence if missed — a harness quirk, a binary with a silent-failure cost, a structural detail of this repo. No amount of reasoning gets a reader there; it has to be told. A constraint restates what a competent read would conclude anyway, made rigid because a past mistake got patched with a rule instead of trust. Its tells: a trip-wire naming one specific way to have failed, a bolded imperative, a numeric threshold standing in for "does this feel right", two callouts making the same point, a worked incident sitting in the instructions instead of git history.

A row can pass on content and still carry this in its decoration — an `⚠️` or trailing `**Tell:**` that only restates the row's own condition adds nothing, while one naming a checkable fact the row's text lacks earns its place. These are separate questions about the same row.

Facts stay, stated plainly. Constraints become reasoning. Two things to protect while cutting: a stated limitation is a fact even though it reads like hedging — delete "this check does not prove X" and the confident half asserts a guarantee the original withheld. And a rule that reads as absolutist may be the surviving fix to a documented incident, so grep the project's `decisions/*.md` for its keywords before softening; a Rejected-alternatives entry saying judgement was tried there and failed outranks this pass's lean toward loosening.

📖 `references/target-types.md` — what counts as a genuine fact per target class, and the ADR-blocks-inside-a-task-doc case where the boundary runs through a file rather than around it.

## Routing decisions during rewrite

As constraints become reasoning and enumerations collapse into mechanisms, ask where the resulting content actually belongs — some fact may have earned its way to the page but still doesn't belong in an always-loaded file. Four routing questions run in sequence:

1. **Is it derivable?** (same test as `update-claude-docs/SKILL.md` §2a) — if a reader could reconstruct it with `ls`, `grep`, reading the manifest, or running `--help`, cut it outright rather than rewriting it.

2. **Is it safety-critical?** — prohibitions that *must* fire even if ignored by a prior session (e.g., "never edit generated files", "never push to main") are always resident, never deferred. Their cost is fixed; their value is irreplaceable.

3. **Does it need to arrive before action, or only during failure?** (§2b's residency gate, reordered by stakes) — A rule governing a routine choice (which tool to use, what to check before an action) needs to be resident, absorbed preemptively, because deferring it behind a pointer means it only fires again after someone violates it. A consultation rule, implementation detail, or symptom-indexed gotcha is different: it's read by someone already holding a failure, so moving it to a `📖` pointer or a lazy-load skill costs nothing and gains resident clarity. This is the every-invocation-vs-twice-a-year test from the six-question read (above) applied to the rewritten content.

4. **Is it a reference table or lookup?** — A section that reads like a catalog (error strings, commands, configuration paths) should usually move behind a pointer in `references/` or become a lazy-load skill, even if you've just finished sharpening its prose. The densest reference table is still the wrong thing to auto-load on every invocation unless it *must* fire unasked.

If content passes all four tests, keep it resident and rewrite as planned. If it fails any, decide whether to delete it (derivable), defer it (failure-triggered), move it to a skill (task-specific), or split it into a companion (reference table). The rewrite — making constraints into judgment — doesn't change this routing; it just clarifies what the content is, so the routing decision lands correctly.

**Coupling note:** A SKILL.md that accumulates multiple routing tiers (resident rules + lazy-loaded content) is a signal to split it. Each tier has a distinct reader audience (absorbed on every session vs. invoked on-demand), and they fight for brevity differently.

## Rewrite the file

List the genuine facts first, marking which are stated absolutely — that list is what verification checks against, and a fact can survive in full while its force quietly doesn't.

Then write it. A full `Write` once more than a handful of rules are affected, targeted `Edit`s for one or two callouts.

Structural findings are the ones that go unexecuted, because moving a section feels like a bigger claim than softening a callout — but a file whose shape is wrong stays wrong when only its wording changes. Do the moves.

A move means the destination file exists and holds the content when you finish. Write it first, then cut from the source — the two halves in one pass, never a deletion now against a companion "ready to split" later, because the leaner file is the same either way and only one version still has the facts. This is the failure worth being most careful about: it looks identical to a successful extraction from the source side, it reads as the pass's best work, and the report will say every fact was preserved because moving them was the intent. Ninety rows of harness facts have gone this way. If the pass ends and a companion you named doesn't exist, the content is deleted, whatever the summary claims.

⚠️ **When the move is "split back into on-demand companions" (the every-invocation-vs-twice-a-year test's trigger), mapping one new file per pre-existing heading reproduces the grab-bag this pass exists to fix, one level down.** A source section titled "Backend Overflow" or "Reference (former companions)" got that name from an earlier merge, not from a reader's search pattern — copying it wholesale into one companion just relocates ten unrelated topics under a new path, so a reader chasing one symptom still scrolls past nine others, and the new file is next session's overconstrained-wall candidate. Cluster by what a reader actually searches on (the trigger symptom, the tool, the class name) and give each real cluster its own file, even when that means many small files instead of one that mirrors the old table of contents. This mechanics — clustering, naming, the pointer-index requirement that makes an unloaded file actually get read — is owned by `condense-claude-md`'s `references/structural-splits.md` (its #7 lever); read it before executing a companion split rather than re-deriving the same call.

Proposing the rewrite back instead of performing it is the failure mode this section exists to prevent. There is no approval step: the file is version-controlled, a bad rewrite is one `git checkout` away from gone, and asking costs more than reverting would.

## Verifying

Read the rewritten file from the top, whole — the same read as the one that opened the pass, asking whether a reader of this file still knows what a reader of the old one knew, and whether it sits right as one document. The worst defects exist in no hunk: two sections that shouldn't coexist, a rule split across two homes hundreds of lines apart, a heading describing the file as something it isn't. Each hunk is locally fine, so a diff review is blind to all of them by construction. Where something is wrong, name the passage.

Counting doesn't reach this. Surviving identifiers, anchors, rows, bytes — each answers "how many survived", which is answerable and different from "does this work", and a search for a fact you suspect was dropped returns zero just as readily when the fact was reworded.

Restructuring also invalidates references, and they never 404: the reader lands somewhere plausible and concludes the fact isn't there. The ones inside the file you just rewrote are the easy half and the half most often missed, because moving a section elsewhere leaves every sentence that said "see the X section below" pointing at nothing — read those in place. References in *other* files are the harder half: locating them is search's job, and deciding whether each still reads true means opening it.

An empty heading is the same defect in miniature. Emptying a section without removing its heading leaves a reader an anchor that promises content and delivers none, and it survives every check because the heading is exactly what a structural pass looks for.

📖 `references/verifying.md` — what each check can and cannot see, what delegation changes, and the markup damage that survives every content check.

Report both halves: what moved, merged or got resequenced, and what stopped being an enumeration or left the hot path. A report that is all structure describes a reorganisation, and one that is all softened callouts describes a wording pass — either alone reads as complete while the other half never happened. Where a half genuinely had nothing to do, say that rather than omitting it. Every claim names an edit that landed; a strategy, a proposal or an estimated cut belongs to a pass that didn't run. Say where you made a bet rather than a strict improvement: trading a mechanical check for a judgement call is a real trade-off, since the mechanical one fires regardless of how a read feels.

Reading the file and finding it well-shaped is a legitimate outcome, and it is the one case where the report is the whole deliverable — say so plainly, since it's also what a marker hunt produces. What it is not is the default when a rewrite felt too large to attempt.

## Owning skill/plugin conventions

For a syafiqkit target, this runs alongside the plugin's authorship conventions: version bump + CHANGELOG entry, the ownership check before patching (never edit a consumer-side install), and a shared-mechanism grep before assuming a fix is single-file. For a third-party file, none of that applies.

## What this is not

Not a condensing pass — `condense-claude-md`/`condense-task-doc` own byte reduction and structural splits. Not a correctness review: a rule can be correct and still the wrong shape, and prose can read well and be quietly wrong, which `code-reviewer` catches and this doesn't. Not a one-time fix, since overconstraint accumulates one patched worst-case at a time.
