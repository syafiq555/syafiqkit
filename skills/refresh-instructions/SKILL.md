# Refresh Instructions

Three passes, same file, one after another: **restructure** (canonical section order) → **condense** (density) → **unhobble** (judgment vs. constraint). Each pass answers a different question, and running them in this order means condense works on already-correctly-ordered content, and unhobble works on already-tight prose instead of fighting bloat and structure at the same time.

This skill is pure sequencing. All three passes, the dispatch mechanics, and the verification discipline (snapshot before, re-measure after, read for meaning not diff, patch-vs-revert) already live in `syafiqkit:haiku`. This file only says which three skills, in which order, on which file type.

⚠️ **Invoke `Skill(haiku)` immediately before writing EACH pass's prompt — three invocations, not one read at the start.** Its `## Writing the prompt` section is what stops a prompt arriving closed, and that section only helps while it is in front of you: a skill body enters context once and is never re-attached, so by the third prompt its rules are being recalled rather than read, and recall drops the clause that applied. Measured 2026-09-14 on a task doc, having read `haiku` at the session's start and dispatched from memory three times: Pass 2's prompt said "a row-existence and density pass, not a demolition" and **zero of 57 rows were deleted** against `condense-task-doc`'s own "expect to delete some"; Pass 3's said "do not condense", which forbids both moves `unhobble-instructions` names as carrying most of the work. `haiku` already holds a **Tell:** naming that exact shape — it was in context at the start of that session and fired for none of the three prompts. This is a routing fix, not a wording one: the rule was correct, present, and stale at the only moment it mattered.

## Pick the pair by file type

| Target | Pass 1 (restructure) | Pass 2 (condense) | Pass 3 (unhobble) |
|---|---|---|---|
| `CLAUDE.md` | `update-claude-docs` (rewrite mode) | `condense-claude-md` | `unhobble-instructions` |
| Task doc (`current.md`, `decisions/*.md`) | `task-summary` (rewrite/conform-to-template) | `condense-task-doc` | `unhobble-instructions` |
| Project doc set (`docs/PRD.md`, `ARCHITECTURE.md`, `ARCHITECTURE-ESSENTIALS.md`) | `setup-project-docs` (update mode) | `condense-task-doc` | `unhobble-instructions` |
| Any other living doc (README, runbook, design doc, spec sibling) | no owning skill — restructure in place, see below | `condense-task-doc` | `unhobble-instructions` |

**`condense-task-doc` on the bottom two rows is deliberate, not a mis-edit.** Its keep-test is about facts rather than file types — *would losing this cause a future session to act incorrectly* — and its own description already claims "current.md or any markdown living-doc". Two of its rules are written for exactly these targets: the spec-sibling rule covering a `stories.md` or acceptance-scenarios file, and the provenance rule that names `PRD.md` and `ARCHITECTURE.md` as the files carrying `[TBD]`/`[SOURCED]`/`[INFERRED]` tags and says to leave them alone. What *is* task-doc-specific lives in 📖 `../condense-task-doc/references/section-rules.md`, a cold-path lookup keyed by literal section heading (`## Quick Start`, `## Bugs Fixed`) — so on a doc with none of those headings it matches nothing and yields nothing, rather than imposing a task doc's shape on a README.

**Where no skill owns pass 1, restructure against the document's OWN contract** — what a reader opens it to answer — never against a template borrowed from a row above. A README reshaped into a task doc is a worse file than the one you started with, and the pass will report success either way. Where the target resembles a PRD or an architecture doc, 📖 `../setup-project-docs/references/standard-shapes.md` is the shape authority (arc42, C4, PR/FAQ, Shape Up); otherwise the ordering question is the one Pass 3 asks anyway — does each rule sit where the reader is when it applies. A file already ordered well gets "nothing to do" reported and the sequence drops to two passes, per *When not to run all three* below.

## Process

Run each pass as its own `haiku` dispatch — three dispatches, not one prompt naming all three skills. A single prompt listing multiple skills has them overwrite each other's accounts; three sequential calls each get a clean snapshot-verify cycle, per `haiku`'s own partition rule.

1. **Snapshot** the target before Pass 1 (per `haiku`'s pre-dispatch discipline). ⚠️ **Probe for git once, here, and carry the answer through all three passes** — `git rev-parse --git-dir` and `git rev-parse HEAD` answer different questions and a repo with no first commit passes the first and fails every later `git diff HEAD`. Where either fails, every verification step below loses its instrument: snapshot to a scratch path and compare with `wc -c`/`cmp` rather than `git diff HEAD`, find surplus agent writes by mtime rather than `git status --short`, and tell each dispatched agent the tree is not a repo so it does not `git init` one to be helpful. 📖 `../_shared/references/verifying-a-write-landed.md` § When Git Cannot Answer holds the full substitution table — and its warning that ownership caution gets *stronger* without git applies hardest here, since a three-pass rewrite has no `git checkout` to fall back on when a pass overshoots.
2. **`Skill(haiku)`, then dispatch Pass 1**, wait, verify (byte/line diff, then read the whole file for meaning — not the agent's report).
3. **Snapshot again** on top of Pass 1's verified output, then `Skill(haiku)` again before writing Pass 2's prompt; dispatch, wait, verify.
4. **Snapshot again**, `Skill(haiku)` again before writing Pass 3's prompt; dispatch, wait, verify.
5. Report what changed pass-by-pass, not just the net diff — a reader deciding whether to trust the result needs to know which pass moved what.

**Stop between passes if a pass fails verification.** A condense running on top of an unverified restructure inherits whatever that restructure silently dropped, and the drop compounds — patch or revert before continuing, never chain onto unverified output.

⚠️ **Verifying a pass and PATCHING it are two acts, and the snapshot between them records your fix without making the next agent see it.** The steps above read as one cycle — verify, snapshot, dispatch — so a patch applied in between feels like part of the verified state it is nominally "on top of". It is not: the next agent re-reads the file, and if it opened the target before your patch landed, it works from the pre-patch copy and then silently reverts you while reporting honestly against its own baseline. Measured 2026-09-11 on a four-file refresh: a restored `<!--LLM-CONTEXT-->` block was gutted a second time by the Pass 2 agent, and the same block needed restoring twice in one run. `haiku` already states the rule ("confirm the file matches the baseline you intend immediately before dispatching"), and stating it again is not the fix — it failed because a patch made minutes ago reads as obviously current.

**So make the next prompt carry the evidence instead of your memory.** After any patch between passes, put the post-patch counts into the next dispatch's prompt as numbers the agent must check before editing (`this file has 18 gotcha lines and 8 Related paths; if you see fewer, stop and report rather than proceeding`). The prompt is an artifact you have to write anyway, so the check rides on work already happening rather than on a discretionary re-read — and it moves the catch to the one party who can still see the mismatch.

**Carry forward the same protected-fact list across all three dispatch prompts.** Build it once, before Pass 1, by reading the target; don't rebuild it per pass, since a fact that survives Pass 1 reworded needs the same protection in Pass 2's prompt even though its wording has changed.

⚠️ **Only two things belong on that list as a CATEGORY, and both for the same reason: they are cross-file contracts a single-file pass cannot see it is breaking.** `{#anchor}`s and `📖` pointers are named by other files, so their loss surfaces somewhere the agent never opens — and both are machine-checkable after the fact, which is what makes blanket protection safe. Everything else goes on as a NAMED INSTANCE whose loss you can state a cost for. The tempting third entry is a content class — dated incidents, `⚠️` callouts, `**Tell:**` lines — and that one inverts the pass: by Pass 3 you are dispatching `unhobble-instructions`, whose entire job is judging whether each rule earns its shape, so protecting a class by its syntax deletes the deliverable and leaves the agent unable to disagree, since a claim about form cannot be refuted the way a claim about code can. Say what the class is FOR and let the agent judge members. 📖 `syafiqkit:haiku` § Writing the prompt for the measured case (2026-09-11) and `../_shared/references/explore-delegation.md` § Handing an agent a judgement-bearing skill.

Every dispatch prompt must name the banned git verbs per `haiku`'s own rule (`commit`, `push`, `stash`, `reset`, `checkout -- .`, `clean`) — this rule exists precisely because a bare "run the skill and report" prompt left one uncaught.

⚠️ **Every instruction above narrows the agent, so a prompt assembled only from them arrives closed — and the move it closes first is the one that removes bytes.** Both condense skills own splitting and `unhobble-instructions` names routing-to-a-companion as one of two moves carrying most of the work; all three write a second file, which "target: this file, edit it in place" forbids without ever appearing to forbid anything. The pass then has only in-paragraph rewording left, which is why the tell is a **line count that barely moves while bytes drift down a few percent** — real structural work shows up as lines leaving. Measured 2026-09-12: a CLAUDE.md briefed this way went 51,030 → 46,461 bytes across two passes and stayed at 301 lines both times, against a skill budget of ≤40KB, with a 11KB layer-named section its own skill would have split on sight.

**Name each pass's own structural count in its prompt, and check it on return.** The prose above is the fourth-plus statement of the over-constraint rule and it keeps failing, so carry a number that a closed prompt cannot satisfy quietly. Each pass owns one: a condense pass owns gotcha/decision **rows** before, after, and how many were *deliberately deleted* (its own step 5 requires exactly this reconciliation); `unhobble-instructions` owns whether anything **became a principle or left the hot path**, which its own reading section calls the two content questions a reorganisation answers by leaving every rule in place. Ask for the figure in the prompt and re-take it yourself on return — an unchanged count with a tidy byte delta is the signature of a pass that only reworded, and it is the one reading the agent's report will never give you. Measured 2026-09-14: 57 rows in, 57 rows out, 10.7% of bytes gone, reported as "no structural rows deleted" and true as far as it went.

**So state the extraction axis before writing the protected-fact list.** Name where a companion may be written and what already lives there, or say plainly that this target has nowhere to extract to and detail should therefore be cut on its merits rather than moved. Either sentence leaves the agent a decision; supplying neither answers it. Where a genuine obstacle closes the axis — a concurrent agent rebuilding the destination directory — say so *as the caller's constraint* and expect the report to name what it would have moved, per `unhobble-instructions`' own rule about a closed axis. A dispatch that mentions companions only as paths that exist is not an opening; it reads as context.

## When not to run all three

A file that's already well-structured and tight needs only `unhobble-instructions` — don't restructure or condense something that isn't bloated or misordered just because this skill exists. Check line count and skim structure first; if restructure and condense would both report "nothing to do," skip straight to unhobble and say so rather than running three passes for one pass's worth of change.

This bites hardest on the bottom two rows, where a skipped pass and a performed one are hard to tell apart afterwards. A restructure with no template to conform to has no artifact proving it ran, so an agent with nothing to do and an agent that did nothing both return a clean-looking report — and the second one has usually reshuffled sections to have something to show. Decide before dispatching whether Pass 1 has real work, and where it doesn't, don't dispatch it.
